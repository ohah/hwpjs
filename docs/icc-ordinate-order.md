# ICC 정확한 출력값과 유리수 목표 비교

## 계약과 책임

`power_ordinate_order.compare(precision,value,target)`는 power_ordinate.Value와 정규화된 u128 목표 분수의 순서를 반환합니다. 결과는 lt/eq/gt 또는 정밀도 부족을 뜻하는 null입니다. 유리수 출력은 기존 WideFraction의 u512 교차곱을 사용합니다. 거듭제곱 출력 `base^(g/65536)+offset/65536`은 목표에서 오프셋을 정확히 뺀 뒤 공통 유리수 거듭제곱 비교기로 전달합니다.

오프셋 차감 분자는 `65536*n-offset*d`, 분모는 `65536*d`입니다. u128 목표와 i32 offset은 분자에 최대 161 signed 비트, 분모에 최대 144 unsigned 비트가 필요하므로 i128로 줄이지 않고 i256/u256을 사용합니다. 부동소수점·16.16 재양자화·근삿값 동등 판정은 하지 않습니다.

기존 [유리수 거듭제곱 비교](icc-rational-power-order.md)는 Of(128/256) 공통 구현으로 확장했습니다. 기존 compare 함수는 Of(128) 진입점으로 유지합니다. 부호·정의역·정확한 동등성·방향성 경계 규칙을 복제하지 않습니다. 폭은 비교 입력의 폭이고 precision은 경계 연산의 정밀도이므로 서로 다릅니다.

목표와 유리수 출력은 [0,1] 유효성을 검사합니다. power 표현은 공장 함수가 (0,1) 내부라고 증명한 정확한 식이지만, 이 비교기에 직접 구성해 전달하면 클리핑 없이 그 식을 비교합니다. 0인 분모·음수 밑의 비정수 지수·0의 비양수 지수는 공통 비교기에서 거부합니다. 이 함수가 임의 power 식을 클리핑하거나 곡선 전체 정의역을 검사한다고 해석하지 않습니다.

## 검증 진행

신규 네이티브 4개와 기존 rational_power_order 테스트 4개가 통과했습니다. i256 최솟값, u128보다 큰 완전제곱의 정확한 제곱근/역수, 넓은 목표의 offset 차감, u256 유리수, 실수 정의역 오류, 공장 출력과의 연결을 검사합니다. sqrt(1/2)와 11749380235262596085/16616132878186749607 비교는 128 정밀도에서 null, 512에서 lt이며 미확정을 동등으로 바꾸지 않습니다.

테스트 mode208은 104바이트 BE 입력을 받습니다. precision u32, 목표 n/d u128, tag u32 뒤 64바이트 payload입니다. tag0은 n/d u256, tag1은 base n i128/d u128·g i32·offset i32와 24바이트 0 패딩입니다. 출력 i32 LE -1/0/+1/2는 lt/eq/gt/미확정입니다. 태그·길이·패딩·정밀도·자원 한도를 검사하며 제품 JS 공개 API는 바꾸지 않습니다.

독립 JS는 기존 BigInt 거듭제곱 기준에 오프셋을 차감한 정확한 유리수 목표를 전달합니다. 제품의 방향성 경계 알고리즘이나 equality 함수를 기대값 생성에 사용하지 않습니다. 직접 Debug WASM 실행은 comparisons=1350/rejected=474/undecided=1, 총 1,825건이 통과했습니다. 오프셋 제거·미확정을 동등으로 변경·순서 반전 변형은 각각 ERR_ASSERTION으로 검출했습니다. 제품에 변형을 남기지 않았습니다.

전체 세 모드 감사 결과는 아래 최종 확인 절을 기준으로 합니다.

적대적 네이티브 검증은 `/tmp`의 별도 소스 복사본에서 오프셋 차감을 덧셈으로 바꿔 실행했습니다. Debug·ReleaseSafe·ReleaseFast 모두 4개 중 2개가 TestExpectedEqual로 실패하여 잘못된 구현을 검출했습니다. 큰 목표 분수와 공장 함수의 실제 출력 연결이 각각 검출했으며 원본에는 변형을 적용하지 않았습니다.

## 실제 프로파일 연결 확인

DCI(P3) RGB·Display P3·ITU-2020·ITU-709·ROMM RGB의 RGB TRC 15개를 읽기 전용으로 검사했습니다. 전체 출력 범위 mode207의 상위 분기 양 끝 값을 그대로 복원해 mode208에 전달하고 목표 0/1과 비교했습니다. type0 하한은 0, type3 하한은 엄격히 (0,1), 모든 상한은 1이라는 기대를 원본 양의 지수·기울기·내부 시작점·a+b=65536 및 양의 시작 밑에서 정한 뒤 대조했습니다. 60건이 모두 통과했으며 수동 검사로 정규 audit 호출 수에는 합산하지 않습니다. OS 색상 변환·HWP 렌더링 검증은 아닙니다.

## 최종 확인

Debug·ReleaseSafe·ReleaseFast 전체 audit가 각각 종료 코드 0, 20/20 단계, 네이티브 582/582, WASM checks=6,574,589로 통과했습니다. 신규 1,825건이 이전 6,572,764건에 추가됐습니다. 각 모드 신규 결과는 comparisons=1350/rejected=474/undecided=1입니다. 로그는 `/tmp/hwpjs-icc-ordinate-order-{Debug,ReleaseSafe,ReleaseFast}.log`입니다.

ReleaseSafe·ReleaseFast의 실제 감사 산출물 직접 실행에서도 같은 신규 수치를 확인하고 미확정을 동등으로 바꾸는 변형을 각각 ERR_ASSERTION으로 검출했습니다. 변경 Zig 포맷·JS 문법·diff 공백 및 관련 문서 로컬 링크 8개를 확인했습니다.

최종 재검토에서는 기존 i128 API 보존, 폭에 따른 공통 equality 재사용, 부호 단축 전 실수 정의역 검사, signed 최솟값의 unsigned 절댓값, 오프셋 차감의 i256/u256 한계, 정확한 동등성과 미확정의 구분, 공장 출력과 직접 구성한 식의 계약 차이, 테스트 wire의 길이·태그·패딩 검사 및 결과 초기화를 확인했습니다. 분자 상한을 160 signed 비트로 적었던 주석·문서 오류를 발견해 161로 수정했습니다. n=d=2^128-1, offset=-2^31이면 크기 160비트에 부호 1비트가 더 필요함을 BigInt로 확인했습니다. 구현은 처음부터 i256이므로 산술 코드 수정은 필요하지 않았습니다. 이외 추가 결함은 발견하지 않았습니다.

## 남은 범위

이 단계는 출력 하나와 u128 목표값의 순서 비교입니다. 두 기호적 출력 간 거리 비교, 최근접 출력의 존재/동률 결정, 역변환 입력 선택과 HWP/HWPX 전체 문서 검증은 아직 미완료입니다. 목표를 u256까지 확장하려면 오프셋 차감이 256비트도 넘을 수 있으므로 현재 함수를 단순 캐스팅으로 확장하지 않습니다.
