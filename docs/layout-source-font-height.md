# 내부 투영에서 문서 글자 높이 보존

## 원인과 수정

layoutContent의 documentBody 경로는 알려진 문서 형식에서만 글자 높이 최소값20px를 제거합니다. 셀·단·개체 영역의 내부 호출이 paragraphs만 전달하면서 content.format을 생략해 실제13pt 높이17.333333px가20px로 강제됐습니다. HWPX145% 행간에서는 한 행이25.133333px 대신29px가 됩니다. 이는 noAdjust 의미와 별개인 구현 문제입니다.

명시적 content.format 또는 문단 paragraphShape.spacingFormat이 HWP5/HWPX인 경우 동일한 문서 높이 정책을 사용합니다. 형식 단서가 없는 프로토타입은 기존 UI 최소값을 유지합니다. 새 글꼴 추정값·캐시·별도 행간 산술을 추가하지 않습니다.

## 재현과 현재 근거

layout-source-font-height.test.mjs는 같은 문단에서 외부 format을 전달한 경우와 셀처럼 생략한 경우의 전체 행·높이를 비교합니다. 수정 전29px 대25.133333px로 실패했고 수정 후 동일합니다. 미지 형식의20px 호환 동작도 검사합니다.

실제 copay/5f3baacd 후보/현재 JS 브라우저에서 이전의 문단520 UnsupportedPageRow가 사라지고 측정16페이지·1206행·그림8/8해독이 됩니다. 꼬리 구간을 스크롤하며 Canvas drawImage 호출6회를 확인했습니다. 첫 실행은 빈 마지막 화면에 그림이 있으리라는 도구 가정 때문에 timeout됐으며, 마지막35%를 순차 탐색하도록 수정한 뒤 통과했습니다. 이는 원본 한글 페이지 동치나 모든 그림의 시각적 정확성 증명이 아닙니다.

두 번째 통과 산출물은 hwpjs-page-area-objects-x0C2Ky입니다. viewport를 화면 안으로 이동한 first.png에서 실제 표·본문 제목 표시를 직접 확인했습니다. tail-picture.png는 흰 영역으로 보이므로 drawImage 호출만으로 꼬리말 그림의 시각적 정확성까지 통과했다고 판정하지 않습니다. 이 도구의 통과 범위는 페이지 오류 없음·자원 해독·꼬리 구간 이미지 호출·원본 불변·세션 정리이며, 꼬리말 픽셀/편집 왕복 검증은 남아 있습니다.

고정8px 진단은17쪽에서13쪽으로 바뀌어 source 선언 소유자는 그대로지만 두 footer의 실제 바인딩 쪽이 모두11이 됩니다. 같은 쪽의 후속 선언을 선택하는 기존 정책에 따라 먼저 선언된 inline footer는 교체됩니다. page-area-declaration-table-reference 회귀는 이 변경과 뒤 footer의 표/도형 합성을 검사합니다. 고정 폭 쪽 번호를 원본 조판 oracle로 다루지 않습니다.

문서 높이·Worker 편집/이력/저장 재열기·행 페이지·숫자 진단 회귀4파일18/18·skip0을 확인했습니다. 포함된 추적 HWPX는45배치/암호1거부입니다. 추가 실제 복합 문서 회귀1/1도 통과했습니다. 기본 데모·전체 native 완료와 구분합니다.
