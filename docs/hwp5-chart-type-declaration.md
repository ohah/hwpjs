# 차트 타입 선언의 관측 배치

## 계약

`chart/type_declaration.zig`의 readObserved16은 호출자가 확정한 새 타입 선언 위치에서 u16 이름 바이트 수 → 이름 원본(마지막 NUL 포함) → u16 버전을 읽습니다. 길이 0과 마지막 NUL 누락은 InvalidChartTypeName, 이름 한도 초과는 LimitExceeded, 부족한 입력은 UnexpectedEnd입니다. 실패 시 입력 Reader 위치는 그대로입니다. 결과는 입력을 빌리고 할당하지 않습니다.

이름을 UTF-16·UTF-8·CP949로 해석하지 않으며 내부 NUL이나 알 수 없는 버전 값을 보정하지 않습니다. 길이 1의 NUL 이름도 바이트 배치로 보존합니다. 유효한 타입 이름의 의미 검증을 뜻하지 않습니다. 반복 타입 ID의 정의 여부, 객체 id/typeId, 객체 데이터, Contents 전역 헤더, 차트 유형 식별은 이 함수가 처리하지 않습니다. 문자열을 검색해 위치를 정하거나 HWP의 UTF-16 문자열 리더를 재사용하지 않습니다.

## 명세와 실측

[공식 자료·초기 관측](hwp5-chart-contents-evidence.md)의 객체 그림은 새 타입의 이름/버전과 재등장 시 생략을 설명합니다. 이번 구현은 그 중 관측된 이름/버전 바이트 배치만 명시적으로 선택해 읽습니다. 그림의 int 표기를 모든 플랫폼의 u16 저장 규칙으로 일반화하지 않습니다.

같은 43개 문자열 관측 표본에서 Contents의 오프셋 32 u32 값은 모두 전체 길이−36과 같았고, 36/40의 u32는 0/0, 44의 u16은 8, 46부터는 VtChart 뒤 NUL, 54의 u16은 6이었습니다. 초기 조사 명령에서 길이를 30에서 읽은 가설은 0/43 일치로 기각했고, 2바이트 단위 덤프로 위치를 다시 확인한 뒤 32에서 43/43 일치를 확인했습니다. 제품에 오프셋 30/32 자동 판정 규칙을 추가하지 않았습니다.

이 관측은 전체 헤더의 의미나 36이 모든 문서에서 루트 객체 시작이라는 규칙을 확정하지 않습니다. 타입 선언 자체는 임의의 호출자 지정 위치에서 처리합니다. 같은 표본의 다음 VtDataGrid 선언이나 VtMatrix 상속 경로를 동일한 두 u32 헤더로 반복 해석할 수 있는지는 아직 별도 검증 대상입니다.

## 검증

네이티브는 위치 0/1/17/96, 이름 원본 포인터, 선언 뒤의 미소비 바이트, 모든 짧은 입력, 최대 offset, 이름 한도·잘못된 NUL·0 길이, 이름 길이 1/7/8/255/256/65535, 버전 0/1/6/256/32768/65535를 검사합니다. 최대 길이 테스트의 초기 `1 + length`가 u16 오버플로로 ABRT했고 테스트 인덱스를 usize로 수정했습니다. 제품 코어에서 발생한 오류로 세지 않습니다. 수정 후 Debug/ReleaseSafe/ReleaseFast 필터는 각각 root 포함 4/4 통과했습니다.

비공개 mode 308은 offset u32, 이름 한도 u32, 원본 바이트를 받습니다. 반환은 이름 길이 u32·버전 u16·소비 후 offset u32·이름 원본입니다. 별도의 limit 인자는 사용하지 않으며 입력에 실린 이름 한도가 해당 선언의 경계입니다. 공개 JS API는 바꾸지 않습니다.

Debug 실제 WASM은 위 43개에서 버전 변경 정상 215건·잘림/한도/offset/이름 오류 688건을 통과했습니다. 오류 후 각 원본으로 복구를 확인합니다. 고정 44/46/54 위치는 해당 표본의 독립 기대값이지 제품 파서의 자동 위치 결정 규칙이 아닙니다. 차트 문자열이 없던 Contents 1개는 이 실험에서 해석하지 않았습니다.

ReleaseSafe/ReleaseFast 실제 WASM에서도 정상 215건·오류 688건을 각각 통과했습니다. 세 모드 모두 18바이트 반환값의 각 바이트를 개별 XOR 1 한 응답을 18/18 검출했습니다. UnexpectedEnd를 같은 메시지의 WebAssembly.RuntimeError로 바꾼 경우도 정상 거부로 세지 않고 assertion 실패했습니다.

별도 `/tmp/hwpjs-chart-declaration-mutants.SnZjKZ`의 소스 복사본에서 실패 시 원본 커서를 변경(atomic), 마지막 NUL 검사 제거(terminator), 버전을 8비트로 잘라냄(version)을 검사했습니다. 각각 세 모드 모두 실제 테스트 실패·종료 코드 1로 검출했습니다. atomic은 커서 1 대신 3, terminator는 기대한 InvalidChartTypeName 누락, version은 256 대신 0으로 실패했습니다. 절대 소스 경로를 사용했으며 제품 소스는 변형하지 않았습니다. 코어는 할당하지 않으므로 소유 버퍼 누수 시험을 별도로 만들어 수행한 것으로 주장하지 않습니다.

소스·테스트를 고정해 Debug → ReleaseSafe → ReleaseFast 전체 audit를 순차 실행했습니다. `/tmp/hwpjs-chart-declaration-{Debug,ReleaseSafe,ReleaseFast}-audit.log`에서 각 모드 27/27 단계·993/993 네이티브 테스트·HWP/WASM 7,843,764회 검사 통과와 종료 코드 0을 확인했습니다. 포맷·JS 구문·공백과 문서 로컬 링크 16개 검사도 통과했습니다. 타입 선언을 읽을 수 있다는 사실을 객체 데이터 경계·타입 테이블·전체 차트 파싱 완료로 대체하지 않습니다.

최종 `zig build test --summary all`은 5/5 단계·993/993 테스트, `zig build -Doptimize=ReleaseSafe --summary all`은 5/5 단계로 통과했습니다(종료 코드 0).
