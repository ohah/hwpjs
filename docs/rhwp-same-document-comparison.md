# 같은 문서·작업의 hwpjs/rhwp 비교

2026-11-09 macOS aarch64에서 `noori.hwp`·`noori.hwpx`로 읽기·그림 추출·치환·저장·재열기를 확인했습니다. 비교 본체는 공개 `@ohah/hwpjs@0.1.0`/Node.js 24.20.0과 rhwp release v0.9.0 네이티브 CLI입니다. 로컬 reference v0.8.7과 공개 rhwp v0.9.0이 같은 커밋이라고 가정하지 않습니다. hwpjs 0.1.1은 아래 거부 원인의 추가 재현에 사용했습니다.

## 동작 결과

| 작업                              | hwpjs              | rhwp             | 검증 범위                                         |
| --------------------------------- | ------------------ | ---------------- | ------------------------------------------------- |
| 두 원본 읽기                      | 성공               | 성공             | 주요 본문·비교표 값. 출력 모델과 주소 체계는 다름 |
| 그림 4개 원본 추출                | 성공               | 성공             | 각 형식 550,665바이트, 원본과 양쪽 SHA 일치       |
| 같은 문자열 치환·저장·자기 재열기 | 성공               | 성공             | 대상 문단 전체 비교                               |
| hwpjs 저장본 → rhwp               | 두 형식 성공       | 읽기 성공        | 치환 문단과 원본 그림 4개 보존                    |
| rhwp 저장본 → hwpjs               | HWP 거부·HWPX 성공 | 자기 재열기 성공 | 아래 컨테이너 필드와 읽기 정책 차이               |

치환은 `새로운 이름으로 “누리”`를 `새로운 이름으로 “누리실측”`로 정확히 한 번 바꿨습니다. hwpjs HWP 편집은 기본 정책에서 `LayoutReflowRequired`로 거부되어 `--allow-stale-layout` 동의 후 저장했습니다. 저장 성공은 원본과 같은 조판을 뜻하지 않습니다. 브라우저 입력·페이지 배치·글꼴·시각 정확도는 검증하지 않았습니다.

## CLI 시간 표본

새 프로세스 3회 실행의 중앙값(ms)입니다. 프로세스 시작·Node/WASM 준비·문서 처리·stdout 캡처·제품 파일 IO를 포함합니다. OS 캐시는 비우지 않았고 실행 시점·다른 프로세스 부하를 통제하지 않았습니다. 네이티브 실행 파일과 Node/WASM의 사용자 작업 시간이며 순수 파서나 언어 자체의 속도 비교가 아닙니다.

| 작업               | 형식 | hwpjs 0.1.0 | rhwp 0.9.0 |
| ------------------ | ---- | ----------: | ---------: |
| 본문 읽기          | HWP  |      74.016 |     14.235 |
| 본문 읽기          | HWPX |     111.079 |     13.144 |
| 치환·새 파일 저장  | HWP  |      76.403 |     13.484 |
| 치환·새 파일 저장  | HWPX |      91.789 |     14.549 |
| 저장본 본문 재열기 | HWP  |      74.564 |     14.124 |
| 저장본 본문 재열기 | HWPX |     112.742 |     13.529 |

이 표본에서는 rhwp CLI가 짧았습니다. info는 응답 의미가 다르고, 그림 추출은 rhwp가 Markdown도 저장하므로 같은 성능 분모의 표에 합치지 않습니다. CLI 수치를 브라우저 WASM 초기화·입력 성능으로 대입하지 않습니다.

## 같은 Node/WASM의 보조측정

같은 Node 24.20.0 프로세스에서 형식별 5회씩 순서를 교대해 10쌍을 실행했습니다. 이 추가 측정의 hwpjs는 0.1.1 동결 내부 소스와 기존 Native820의 조합입니다. 공개 0.1.0 SDK 또는 새 Native를 포함한 공개 0.1.1 패키지 전체의 벤치마크로 부르지 않습니다.

| open·본문 API 반환 | hwpjs first / warm 중앙값(ms) | rhwp first / warm 중앙값(ms) |
| ------------------ | ----------------------------: | ---------------------------: |
| HWP                |                20.106 / 7.414 |               53.634 / 6.523 |
| HWPX               |               73.299 / 57.782 |               15.986 / 4.827 |

first는 형식별 1회, warm은 후속 4회입니다. hwpjs는 매번 새 인스턴스·입력 복사·SHA·모델 수집을 포함하고 rhwp는 전역 WASM 인스턴스를 공유합니다. 출력 투영과 내부 작업량도 다릅니다. 파일 IO·초기 import·rhwp 전역 init·사후 검사는 표에서 제외했습니다. hwpjs engine import는 40.228ms, rhwp import는 2.659ms와 별도 init 27.451ms였고, hwpjs compile/instantiate는 각 open에 포함됩니다. 차감으로 순수 파서 시간을 추정하지 않습니다.

JSON·숫자 문자참조를 해제한 뒤 양쪽 20개 출력 모두 본문 19키를 확인했고 close/free도 모두 성공했습니다. 특히 HWPX 비용은 CLI 프로세스 시작만으로 설명할 수 없으며, 이 내부 경로의 open·본문 수집 비용도 후속 조사 대상입니다. 원자료와 원시 문자열 검사 실패의 구분은 `node-wasm/report.ko.md`에 기록했습니다.

WASM 단독 바이트도 확인했습니다. hwpjs 0.1.1은 6,974,903바이트, rhwp 0.9.0은 26,835,482바이트입니다. hwpjs가 약 74% 작지만 지원·내장 기능 범위가 달라 동등한 엔진의 순수 최적화 효과라고 해석하지 않습니다.

## HWP 교차 거부의 원인

rhwp 저장본 세 개는 CFB 루트 Creation Time에 `133523092201799680`을 기록했고 원본은 0이었습니다. [MS-CFB §2.6.2](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-cfb/026fde6e-143d-41bf-a7da-c08b2130d50e)는 루트 생성 시각 필드를 모두 0으로 쓰도록 요구합니다. 해당 출력은 명세 요구와 다릅니다.

offset 612–619의 8바이트만 0으로 만든 사본은 hwpjs 0.1.0과 0.1.1에서 읽혔습니다. 필드 밖 바이트와 payload stream 13개의 경로·길이·SHA는 같았습니다. 메인도 최종 0.1.1 설치본으로 원저장본 거부와 필드 수정 사본의 읽기 성공을 독립 재현했습니다.

rhwp의 해당 저장 필드 문제와 hwpjs가 읽기에서도 CFB 보정을 거부하는 정책은 별개입니다. 본문 손상으로 단정하지 않습니다. hwpjs는 이 필드를 검사하지만 사용자 관점의 읽기 호환성은 더 보수적입니다. 이 사례 하나로 제품 전체의 저장 정확도나 파서 완성도 우위를 판단하지 않습니다.

## 재현 증거

원자료는 `zig-out/verification/rhwp-same-work-r1/`에 보존합니다. `hwpjs/report.ko.md`와 `rhwp/report.ko.md`는 명령·반복별 시간·실패와 성공 코호트를 구분합니다. `rhwp/published-provenance.json`은 배포 SHA와 버전을, `rhwp/cfb-root-created-experiment/`는 단일 필드 실험을, `main-independent-control.json`은 메인의 독립 재현을 기록합니다. 초기 환경·경로·검사 스크립트 오류를 제품 실패나 정상 성능 표본에 포함하지 않았습니다.

## 최신 로컬 후보의 Node/WASM 재측정

2026-11-09 로컬 `77d9e0ccd` 변경을 포함한 격리 소스와 최종 Native `38c4dd02eafacefb89318b46c001f787716c997cf15f660e66d44a92b08aecc0`를 같은 rhwp 0.9.0 고정 Node/WASM 패키지와 비교했습니다. 공개 npm 배포본이나 rhwp 최신 릴리스 전체의 측정이라고 부르지 않습니다.

같은 Node 24.20.0 프로세스에서 Noori HWP/HWPX를 7라운드씩 처리했습니다. 라운드마다 양쪽 순서를 교대했고 각 구현·형식 first 1회와 후속 6회를 구분했습니다. 총 28개 문서의 open/close가 성공했고 JSON·유니코드 숫자 참조를 해제한 출력에서 주요 본문 19항목을 모두 확인했습니다. 출력 전체 동치나 조판·개체 보존 검사는 아닙니다. 소스·입력·양쪽 WASM의 전후 pin이 같았습니다.

| open·본문 API 반환 | hwpjs first / warm 중앙값(ms) | rhwp first / warm 중앙값(ms) |
| --- | ---: | ---: |
| HWP | 20.473 / 4.809 | 52.791 / 6.282 |
| HWPX | 44.160 / 27.190 | 16.468 / 5.025 |

이번 표본에서 HWP는 hwpjs가 짧았고 HWPX는 여전히 약 5.4배 길었습니다. hwpjs는 입력/WASM 복사·입력 SHA·새 Instance·현재 모델 수집·text 렌더를 포함하며 컴파일된 Module은 프로세스 안에서 재사용합니다. rhwp는 전역 WASM Instance를 재사용하고 `HwpDocument`/`getTextFileText`를 호출합니다. 양쪽 출력 구조와 내부 작업량은 다르므로 순수 파서·언어·모든 문서의 성능 순위로 일반화하지 않습니다.

초기 import와 rhwp 전역 init은 표에서 제외했습니다. hwpjs engine import 37.779ms, rhwp import 2.660ms와 별도 init 27.416ms를 따로 기록했습니다. CLI 새 프로세스 전체 시간이나 브라우저 첫 화면 시간과도 구분합니다. 이번 재측정은 최근 문단/열기/Module 재사용 변경을 합친 최신 후보의 현재 상태이며, [웹 헤더 재사용](web-hwpx-open-performance.md) 한 변경만의 개선량으로 해석하지 않습니다.

원자료는 `zig-out/verification/rhwp-latest-read-r1/`의 `run.mjs`, `pins.json`, `result.json`, `stdout.jsonl`, `text/`에 있습니다. 문자열 디코딩·내용 확인은 open·본문 타이머 종료 후 수행했고 검사용 Native export 래퍼는 사용하지 않았습니다. 실제 compile/instantiate 호출 시간만 관찰했습니다. 미기록 예열이나 source/WASM 교체는 없었습니다. npm 게시·main 푸시·데모 배포는 수행하지 않았습니다.

후속 XML·표 조회 최적화의 최종 WASM965d67 후보는 같은 방식의 Noori HWPX open+본문 반환 중앙값을 기준27.13ms에서22.68ms로 줄였습니다(구현별 후속12회). 같은 집단의 rhwp0.9.0은 약4.95ms로 여전히 약4.6배 차이가 있습니다. 표 누락이 있던 초기 후보는 제외했습니다. 성능·저장 동치와 실제 브라우저의 별도 분모는 [후속 읽기 비용 검증](hwpx-read-cost.md#최종-실측)을 따릅니다.
