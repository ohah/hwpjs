# Canvas 제어 표시와 원문 위치 연결

기존 탭과 확장 anchor(제어 코드 2·11), 자동 번호(18), 같은 문단 하이퍼링크를 포함한 문단의 직접 입력을 연결합니다. native의 [제어 보존 계약](hwp5-control-text-edit.md)을 변경하지 않으며 새 제어 생성·삭제·원본 개체/탭 조판은 아직 지원하지 않습니다.

## 책임과 SSOT

`text-offsets.mjs`는 native 미리보기 토큰의 시작 위치와 raw 길이만 소비합니다. 부가 데이터를 해석하거나 제어 폭 표를 복제하지 않습니다. 탭은 textarea의 1 UTF-16 단위, 확장 anchor와 자동 번호는 U+FFFC 보호 표식으로 표시하고 뒤 경계에는 원문 위치를 기록합니다. 하이퍼링크 시작/끝의 보호 표식은 아래 계약을 따릅니다. 보호 표식은 실제 표·이미지·도형 렌더링이 아닙니다. 일반 텍스트는 같은 길이를 유지하며 끝 PARA_BREAK는 표시하지 않습니다. 토큰 시작·종결·전체 길이가 맞지 않거나 지원 대상 밖의 제어가 섞이면 편집 후보를 만들지 않습니다. 표시 후보 판정은 제어 ID의 유효성을 보증하지 않으며 native가 최종 연결을 검증합니다.

`content.mjs`는 표시 문자열과 파생 `sourceOffsets`를 반환합니다. 표시가 잘렸으면 문단 입력을 비활성화하고 위치 대응표도 제공하지 않습니다. 이 대응표는 저장 모델이나 원문 캐시가 아닙니다.

`canvas-editor.mjs`는 textarea의 표시 좌표로 caret·선택·임시 입력을 유지합니다. 명령 직전에만 확정 표시 대응표로 splice 시작/끝을 원문 위치로 변환합니다. 진행 중 입력을 한 번에 하나씩 native에 보내고 다음 명령은 응답에서 갱신된 대응표를 사용합니다. 실패 복원은 표시 좌표를 사용합니다. 제어 삭제를 native에서 거부하며 JS에서 저장 의미를 재구현하지 않습니다.

`layout.mjs`의 `displayRunText`가 탭의 실험용 4칸 표시를 소유합니다. 동일 변환으로 폭을 측정하고 `renderer.mjs`가 그립니다. HWP 탭 정의의 위치·정렬·채움선 재현은 아닙니다. 탭을 포함한 clipboard 전체 교체 등 제어를 건드리는 명령은 거부될 수 있습니다.

## 2026-10-01 검증

실제 software 문단 33의 제품 WASM 연결 테스트에서 표시 범위 `[1,3)`이 원문 `[8,10)`으로 변환되는 것을 확인했습니다. 대기 입력이 첫 응답 뒤 갱신된 원문 위치 11로 전송되고, 탭의 16바이트 부가 정보가 보존됐습니다. 탭 표시 삭제는 `UnsupportedControlDeletion`으로 거부되고 확정 문자열과 원문이 복원됩니다.

순수 검사는 여러 탭·이모지 코드 단위·모든 표시 경계·불완전 토큰·잘린 표시의 대응표 제외·폭 측정 일치·원본 projection 불변성을 검사합니다. 최초 복사본 비교의 Buffer/Uint8Array 타입 차이를 실제 제품과 같은 Uint8Array로 수정했습니다. Canvas·projection·Worker 집중 Node 20개와 Debug·ReleaseSafe·ReleaseFast 제품 편집 검사 각 47개가 통과했습니다.

agent-browser로 공개 Chromium 화면의 실제 software 문단 33을 탭 뒤 좌표로 클릭했습니다. 표시 caret `0:33:1`, `한😀` 입력과 native 확정 대체 텍스트, Backspace 이모지 삭제, Home/Delete 탭 삭제 거부 및 복원, End 후 `끝` 입력을 확인했습니다. 오류 목록은 비어 있었고 `/private/tmp/hwpjs-software-tab-input.png`에서 caret와 텍스트를 확인했습니다. 실제 OS IME 후보창·모바일·Safari/Firefox·원본 조판 검증이 아닙니다.

후속 확장에서는 실제 software 문단 44의 도형 anchor 뒤 삽입과 대기 입력을 제품 WASM으로 확인했습니다. 첫 표시 위치 1을 원문 위치 8로 변환하고 anchor 원문 16바이트를 유지합니다. 보호 표식 삭제는 native가 거부하고 확정 표시와 원문을 복원합니다. 순수 검사는 anchor·탭 혼합 위치, 필드 후보 제외와 잘린 표시를 확인했습니다. Canvas 집중 20개 및 ReleaseSafe 제품 편집 53개가 통과했습니다. 기존 일반 텍스트 검사에서 새로 편집 가능해진 root anchor 문단을 자동 선택해 실패한 것은 검사 대상 선택 변경이며, 일반 텍스트 경로를 명시적으로 선택하고 anchor 경로는 별도 실파일 검사로 유지했습니다. 새 anchor 연결의 실제 브라우저 검증은 아직 수행하지 않았습니다.

하이퍼링크 시작/끝은 각각 `«`·`»`로 표시합니다. 원문을 바꾸는 문자나 최종 필드 렌더링이 아니라 보호된 표시 위치입니다. 0폭으로 지워 하나의 표시 위치에 서로 다른 원문 경계를 겹치지 않습니다. 부가 payload/URL을 JS에서 해석하지 않고 native가 필드 종류·짝·연결을 최종 판정합니다. 기존 후보 제외 설명의 ‘필드’는 이 확장 이전 기록이며, 현재 다른 미지원 제어가 섞이면 계속 제외합니다.

실제 software 문단 93에서 label 전체 교체·대기 입력·끝 표식 삭제 거부를 제품 WASM으로 검사했습니다. `[1,8)` 표시 범위가 `[8,15)` 원문 범위로 변환되고 시작/끝 표식 원문과 필드 수정 속성을 포함한 전체 Section 및 비대상 스트림을 독립 oracle로 대조합니다. 당시 순수/Canvas 집중 검사는 22개였고, 실제 브라우저 검증 전 단계였습니다. 후속 실측은 다음 문단과 구분하며 OS IME는 계속 미검증입니다.

외부 공개 Chromium 화면에서 실제 software 문단 93의 라벨 앞을 마우스로 클릭하고 `한😀`를 입력했습니다. caret `0:93:4`, 확정 표시 `«한😀mozuAPI»`, Worker 재투영 대체 텍스트와 변경 적용 상태를 확인했습니다. End/Backspace로 끝 보호 표식 삭제를 시도하면 `UnsupportedControlDeletion`으로 거부하고 같은 확정 표시로 복원됩니다. 증거 화면은 `/private/tmp/hwpjs-software-field-input.png`입니다. 이는 실제 OS 한글 입력기·다른 브라우저·한컴 렌더링 검증은 아닙니다. 최신 ReleaseSafe 제품 편집 검사는 54개가 통과했습니다.

위 검사 수치는 각 연결 단계의 이력입니다. 캡션·바탕쪽·손상 소유 관계 반례까지 추가한 최신 ReleaseSafe 제품 편집 검사는 63개가 통과했습니다. 캡션·바탕쪽의 실제 브라우저 입력은 이 결과로 검증됐다고 보지 않습니다.

실행 명령은 [개발 명령](development-commands.md)이 소유합니다. 개체/필드 렌더링·문단 간 필드·전체 문서 범위 편집은 남아 있습니다.
