# ICC 기호적 출력과 유리수 후보의 거리 비교

## 계약과 수학적 경계

`power_ordinate_distance.compare(precision,value,r,target)`는 `|value-target|`와 `|r-target|`를 비교합니다. r은 정규화 u256 분수, target은 정규화 u128 분수이며 결과는 lt/eq/gt 또는 정밀도 부족 null입니다. 동률을 한 후보의 승리로 바꾸거나 실제 출력의 도달 여부를 결정하지 않습니다. value가 유리수이면 기존 ordinate_distance의 정확한 교차곱을 재사용합니다.

value가 거듭제곱 식이면 r과 `2*target-r`를 양 끝으로 하는 닫힌 구간을 구성합니다. value가 그 내부이면 더 가깝고, 경계이면 동률이며, 밖이면 더 멉니다. 이 구간은 [0,1]로 클리핑하지 않습니다. 반사값이 음수 또는 1보다 클 수 있기 때문입니다. `ordinate_distance_band`가 이 계산을 소유하며 입력 유효성을 먼저 검사합니다.

공통 분모는 `target.d*r.d`로 u384에 들어갑니다. 두 분자는 `r.n*target.d`와 `2*target.n*r.d-r.n*target.d`이며 i386으로 보존합니다. 분모는 양수입니다. 거듭제곱 offset을 차감할 때는 signed 417비트·unsigned 400비트로 충분하므로 i512/u512에서 계산합니다. 범위를 줄이기 위한 근삿값·비트 잘림은 사용하지 않습니다.

## SSOT와 확장

`power_ordinate_rational_order.Of(128/384)`가 signed 임계 분수에서 offset을 빼는 규칙을 소유합니다. 기존 정규화 출력 순서 비교도 이 모듈을 재사용합니다. 작업 정수 폭은 각각 256/512비트이며 비교 정밀도 128/256/512/1024와 다릅니다. signed 입력 분자 폭은 분모 폭+2, offset 적용 뒤에는 분모 폭+33비트가 상한입니다.

integer_power·rational_power_equality·rational_power_order의 공통 Of에 512비트를 추가했습니다. 기존 128/256 진입점은 유지합니다. positive_bounds의 fraction/fractionWide는 하나의 ratio 생성기를 사용합니다. 낮은 정밀도와 큰 입력 비율에서 분모를 이동시키는 기존 방향성 반올림을 그대로 재사용하며 초기 정수 폭은 precision+입력 폭입니다. 정확한 동등성은 공통 완전근/거듭제곱 검사로 판정하고, 방향성 경계가 겹치면 null입니다.

power 표현을 직접 구성해서 넣으면 원래 식을 비교합니다. 실제 (0,1) 출력임을 증명하거나 클리핑하지 않습니다. 실수 정의역·분모 검증은 공통 비교기가 수행합니다. 이 기능은 두 개의 서로 다른 기호적 거듭제곱 식 사이 거리를 비교하는 API가 아닙니다.

## 검증 진행

신규 네이티브 4개와 기존 출력 비교 테스트 4개가 통과했습니다. 범위 밖 반사값·384비트 분모, 512비트 완전제곱/최소 signed 값·큰/작은 비율의 방향성 경계, 동률·양쪽 거리 순서, 극단 offset을 검사합니다. sqrt(1/2), r=0, target=11749380235262596085/33232265756373499214는 128에서 null, 512에서 lt입니다. 목표 반사값을 끼고 발생하는 실제 정밀도 반례입니다.

테스트 mode210 입력은 기존 mode208의 104바이트 값·목표·정밀도 형식 뒤 r의 n/d u256 BE 64바이트를 붙인 168바이트입니다. 공통 icc-ordinate-input이 값·목표·정밀도 필드를 읽고 두 probe가 재사용합니다. 출력 i32 LE -1/0/+1/2는 lt/eq/gt/미확정입니다. 길이·패딩·태그·정밀도·분수 유효성과 오류 뒤 복구를 검사합니다.

독립 JS oracle은 작은 정수 지수의 값을 BigInt 분수로 직접 계산한 뒤 두 절댓값 거리를 교차곱합니다. 제품의 반사 구간 방식이나 방향성 경계 알고리즘을 복제하지 않습니다. 큰 정규화 분수와 네 정밀도의 극단 offset도 포함합니다. 직접 Debug WASM 실행은 comparisons=5390/rejected=900/undecided=1, 총 6,291건이 통과했습니다. 기존 출력 순서 비교 1,825건도 동일하게 통과했습니다.

거리 순서 반전·동률을 lt로 변경·미확정을 동률로 변경하는 변형을 각각 ERR_ASSERTION으로 검출했습니다. 제품에는 변형을 남기지 않았습니다. 전체 세 모드 audit 결과는 아래 최종 확인 절을 기준으로 합니다.

별도 `/tmp` 소스 복사본에서 반사식의 계수 2를 제거했습니다. Debug·ReleaseSafe·ReleaseFast 모두 4개 중 3개가 실패하여 넓은 반사 구간, 동률, 실제 정밀도 반례가 이 수식 오류를 검출했습니다. 원본에는 변형을 적용하지 않았습니다.

## 실제 프로파일 연결

DCI(P3) RGB·Display P3·ITU-2020·ITU-709·ROMM RGB의 RGB TRC 15개를 읽기 전용으로 조사했습니다. 원본 양의 지수, type3의 양의 기울기·내부 시작점·a+b=65536·시작 밑 (0,1)을 확인해 type0 하한=0, type3 하한∈(0,1), 모든 상한=1이라는 기대를 먼저 정했습니다. mode205의 두 출력 끝점을 그대로 mode210에 전달하고 `(r,target)=(0,0),(1,1),(0,1),(1,0)`에 대한 거리 순서를 확인했습니다. 120건 모두 일치했습니다. 수동 확인으로 정규 audit 호출 수에는 합산하지 않으며, 중간 목표 전체·OS 색변환·HWP 렌더링 대조를 의미하지 않습니다.

## 최종 확인

Debug·ReleaseSafe·ReleaseFast 전체 audit가 각각 종료 코드 0, 20/20 단계, 네이티브 589/589, WASM checks=6,593,960로 통과했습니다. 신규 6,291건이 이전 6,587,669건에 추가됐습니다. 신규 결과는 세 모드 모두 comparisons=5390/rejected=900/undecided=1입니다. 로그는 `/tmp/hwpjs-icc-ordinate-distance-{Debug,ReleaseSafe,ReleaseFast}.log`입니다.

ReleaseSafe·ReleaseFast의 실제 감사 산출물 직접 실행에서도 같은 신규 수치를 확인하고 동률을 lt로 바꾸는 변형을 각각 ERR_ASSERTION으로 검출했습니다. 변경 Zig 포맷·JS 문법·diff 공백과 관련 문서 로컬 링크 8개도 확인했습니다.

최종 재검토에서는 반사 구간의 비클리핑·분모 양수·양 끝 순서, 끝점 동등성과 거리 동률의 관계, 확정된 외부 비교에 의한 조기 반환, 미확정 유지, 기존 128/256 연산의 공통 구현 보존, 512비트 비율 초기화의 이동 방향·반올림, 공통 offset 적용과 입력 wire 책임 분리를 확인했습니다. 최대 입력의 BigInt 계산에서도 분모 384비트·반사 분자 signed 386비트·offset 적용 분자 signed 417비트·분모 400비트를 확인했습니다. 이번 범위에서 추가 결함은 발견하지 않았습니다.

## 남은 범위

이 비교 결과와 선형·거듭제곱 분기 후보를 결합하여 최근접 출력의 존재·동률·열린 경계의 미도달을 결정하는 작업이 남아 있습니다. F.1(a) 역변환 입력 선택 연결과 전체 HWP/HWPX 문서 검증도 미완료입니다.
