# HWP5 원본 표 격자 후보

현재 줄·칸 편집은 [알려진 단순 캡션의 원시 보존](source-table-grid-live-edit.md#알려진-단순-캡션의-보존-입장)을 허용합니다. 캡션 속성 setter 확장이 아니며 field/자동번호·cache·중첩·unknown extension은 계속 거부합니다. 아래 초기 캡션 전체 거부 기록은 이 좁은 보존 입장으로 대체됩니다.

현재 줄·칸 삽입/삭제는 [live 편집의 지원 경계](source-table-grid-live-edit.md#지원-경계)를 따릅니다. 명시된 단일 span 또는 정확한 원본 구간 합으로 모든 경계를 결정할 수 있는 병합 격자와 보호되지 않은 중첩 leaf 대상까지 확장했습니다. 아래 초기 비병합/최상위 제한과 당시 검증 기록은 이전 단계의 이력이며, 필드·개체·부모 크기 자동 조정까지 지원한다는 뜻은 아닙니다. 기존 merge/split 명령의 선택 권한과 지원 경계는 확장하지 않습니다.

`src/hwp5/edit/source_table_grid.zig`는 명시된 원본 Section의 TABLE 레코드와 예상 행·열 수를 받아 새 구역 바이트만 반환하는 private 후보입니다. 세션·이력·WASM 연결은 [live 편집 계약](source-table-grid-live-edit.md)을 따릅니다. 파일 컨테이너 저장은 아래 어댑터에서 별도로 검증합니다. 생성 표의 웹 명령 지원과 구분합니다.

공식 HWP5 revision1.2의 표75/79/80과 기존 프로젝트 framing/tree/list-group 모듈을 사용합니다. ListHeader는 spec6/observed8을 호출자가 명시하며 길이나 버전으로 추측하지 않습니다. 전체 문서의 새 문단 ID 발급은 호출자 책임이고 후보는 현재 구역 내 충돌·중복·0값을 추가 거부합니다. 현재 레코드 번호와 예상 크기는 내용 지문이나 영구 identity가 아닙니다.

현재 지원 후보는 최상위 본문의 절대 크기·간격0인 직사각형 표입니다. 주소는 행 우선 완전 격자이며 span은1×1이어야 합니다. 각 열 폭·행 높이는 해당 축에서 일정한 양수이고 합계는 표 공통 크기와 같아야 합니다. 셀은 하나 이상의 일반 직접 문단을 허용하며, 각 문단에는 plain UTF16 본문과 글자 모양 leaf 레코드만 허용합니다. 모든 직접 문단의 헤더·본문 길이·문자 경계·글자 모양 수와 위치를 검사하므로 삭제될 셀이나 뒤쪽 문단의 미지원 구조도 거부합니다. 줄 캐시·변경추적 병합 문단·필드·캡션·중첩 표·미해석 셀/표 확장·유효 구역은 거부합니다. 각주/도형 안 소유자 등 다른 문맥도 현재 거부합니다.

원본 표 정책은 생존 셀의 폭·높이·본문·서식을 유지하는 것입니다. 삽입은 앞선 행/열(처음 위치에서는 첫 행/열)의 크기와 기본 문단/글자 모양을 사용해 빈 셀을 만들고 합계 크기를 늘립니다. 삭제는 제거한 축 크기만큼 합계를 줄입니다. 생존 셀의 모든 문단은 헤더·본문·글자 모양·ID·순서를 원시 바이트로 보존합니다. 삽입 셀의 한 빈 문단·셀당 새 ID 하나 정책은 [셀 문단 공통 계약](source-table-grid-cell-paragraphs.md)을 따릅니다. 이 정책은 생성 표의 고정 총 폭 재분배와 구분하며, 한컴 UI가 요구하는 공식 삽입 정책이라는 주장은 아닙니다.

준비 중 원본을 수정하지 않으며 실패/OOM 시 후보와 arena를 해제합니다. 비대상 앞뒤 레코드는 원시 바이트로 보존하고 결과를 tree/list-group으로 다시 검사한 뒤 반환합니다. 원본 줄/페이지 조판 캐시 갱신, HWP5 파일 저장의 reflow 동의와 문서 전체 ID 선택은 향후 상위 거래가 소유해야 합니다.

집중 검사는 두 명시 ListHeader 형식에서 네 action의 앞/중간/끝 매핑·생존 본문/서식·비대상 원문, ID/대상/크기·위험 구조 거부와 OOM 원자성을 검사합니다. OOM은 공통 `src/testing/allocation_failures.zig`를 사용해 일반 resize 성공 경로와 resize를 거부한 결정적 allocate/copy 실패 경로를 구분합니다. std Arena의 기회적 backing resize 때문에 단순 주입 실행 수가 달라지는 초기 실패 기록을 보존합니다. 이는 원본 변경이나 누수의 재현이라는 뜻은 아닙니다.

실행 명령은 [개발·검증 명령](development-commands.md), 공통 좌표 매핑과 공개 생성 표의 범위는 [격자 계약](created-table-grid-edit.md)을 따릅니다. 타 구현 소스/역분석 결과를 새로 열람하지 않았으며 엄격한 클린룸 인증을 주장하지 않습니다.

## 파일 단위 후보

`src/hwp5/edit/source_table_grid_file.zig`의 `transform`은 DocInfo와 모든 구역의 문단 ID를 한 번 색인하고 새 ID를 발급한 뒤 대상 구역만 교체한 새 CFB를 반환합니다. 명시된 spec6/observed8 정책을 유지하며 보정이 필요한 CFB와 변경 이력·서명 문서는 거부합니다. 비대상 스트림 바이트와 디렉터리 메타데이터를 검사합니다. 컨테이너 내부 섹터 배치까지 동일하다는 의미는 아닙니다.

삽입 후 해제 바이트·레코드 총량이 입력보다 커질 때 한도를 우회하는 반례를 재현했습니다. 출력 준비 전 비대상 예산을 예약하고, 후보 합계와 엄격한 재개방 뒤 합계를 다시 검사하도록 수정했습니다. 입력 932바이트·43레코드가 행 삽입 후 1,102바이트·51레코드로 늘어나는 경우의 거부와 정확한 한도 수용을 함께 확인했습니다.

ReleaseSafe 집중 검사 11개는 합성 compressed/raw 입력, 네 명령, OOM·원본 불변성, 예산 증가·경계, 메타데이터 변조 거부와 기존 브라우저가 저장한 단순 표의 재열기를 포함합니다. 실제 브라우저에서 원본 표를 편집한 증거는 아니며 공개 SDK·CLI 연결과 복합 표 지원은 남아 있습니다. 실행과 필수 픽스처 환경변수는 [개발 명령](development-commands.md)의 파일 단위 표 격자 후보를 따릅니다.

## 보호 셀 편집 거부

공식 HWP5 revision1.2의 표65/79/80은 ListHeader 공통 속성과 셀 필드를 구분하지만 보호 bit17은 명시하지 않습니다. 이 해석은 기존 `body/cell_attributes.zig`의 `Attributes.fromList(view).isProtected()` 계약을 재사용합니다. 새 공식 명세 필드를 발견했다는 의미는 아닙니다.

spec6·observed8의 보호 셀을 포함한 행0·열0 삭제가 수정 전 실제로 허용되는 반례를 재현했습니다. 이제 대상 표의 어느 셀이든 보호 상태면 `UnsupportedSourceTableGrid`로 전체 편집을 거부합니다. 다른 속성과 원본 바이트는 유지합니다. 두 레이아웃의 앞·뒤 보호 셀과 네 명령 40개 거부 조합, 보호 외 속성 보존, 기존 네 편집과 OOM 검사를 포함한 집중 검사 6개가 통과했습니다. 수정 전 실패와 수정 후 근거는 `zig-out/verification/document-transforms-connect-r1/task-t-baseline-1794272234942317000/`에 보존합니다. 이는 primitive 검사이며 파일·공개 API 검증과 구분합니다.

## 일반 셀의 다중 문단

문단 검사는 각 그룹의 직접 문단과 leaf 자식을 한 번씩 진행합니다. 격자 조립은 셀 인덱스를 재사용하고 새 ID 충돌은 기존 Map으로 검사합니다. 파일·live 어댑터가 호출하는 `prepare`의 계약 확장이며 별도 세션·이력 스택을 추가하지 않습니다.

공식 revision1.3 표58·65의 확인, count 상위 비트의 독립 관측 및 삽입 템플릿 정책의 단일 출처는 [셀 문단 공통 계약](source-table-grid-cell-paragraphs.md)입니다. 로컬 정리본의 구현체 보정 주석은 이번 변경의 근거로 사용하지 않습니다. HWP5는 기존 `Header.writeTextCounts`와 `paragraph_list_count.Count.encode`를 사용합니다. source-grid의 지원 자격에서만 `ListHeader.signedCount() <= 0`을 거부하며, 공용 파서의 unsigned 원값 보존은 변경하지 않습니다. 직접 문단 수와 선언값의 일치는 별도로 기존 Groups가 검사합니다.

새 합성 진입점의 실행은 [개발 명령](development-commands.md)의 원본 표 셀 여러 문단 절을 따릅니다. spec6/observed8의 3×3 입력에서 네 명령의 처음·중간·끝, 2/3문단 생존 원문, 첫 서식/마지막 count 비트 승계, count 1과 셀당 새 ID 하나를 검사합니다. 관측형·역형·전부0·전부1 비트를 별도 대조합니다. 후속 문단의 손상·컨트롤·중첩·캐시·보호 셀 거부와 성공/거부의 전체 할당 실패 주입을 포함합니다. 증거는 소스 트리 밖 `zig-out/verification/source-grid-multipara-r1/`에 둡니다. 이 검증은 primitive 범위이며 파일/live 통합이나 전체 엔진 완료의 증거로 확대하지 않습니다.

통제 소스의 ReleaseSafe 실행에서 신규 집중 검사 4/4과 기존 단일 문단·보호 셀 회귀 6/6이 통과했습니다. 신규 양성 대조는 레이아웃2×비트패턴4×명령4×위치3의 96조합이며, 후속 문단/보호·리스트 손상 거부는 96조합입니다. 할당 실패는 관측형 비트의 성공24·거부96 각각에 공통 helper의 정상 resize 성공 대조와 resize 거부 후 모든 fallback 할당 실패 주입을 수행했습니다. `red.log`는 기존 primitive의 다중 문단 거부, `green.log`와 `regression.log`는 변경 후 결과입니다. main의 `noori-count-bits.json`은 count 상위 비트의 별도 독립 원본 관측이며 이 합성 테스트가 원본 파일 변환을 실행한 것은 아닙니다.

INT16 음수 영역 감사에서는 선언 `0x8000`과 실제 직접 문단 32,768개가 일치하는 합성 셀을 만들고 기존 Groups의 일치 검사가 통과함을 먼저 확인했습니다. 이전 수용 경로를 `signed-red-compact.log`로 보존했고, source-grid 자격 검사 후 두 레이아웃·네 명령에서 거부합니다. 최초 `signed-red.log`의 누수 진단은 예상 밖 성공 바이트를 `expectError`가 해제하지 않은 테스트 자체의 실패 정리 문제였습니다. 테스트를 명시적 해제 분기로 고친 compact red에는 해당 누수가 없으며, 제품 실패 정리의 누수로 해석하지 않습니다.

### 문자 수 0인 빈 원본 문단

main이 확인한 공식 revision1.3 PDF p38의 text_count 0/PARA_BREAK 규칙을 바탕으로 source-grid 내부 검증만 확장합니다. 문자 수가 0이고 PARA_TEXT가 없거나 payload가 0바이트인 문단은 글자 모양 선언·실제 개수가 모두 1이고 첫 run 위치가 0일 때만 알려진 빈 문단으로 허용합니다. 원본에 없는 문자를 경계 검사에 추가하지 않으므로 run 위치 1도 거부합니다. 생존 문단은 TEXT 부재와 빈 payload의 차이까지 원시 보존합니다. 첫 템플릿이 이 빈 문단인 삽입 셀도 기존 한 빈 문단 생성 경로와 첫 글자 모양을 재사용합니다. 삽입 정책 자체는 [공통 계약](source-table-grid-cell-paragraphs.md)을 따릅니다.

문자 수가 양수인 문단의 PARA_TEXT 부재·빈 payload는 계속 거부합니다. 상위 본문 파서의 관측 빈 문단 정책이나 문서 전체 Native parser의 지원 범위를 변경하지 않습니다. 기존 집중 검사 4개를 유지하고 빈 문단 양성·음성/OOM 검사 2개를 추가했습니다. 두 레이아웃·TEXT 표현2·첫/중간/끝 빈 문단·네 명령·편집 위치3의 144양성 조합과 양수 선언/잘못된 글자 모양48거부 조합을 독립 원시 레코드 oracle 및 전체 할당 실패 주입으로 검사합니다. 변경 전 재현은 `empty-red.log`, 변경 후 결과는 `empty-final-green.log`와 `empty-final-regression.log`에 둡니다.
