# 변경 추적 병합 문단과 줄 캐시 조사

[ViewText 계약·남은 작업](hwp5-track-change-viewtext.md)

조사로 확인한 `0x11` 제외 동작은 [명시적 Zig 바이트 변환 API](hwp5-revision-projection.md)로 분리했습니다. 이 문서는 대조 근거를, 연결된 문서는 코어 계약을 소유합니다. 관측 병합 소유권과 문단 내부 좌표는 별도 코어 API로 구현했으며 기본 ViewText 의미 검사·줄 캐시 좌표 해석은 아직 후속 범위입니다.

## 확인한 사실

명세 표 58은 문단 헤더의 마지막 UINT16을 5.0.3.2 이상에서의 변경추적 병합 문단여부로 정의합니다. 표 62는 줄 레코드를 출력 cache로 설명합니다. 병합된 텍스트의 위치 계산법, 문단 종료 문자 차감 여부, 리스트·구역 경계 동작은 이 두 표에 설명되어 있지 않습니다.

실제 `reference/rhwp/samples/issue5169_viewtext_changetracking.hwp`에서 ViewText 줄 시작 초과 9건은 5개 루트 문단에 집중됩니다. 이 5개 문단의 선언 길이는 실제 PARA_TEXT의 UTF-16 길이와 일치합니다. 뒤에 연속해서 오는 병합 값 1의 루트 문단에는 줄 레코드가 없으며, 길이를 합하면 기존 9개 초과 위치가 모두 합산 길이 안에 들어옵니다.

| 선두 문단 레코드 | 줄 시작 위치 | 문단별 선언 길이(선두 → 병합 후속) | 합 |
|---|---|---|---:|
| 35 | 0, 97, 119 | 15, 14, 22, 71 | 122 |
| 116 | 0, 183, 226 | 3, 132, 123 | 258 |
| 133 | 0, 52, 92 | 4, 106 | 110 |
| 147 | 0, 49, 92 | 11, 1, 110, 1 | 123 |
| 167 | 0, 46, 84 | 64, 35 | 99 |

선두의 병합 값은 모두 0입니다. 길이 1인 후속 문단에는 PARA_TEXT가 없는 사례가 있으므로 실제 텍스트 바이트의 단순 합과 선언 길이 합을 같은 값으로 취급하지 않습니다. BodyText는 개별 문단 길이를 넘는 줄 시작이 0건입니다.

이는 **병합된 문단 묶음 기준의 캐시라는 가설을 지지**하지만 정확한 좌표 변환을 증명하지는 않습니다. 특히 여러 가능한 종료 문자 차감 규칙이 모두 현재 줄 시작을 포함할 수 있습니다. 이 결과만으로 기존 문단 검사의 길이를 합산 값으로 바꾸거나 전체 ViewText 의미 검증을 완료 처리하지 않습니다.

## 종료 문자와 최종 본문 대조

같은 파일의 BodyText 전체 문단과 두 가지 UTF-16 바이트 후보를 비교했습니다. 첫 후보는 실제 PARA_TEXT를 그대로 이어 붙이고, 둘째는 마지막 멤버를 제외한 각 멤버 끝의 CR 한 개만 제거합니다. 텍스트가 없는 문단에 문자를 생성하지 않습니다.

| ViewText 선두 | 원문 연결 길이 | 중간 CR 제거 길이 | CR 제거 후 일치한 BodyText 문단 |
|---|---:|---:|---|
| 35 | 122 | 119 | 없음 |
| 116 | 258 | 256 | 없음 |
| 133 | 110 | 109 | 73 |
| 147 | 121 | 119 | 없음 |
| 167 | 99 | 98 | 85 |

원문 연결 후보는 5개 모두 BodyText 문단과 일치하지 않았습니다. 선두의 PARA_LINE_SEG 전체 바이트도 BodyText 어느 문단과도 일치하지 않았습니다. 단, 추가 조사에서 BodyText 루트 문단의 줄 레코드가 전부 부재함을 확인했으므로 이를 대응 줄 위치의 값 불일치로 해석하면 안 됩니다([좌표 가설과 캐시 부재 실측](hwp5-line-cache-coordinates.md)). 두 텍스트 일치는 최종 본문 변환의 증거이지 줄 좌표 변환의 증거가 아닙니다. 선두 35의 마지막 줄 시작 119는 CR 제거 후보의 전체 길이 119와 같아, 그 위치에서 실제 문자를 가리킨다고 가정할 수도 없습니다. 선두 147은 텍스트 없는 두 멤버 때문에 선언 합 123과 원문 연결 길이 121부터 다릅니다.

따라서 모든 문단의 CR을 제거한 길이로 줄 범위를 검사하거나, 선언 합을 그대로 렌더링 문자열 길이로 사용하는 일반화는 채택하지 않습니다. 원본 문단 축·병합 캐시 축·최종 본문 축의 구분을 유지해야 합니다.

## 범위 태그를 적용한 대조

표 63은 영역 태그를 시작·끝·상위 8비트 종류·하위 24비트 데이터로 정의하지만 `0x10`~`0x13`의 의미는 정의하지 않습니다. 조사 도구에서 **종류 `0x11`의 반열린 구간 `[start,end)`을 제외하는 후보**를 만들었습니다. 중간 CR을 무조건 제거하지 않고 범위에 포함될 때만 제외합니다. PARA_TEXT가 없고 선언 길이가 정확히 1인 문단은 이 후보에서만 CR 1유닛으로 대조합니다. 다른 부재 길이를 채우거나 원본을 수정하지 않습니다.

| ViewText 선두 | `0x11` 제외 결과 길이 | 정확히 일치한 BodyText 문단 |
|---|---:|---:|
| 35 | 51 | 27 |
| 116 | 125 | 68 |
| 133 | 109 | 73 |
| 147 | 120 | 79 |
| 167 | 98 | 85 |

5개 모두 UTF-16 바이트 전체가 일치했습니다. 대조군으로 `0x10`을 제외하면 5개 모두 일치하지 않았습니다. 실제 각 비어 있지 않은 `0x11` 범위를 하나씩 제외 대상에서 빼면 원래 후보 바이트와 달라지는 것도 확인했습니다. 이는 이 표본의 `0x11`을 삭제 범위로 해석할 근거입니다. `0x10`을 삽입으로 확정하거나 하위 24비트를 작성자/변경 내용 ID로 확정한 것은 아닙니다.

문제 문단에 편향되지 않도록 루트 문단 전체로 대조를 확장했습니다. ViewText 루트 문단 164개를 병합 값 0/1에 따라 99묶음으로 만들면, `0x11` 제외 결과가 BodyText 루트 문단 99개와 **순서 및 UTF-16 바이트 전체에서 99/99 일치**합니다. 텍스트가 없는 BodyText 문단도 선언 길이 1을 먼저 확인한 뒤 CR 1유닛으로 대조합니다. 임의로 같은 문자열을 검색해 매칭한 결과가 아니며, 99개의 각 대응 쌍을 순서대로 assert합니다. 중첩 표/리스트의 문단·개체 속성·스타일·줄 캐시와 다른 파일/버전까지 동일하다는 주장은 아닙니다.

이제 앞서 CR 제거만으로 실패했던 세 묶음의 차이는 이 범위 적용으로 재현됩니다. 그러나 대응하는 BodyText 루트 줄 캐시가 없으므로 **최종 본문 변환 성공을 ViewText 줄 좌표 검증 성공으로 대체하지 않습니다**. 병합 후속의 삭제된 CR·텍스트 없는 문단·삭제 전후 위치를 구분한 명시적 좌표 API는 구현했지만, 캐시가 실제로 어떤 원문 축을 사용하는지 확정하는 증거는 여전히 필요합니다.

## rhwp와의 대조

확인한 로컬 reference HEAD는 `e8800c8de`입니다. `src/parser/mod.rs`의 `decode_rendered_viewtext`는 일반 압축 해제 성공 및 첫 레코드가 PARA_HEADER인지로 ViewText 선택을 판단하며, 실패하면 BodyText로 돌아갑니다. 이는 전체 줄 위치 검사와 다릅니다. 이 reference가 일반 압축 실패 예로 든 hongbo 파일은 우리 조사에서는 배포용 형태 envelope로 해제되었습니다([별도 계약](hwp5-distribution-viewtext.md)).

`src/parser/body_text.rs`의 `parse_para_header`는 offset 12 이후를 `raw_header_extra`로 보존합니다. `parse_para_line_seg`는 36바이트 단위로 줄을 읽으며 이 함수 자체에서는 문단 길이와 비교하지 않습니다. 따라서 rhwp가 파일을 읽는 사실만으로 병합 줄 좌표가 검증되었다고 볼 수 없습니다. 렌더러 전체의 병합 지원 여부를 이 두 함수만으로 단정하지 않습니다.

## 재현과 후속 검증

```sh
node tests/hwp5/line-cache-survey.mjs zig-out/bin/hwpjs.wasm
zig build line-cache-audit
```

읽기 전용 도구는 CFB 제품 reader와 Node raw DEFLATE, 독립 레코드 순회를 사용합니다. 레코드 헤더에서 level을 직접 읽어 즉시 부모의 텍스트·줄만 수집합니다. 모든 문단의 초과 수와 루트 문단의 후속 병합 묶음을 별도로 계산하여 표의 5개 선두, 초과 9건, 선두 텍스트 길이 일치, 후속 줄 부재, 합산 범위를 assertion으로 확인합니다. 중첩 리스트를 같은 level이라는 이유로 묶지 않습니다. 실행 및 JS 구문 검사를 통과했으며 제품 파서나 입력 파일은 변경하지 않았습니다.

관측 흐름별 병합과 경계 검사는 [병합 인덱스](hwp5-revision-groups.md), 문단 내부 변환은 [좌표 맵](hwp5-revision-coordinates.md)으로 구현했습니다. 줄 캐시 좌표 축의 추가 가설·대조 대상 부재·남은 증거 요건은 [줄 좌표 조사](hwp5-line-cache-coordinates.md)가 소유합니다. 기존 `metadata.validate`의 제한은 현재 유지합니다.

`line-cache-evidence.mjs`가 독립 레코드·텍스트 수집과 두 후보 생성을 소유하고 survey가 실제 파일 대조를 소유합니다. `line-cache-evidence.test.mjs`의 8개 적대적 테스트는 중첩 문단의 직접 자식 분리, 병합 필드 부재와 0, 모든 잘린 prefix, 누락 부모, 중복/홀수 텍스트, 부분/중복 줄 배열, CR 제거 경계, 빈 텍스트·서로게이트·제어문자 보존을 검사합니다. `line-cache-audit`는 이 테스트와 실제 파일 조사를 실행하며 전체 `audit`에도 연결되어 있습니다. 이는 조사 도구 검증이며 제품 ViewText 의미 검증 완료를 뜻하지 않습니다.

최종 `line-cache-audit`를 Debug → ReleaseSafe → ReleaseFast 순서로 실행해 모두 7/7 빌드 단계 및 Node 8/8 테스트와 실제 파일 바이트 대조를 통과했습니다. 제품 코어 수정은 없으며 이번 변경에서 전체 HWP5 audit를 다시 실행한 것은 아닙니다. 로그는 `/tmp/hwpjs-line-cache-audit-{debug,safe,fast}.log`입니다.

범위 대조 후에는 조사 도구의 테스트를 15개로 늘렸습니다. 반열린 구간·중첩 합집합, 종류와 하위 데이터 분리, 역전/초과 범위, 선언 길이 불일치, 부재 텍스트의 1유닛 조건, 중첩 부모·부분/중복 범위 레코드, 병합 값 부재/미지 값·선두 없는 병합·중첩 제외·호출 간 격리를 추가했습니다. `rootMergeGroups`가 관측 루트 묶음 규칙을 소유하여 문제 문단 조사와 전체 순서 대조가 공유합니다. 제품 파서는 계속 원본 범위를 보존하며 조사 후보 변환을 자동 적용하지 않습니다.

최종 범위 대조 및 99개 순서 대조를 포함한 `line-cache-audit`는 Debug/Safe/Fast 모두 Node 15/15, 빌드 단계 7/7로 통과했습니다. 로그는 `/tmp/hwpjs-line-cache-range-{debug,safe,fast}.log`입니다. 전체 HWP5 audit 재실행이나 제품 의미 검증 완료를 주장하지 않습니다.
