# 원본 셀의 기본 대각선

## 범위와 근거

HWP5·HWPX의 원본 셀에서 없음·상향·하향·양방향을 다룹니다. 상향은 왼쪽 아래에서 오른쪽 위, 하향은 왼쪽 위에서 오른쪽 아래입니다. 공식 웹한글의 별도 빈2×2 표에서 정상 UI 적용·HWP/HWPX 출력·창을 닫은 본문을 비교했습니다. HWP5 속성0x0008은 HWPX slash=CENTER와 상향, 0x0040은 backSlash=CENTER와 하향, 양쪽은0x0048입니다. 이름이나 UI 아이콘 순번만으로 방향을 추측하지 않습니다.

원시 증거는 ignored `zig-out/verification/table-fill-r1/diagonal-reference/FINAL-SMALL.json`과 같은 디렉터리의 쌍별 파일·본문 PNG입니다. 뒤에 조사한 꺾은선 사례는 이전 설정이 남은 합성 문맥이어서 단독 매핑의 근거로 쓰지 않습니다. 이중선·굵기 변경의 후기 출력은 방향이 비활성 상태였으며 빨강 저장도 확인하지 못했으므로, 활성 이중선의 한글 픽셀 동치를 주장하지 않습니다. 공식 문서의 오래된 대각선 종류 표를 선 스타일 enum으로 직접 캐스팅하지 않습니다.

## 값과 책임

공통 `border_fill_patch.zig`의 `Patch.diagonal`은 nullable `DiagonalPatch`이며 `directions`와 sparse `stroke`를 가집니다. 네 기존 변 배열은 계속4개입니다. 방향 없음은 선 종류 NONE과 다릅니다. 전자는 방향만 끄고 기존 비활성 선 속성을 보존하며, 후자는 방향을 바꾸지 않습니다. 생략한 방향·종류·굵기·색은 현재 편집값을 유지합니다.

원본 값과 대기 편집의 병합·`has`·검증·비교·canonical 정리는 공통 모델을 사용합니다. 배경의 현재 foreground 보존 규칙도 그대로입니다. 대각선용 병렬 세션이나 직렬화 XML/DocInfo 캐시를 편집 SSOT로 추가하지 않습니다. 포맷별 기존 셀 Entry 안의 scalar 값으로 저장하고 같은 체크포인트·현재 리소스·저장 계획을 사용합니다.

HWP5 방향은 `table_diagonal_values.zig`, JS 관측·표 렌더링은 `table-diagonal-directions.mjs`가 각 경계를 소유합니다. HWP5 bit2–7만 바꾸고 나머지는 보존합니다. 원본 방향이0/2 이외이거나 꺾은선·회전·중심·미확인 상위 비트가 있으면 방향 변경을 거부합니다. 선 속성만 바꾸는 요청은 그 원시 방향 바이트를 보존합니다. 다섯째 선의 종류·굵기·COLORREF는 고정 prefix의26/27/28 위치를 사용합니다.

HWPX는 slash/backSlash의 NONE/CENTER와 Crooked/isCounter 각각 문자열0, centerLine=NONE을 확인한 기본 문맥에서만 방향을 바꿉니다. 필드 부재를0으로 관측하지 않습니다. 선 속성만 바꿀 때에는 미확인 방향 속성을 그대로 둡니다. `<diagonal>`이 없으면 새 선의 종류·굵기·색이 모두 명시돼야 생성합니다. 단, 알려진 기본 방향을 없음으로 끄는 동작은 새 선 생성이 아니므로 선 부재를 보존합니다. 이 구분은 실제 실패를 재현한 뒤 회귀 검사로 고정했습니다.

## ABI와 앱

기존 `set_cell_styles`의4인수·테두리32바이트·채우기48바이트 형식은 유지합니다. 새 `set_cell_styles_v2`는 세 버퍼/길이 쌍의6인수입니다. 별도 대각선 wire48바이트는 다음12개 little-endian uint32 순서입니다.

| 위치 | 값                                        |
| ---- | ----------------------------------------- |
| 0–2  | section, tableNode, listNode              |
| 3    | presence mask: 방향1, 종류2, 굵기4, 색8   |
| 4    | 없음0, 상향1, 하향2, 양방향3              |
| 5    | 공통 선 코드: NONE0, SOLID1, DOUBLE_SLIM2 |
| 6–7  | 굵기(0.01mm), RGB24 색                    |
| 8–11 | 예약0                                     |

생략한 슬롯도0이어야 하며 mask가 명시0과 부재를 구별합니다. 메시지의 optional `diagonals` 배열은 `borders`·`fills`와 같은 소유자로 합칩니다. 배열 내 중복·서로 다른 tableNode 충돌을 거부하고 세 배열 전체의 서로 다른 셀 한도4096을 적용합니다. Map으로 병합한 단일 planner·명령·이력 사건으로 게시하며 마지막 셀이나 할당 실패에서 부분 적용하지 않습니다. 구 두 배열 메시지는 새 필드를 억지로 추가하지 않습니다.

`cellDiagonalAvailable === true`는 실제 v2 export를 확인한 capability입니다. 앱은 이때만 세 번째 탭을 제공합니다. 관측 seed는 dirty가 아니며 확인만 눌러 쓰지 않습니다. 바꾼 성분만 요청하고, 범위·표 전체는 [공통 셀 범위 검증](table-cell-fill-batches.md)을 공유합니다. 미확인 값을 검정·기본 굵기로 만들어 보내지 않습니다. 새 이중선 선택은 활성화하지 않으며, 원본 이중선은 관측과 보존을 구분합니다.

## Canvas와 검증 경계

대각선은 네 변의 edge4가 아니라 별도 선분 목록입니다. 현재는 SOLID 선을 셀 좌표와 기존 행 변환·스크롤·clip 안에서 그립니다. 미지원 대각선은 별도 진단으로 남기고, 확인된 네 변·채우기를 지우지 않습니다. 대각선만 있는 셀도 실제 원본 선으로 집계하며 미지원 성분을 완성으로 세지 않습니다. 꺾은선·회전·중심선·이중선 대각선의 조판 동치는 이 범위 밖입니다.

집중 Native 검사는 새 HWP5 12개와 기존 채우기14개, HWPX 14개, 별도 wire12개입니다. HWPX의 알려진 방향 끄기/없는 선 보존 반례는 최초 실패와 수정 후 결과를 구분합니다. 현재 Native WASM 후보는 `82031994…155ccc`,446 exports이며 기존444개와4인수 ABI를 보존하고 v2 두 함수만 추가했습니다. 실제 API 저장·재열기·브라우저·공개 배포 증거는 집중 Native 검사와 별도 gate로 기록합니다. 이 수치를 서로 중복 합산하거나 전체 표·한글 조판 완료율로 사용하지 않습니다.

## 실제 WASM 회귀

2026-11-07의 실제 WASM 후보에서 기본4방향×2형식, 세 성분의 단일 이력, 마지막 잘못된 셀의 전체 거부·redo 보존·구4인수 API 회귀를12개 검사로 확인했습니다. HWP5 저장은 독립 CFB 스트림·레코드 검사, HWPX 저장은 Python 표준 ZIP/XML 검사로 검증하며, 원본 리소스·비대상 스트림·항목과 참조를 대조합니다. 일부러 잘못된 색을 기대값으로 주는 음성 대조도 거부돼야 합니다. 실제 DTO에서 Canvas 선분 계획으로 연결한 검사는 브라우저의 실제 픽셀 검사와 구분합니다.

같은 후보에서 기존 채우기·테두리 실제 검사18개와 HWPX 원시 필드 검사1개도 통과했습니다. 이19개를 새12개와 중복 합산하지 않습니다. 새 UI의 port·view·tool102개, 관측106개, 렌더러 및 의미 채우기86개가 통과했습니다. 오래된 합성 DTO에서 없는 방향 필드를0으로 간주하던 기대값은 수정했으며, 실제 입력의 부재를 허용하는 제품 fallback을 넣지 않았습니다. 사용자 미추적 이중선 합성 검사의 기존 실패는 별도 보존했고 이 결과에 포함하지 않습니다.

증거는 ignored `zig-out/verification/table-diagonal-r1/`의 `node-integration/native-node-r1/`, `node-legacy19/`, `ui-observer/`, `render/`에 나눠 둡니다. 새 SDK4종·단일 Vite 빌드·엄격 타입·정적 배포 쌍 검사는 통과했고, 실제 브라우저와 공개 배포는 이 결과만으로 완료라고 판단하지 않습니다.

## 교차 경계 재검증

교차 검토에서 첫 SDK 후보의 runtime이 검증된 메시지에서 `borders`·`fills`만 SDK setter로 넘겨 `diagonals`를 누락하는 결함을 재현했습니다. 이 후보는 API 단독 검사 통과와 별개로 배포 대상에서 제외했습니다. runtime은 대각선 배열의 명시 여부까지 보존해 전달하고, 구 두 배열 메시지에는 새 필드를 만들지 않습니다. 수정 후 실제 Native를 연결한 runtime 명령 검사와 새 SDK·브라우저 검사를 별도로 수행합니다.

한 셀의 안쪽 테두리 범위가 비어 있어도 같은 원자 요청에 유효한 대각선이 있으면 적용할 수 있어야 합니다. 기존 채우기와 같은 규칙으로 빈 테두리만 있는 요청은 계속 거부하고, 대각선이 있는 결합 요청의 불필요한 전체 거부를 수정했습니다.

수정한 경계는 실제 DOM 없는 `ReaderRuntime`에 Native WASM을 연결해2개 형식별 검사로 확인했습니다. 이 증거는 Worker 메시지 전송이나 실제 Canvas를 대신하지 않습니다. 구 배열 부재·명시 빈 배열의 no-op에서는 바로 직전 이력 열거 순서·현재 revision·저장 바이트·redo 가능 여부가 유지돼야 합니다. 이력 열거는 현재 revision·undo·redo 순서이므로, 서로 다른 현재 revision 사이의 배열 순서를 그대로 비교하는 초기 검사 착오도 수정했습니다.

최종 CI와 같은 Node24.20 명령에서 변환 플래그 없이 기존18개·새 API12개·runtime2개·원시 필드1개, 총33개가 통과했습니다. 초기 runtime 조사에서 독립 Python oracle의15초 시간 초과가 한 번 있었으며 실패 원본과 플랫폼 기록을 보존했습니다. 원인은 확정하지 못했고, 최종 통과를 그 시간 초과의 수정이라고 주장하지 않습니다. 해당 증거는 `render/runtime-initial-failure-classification.json`과 `runtime-ci33-no-transform.tap`입니다.

## 미지원 바깥 선과 알려진 대각선의 분리

다음 교차 검토에서는 HWP5의 네 변 중 kind2 또는 HWPX의 DASH가 있을 때, 따로 확인된 SOLID 대각선까지 그리기 계획의 조기 실패로 사라지는8개 합성 반례를 확인했습니다. 이는 새 기본 대각선의 부분 렌더링 공백이며 Native 저장 손상이나 기존 기능의 회귀를 입증한 결과는 아닙니다. 실제 Noori 브라우저10개 통과와도 별개입니다.

수정 범위는 확인된 채우기·효과·prefix 검사 이후의 네 변 거부입니다. 알려진 대각선 선분은 실패 계획에서도 보존하고, Canvas는 행 변환·셀 clip을 유지해 이 선분을 따로 그립니다. 미지원 바깥 선 진단과 부분 지원 집계는 유지하며 전체 원본 렌더링 완료로 세지 않습니다. 미확인 최상위 속성·효과·채우기·방향의 안전 검사를 이 변경으로 완화하지 않습니다. 기록은 ignored `next-ui/diagonal-partial/`에 있으며 후속 source·실제 API·새 SDK·브라우저 결과를 별도 gate로 확인합니다.

부분 렌더링의 최종 source gate는 집중29개·확장86개·UI102개·엄격 타입·선택 lint/format 통과입니다. 실패 집계가 한 셀을 두 번 세던 반례는 최초 검토와 수정 후 결과를 나눴습니다. 확인된 선분 표시를 성공 집계로 바꾸지 못한 경우에는 부분 표시가 아니라 paintFailureCount만 증가시키며 원래 바깥 선의 미지원 셀 수는1로 유지합니다.

이 수정 후 실제 WASM 저장·재열기 API12개를 새 renderer source pin으로 다시 실행해 통과했습니다. 앞의33개 전체를 다시 실행했다고 주장하거나33+12를45개 고유 검사로 합산하지 않습니다. Native binary·runtime·원본 Noori 지문은 그대로이며 shipping source의 변경은 표시 계획·Canvas·안내 문구에 한정됩니다. 증거는 `render/r3-actual12-final-handoff.json`과 `next-ui/diagonal-partial/r3/`입니다.

## 적대적 검증의 다섯 경계

1. 원시 포맷: 공식 쌍별 출력과 Native 방향·없는 선·미확인 비트·현재 편집값을 대조했습니다.
2. ABI·원자성:15개 sparse mask, 배열 간4096 공통 한도·중복·충돌·예약값·할당 실패와 구4인수 계약을 확인했습니다.
3. UI·관측: 원본 seed 무변경, 정확 capability, sparse 색, Apply 후 새 lease·탭, 빈 안쪽 테두리와 유효 대각선 결합을 확인했습니다.
4. 전달·저장: runtime의 누락을 재현·수정하고 실제 WASM·독립 CFB/XML·이력·재열기로 대조했습니다.
5. 부분 Canvas: 미지원 네 변과 알려진 대각선의 독립 표시·clip·실패 집계, 실제 브라우저와 다운로드를 별도 증거로 확인합니다.

이 다섯 경계의 검토를 전체 형식·모든 예제·한/글 전체 조판의 무결점 전수검사라고 부르지 않습니다.

## 최종 R3 브라우저 후보
