# 양식 속성의 UTF-16 토큰과 중첩 구조

[양식 접두부](hwp5-form-object.md) · [본문 계약](hwp5-body-contracts.md)

## 근거와 선택 범위

공개 명세는 양식 태그를 나열하지만 속성 문자열 문법을 정의하지 않습니다. `form-01.hwp`·`form-02.hwp`의 양식 10개에서 `CommonSet`, `CharShapeSet`, 타입별 묶음의 `set:N` 끝이 다음 묶음 시작과 일치하고, `wstring:N` 안의 공백이 문자열에 포함되는 것을 확인했습니다. 파일 버전은 두 개 모두 5.0.3.0입니다.

이 API는 **N을 원시 UTF-16 코드 유닛 수로 해석하는 모델을 명시적으로 선택**합니다. 실제 표본의 문자열은 이 기준에 맞지만, 보충 평면 문자가 있는 원본 한글 프로그램 산출물까지 대조한 것은 아닙니다. rhwp `e8800c8de`의 `parse_form_properties`는 문자열을 Rust `char` 배열로 바꾸고 set 길이를 건너뛰며 속성을 평탄화합니다. 같은 레퍼런스의 문자열 작성기는 내부 문자열/묶음 길이에 `chars().count()`를 사용합니다. 비 BMP 문자에 대한 단위 차이를 확인하지 않은 상태에서 두 규칙을 자동 혼용하지 않습니다.

## 문법과 토큰 책임

`body/form_property.zig`의 `Iterator.initObservedUnits(bytes)`와 `next()`는 한 범위 안의 토큰만 읽습니다. 모든 입력·반환 문자열은 UTF-16LE 원시 바이트이며 할당·Unicode 정규화·손실 디코딩을 하지 않습니다. init으로 생성한 iterator의 내부 상태를 임의 변경하지 않는 전제입니다. 입력 길이가 홀수면 `InvalidFormPropertyEncoding`입니다. 실패한 next는 앞쪽 공백을 포함해 호출 전 위치를 유지합니다.

| 형식 | 반환 value | 범위 |
|---|---|---|
| `Key:set:N:BODY` | BODY 원문 | 정확히 N유닛인 하위 속성 범위 |
| `Key:wstring:N:TEXT` | TEXT 원문 | 정확히 N유닛, 공백·콜론·NUL·서로게이트 보존 |
| `Key:int:NUMBER` | 숫자 표기 원문 | 선택적 `-` 뒤 십진 숫자, 공백 또는 현재 범위 끝까지 |
| `Key:bool:NUMBER` | 숫자 표기 원문 | int와 같은 문법, bool이라는 원래 종류는 구분 |

키는 비어 있지 않아야 하며 U+0000~U+0020이나 콜론을 포함하지 않습니다. 형식 이름은 대소문자를 구분하는 위 네 종류만 지원합니다. 모르는 형식은 `UnsupportedFormPropertyType`이며 경계를 추측해 다음 속성으로 건너뛰지 않습니다. 속성 사이와 범위 앞뒤의 구분자는 U+0020 공백입니다. 문자열/묶음을 읽은 뒤 다른 속성이 바로 붙어 있으면 `InvalidFormPropertySeparator`입니다. 같은 이름의 키가 반복되어도 덮어쓰거나 제거하지 않습니다.

정수·불리언은 고정 폭 수나 true/false로 변환하지 않습니다. `0001`, `-1`, 큰 정수, bool의 0/1 외 표기를 그대로 남깁니다. 이러한 값의 문법이 맞다는 것과 해당 속성에 허용되는 값이라는 것은 다릅니다. 속성별 범위·기본값·불리언 의미는 후속 스키마 책임입니다.

N은 부호 없는 십진 표기를 u64로 계산합니다. u64 초과는 `FormPropertyLengthOverflow`, 유효한 수이지만 현재 입력에 담을 수 없는 길이는 `UnexpectedEnd`입니다. 내부 주소 크기에 따라 오류가 달라지지 않도록 고정 폭 계산 뒤 안전하게 변환합니다. 실제 UTF-16 슬라이스의 길이 검사는 기존 `utf16_string.readUnits`가 소유하며 선언 크기로 할당하지 않습니다.

Property의 offset/value_offset은 바이트 위치, raw/key/value는 빌린 원문, kind는 원래 형식입니다. 토큰 iterator의 위치는 해당 범위 기준입니다. set의 본문이 완전한 속성 문법인지는 iterator 자체가 재귀적으로 검사하지 않습니다.

## 전체 중첩 구조와 SSOT

`body/form_property_tree.zig`의 `Tree.parseObservedUnits(allocator, bytes, options)`는 같은 iterator를 프레임마다 사용해 모든 set 본문을 검사합니다. set 길이를 무시하고 안쪽 토큰을 외부 범위에서 완성할 수 없습니다. 재귀 호출 대신 명시적 프레임 배열을 사용합니다.

Tree는 노드 배열만 소유하고 `deinit`으로 해제합니다. 원문 슬라이스는 계속 입력을 빌리므로 Tree를 사용하는 동안 원본 입력을 유지해야 합니다. 노드는 원본 순서의 전위 순회이며 parent(null은 루트), 배타적 subtree_end, Property를 가집니다. 트리의 두 바이트 위치는 전체 입력 기준으로 변환됩니다. 부모 set의 원문과 자식 원문은 겹칠 수 있으며 서로 독립된 소유 버퍼가 아닙니다.

기본 전체 입력 한도는 64MiB, 노드 수는 100,000, set 중첩 깊이는 64입니다. 노드 수는 모든 묶음과 하위 속성이 공유하며 하위 범위마다 초기화하지 않습니다. 루트 속성 범위 깊이는 0, 첫 set은 1이고 빈 set도 깊이를 소비합니다. 한도 초과는 각각 `FormPropertyInputLimit`, `FormPropertyNodeLimit`, `FormPropertyDepthLimit`입니다. 입력 바이트 한도가 메타데이터까지 포함한 프로세스 메모리 한도라는 뜻은 아닙니다.

문법은 토큰 모듈, 소유 관계·전역 예산·전체 실패 정리는 트리 모듈, 길이 접두부는 기존 양식 envelope 모듈에 둡니다. 실패 시 노드와 프레임 배열을 해제하고 부분 트리를 반환하지 않습니다. 시간은 입력 길이와 노드 수에 선형이고 메타데이터 메모리는 실제 노드 수·깊이에 비례합니다. 큰 선언 길이만큼 버퍼를 생성하거나 조상마다 본문을 복사하지 않습니다.

## 실파일·적대적 검증

테스트 mode 105는 노드·깊이 한도(u32 두 값) 뒤의 UTF-16 속성 문자열을 받고, 전체 노드 수와 노드별 parent/subtree_end/kind/두 위치/원문·키·값 길이 및 키·비-set 값의 정확한 바이트를 반환합니다. set의 본문은 자손으로 표현하여 보고서 크기가 깊이 배로 증가하지 않게 합니다. 제품 공개 ABI가 아닙니다.

`form-property.mjs`는 독립 JS 정규식·범위별 재귀 oracle과 전체 반환 바이트를 비교합니다. 합성 정상 173건·거부 245건으로 빈 입력·중복 키·음수·u64보다 큰 정수 원문·선행 0, 비 BMP/고립 서로게이트·NUL·콜론·공백, 범위 밖 길이, 알려지지 않은 형식, 누락 구분자, 노드·깊이·입력 한도 정확값/부족, 256단계 중첩과 오류 후 재처리를 검사합니다. 기본 한도 100,000노드 성공·100,001노드 거부·원본 재처리도 포함합니다.

| 파일 | 양식 | 전체 속성 노드 | set | 정상인 잘린 prefix | 손상된 prefix |
|---|---:|---:|---:|---:|---:|
| form-01.hwp | 5 | 118 | 15 | 30 | 4,276 |
| form-02.hwp | 5 | 118 | 15 | 30 | 4,268 |

각 속성 문자열의 모든 바이트 prefix를 검사합니다. 일부 prefix는 완전한 루트 묶음에서 끝나므로 그 자체로 유효한 속성 문자열입니다. 이를 잘림이라는 이유만으로 거부하지 않으며, 실제 HWP payload 전체의 길이 검사는 상위 envelope와 framing의 책임입니다. 두 파일의 Caption 값 `명령 단추`, `선택 상자`, `라디오 단추`도 원문과 대조합니다. 같은 값이 나오는 것만 확인하지 않고 부모·범위·순서·바이트 위치를 포함한 보고서 전체를 비교합니다. 디스크 표본·스냅샷은 수정하지 않습니다.

네이티브 테스트는 next 오류의 원자성, 부모 범위 밖 값을 읽지 않는 조건, 전역 예산, 전체 성공·늦은 오류의 모든 할당 실패를 검사합니다. 32단계 중첩의 프레임·노드 배열 증가와 안쪽 미지 형식 실패도 모든 할당 실패 지점에서 실행합니다. 처음에는 길이를 usize로 계산하여 `4294967296`이 네이티브에서는 UnexpectedEnd, WASM에서는 FormPropertyLengthOverflow인 차이를 재현했습니다. u64 계산으로 수정하고 두 플랫폼 모두 UnexpectedEnd, u64 초과는 동일한 오버플로 오류임을 회귀 검사합니다.

## 남은 범위

기본 문서/컨테이너 검사와 양식 envelope에서 자동 실행하지 않습니다. 미지원 형식이 있는 원문은 상위 View에 그대로 남아 있으며, 문법 검증 성공을 양식 의미 검증 성공으로 집계하지 않습니다. 양식 타입별 허용 키·자료형·기본값, 참조 검증, 컨트롤 소유권·공통 속성과의 연결, 이벤트 실행·레이아웃·편집·저장은 후속 범위입니다. 다른 파일 버전과 비 BMP 원본 프로그램 표본의 길이 규칙도 추가 대조가 필요합니다.

## 실행 결과와 재검토

Debug → ReleaseSafe → ReleaseFast 전체 audit가 성공했습니다. 당시 네이티브는 Debug 282/282, Safe/Fast 283/283이며 각 모드 기존 Node 47/47, 조사 도구 Node 22/22, 빌드 단계 16/16, HWP5 WASM 검사 호출 1,403,442회입니다. 실행 중 중첩 할당 실패 테스트를 확장했으므로 완료 후 최종 네이티브 전체 테스트를 세 모드에서 다시 실행해 모두 283/283을 확인했습니다. 기본 노드 한도까지 포함한 최종 양식 속성 전용 검사도 세 WASM 산출물에서 재실행하여 위 정상 173건·거부 245건 및 실파일 전체 보고서·prefix 대조를 확인했습니다.

적대적 재검토에서는 부모 범위 밖 읽기, 토큰 오류 원자성, 중첩/전체 예산과 모든 할당 실패, 원문·중복 키·숫자 의미 보존, 네이티브/WASM 길이 오류의 일관성과 SSOT 책임 분리를 확인했습니다. 포맷·JS 구문·문서 링크·diff 검사도 통과했습니다. 전체 로그는 `/tmp/hwpjs-form-property-{debug,safe,fast}.log`, 최종 네이티브 재실행은 `/tmp/hwpjs-form-property-native-final-{debug,safe,fast}.log`입니다. 이러한 통과를 전체 양식 의미 지원이나 전체 명세 완료로 해석하지 않습니다.
