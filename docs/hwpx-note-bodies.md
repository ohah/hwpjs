# HWPX 각주·미주 본문 구조와 원값

`Document.inspectNoteBodies()`와 `XmlTrees.inspectNoteBodies()`는 구조가 선택한 2011 section XML의 정확한 `hp:footNote`·`hp:endNote`를 문서 순서대로 소유 보고서에 반환합니다. `Document.inspectKnown().note_bodies`도 같은 검사기를 사용합니다. 이 검사는 [구역 각주·미주 모양](hwpx-section-note-shapes.md)의 `footNotePr`·`endNotePr`와 별도입니다. 주석의 부모 이름/namespace·요소 인덱스·원문, 직접 `hp:subList`의 순서·중복·부재, 각 목록의 직접 `hp:p` 인덱스와 원문을 보존합니다. 다른 namespace의 동명 요소나 중첩 목록을 직접 자식으로 승격하지 않습니다.

`note_bodies.zig`가 선택 범위·관계·원문 수명·한도를 소유하고, `note_body_fields.zig`가 주석 필드를 읽습니다. 공식 [한컴 NoteType 구현](https://github.com/hancom-io/hwpx-owpml-model/blob/1453388472c703a4b299a0834f425cdac16644b9/OWPML/Class/Para/NoteType.cpp)과 [선언](https://github.com/hancom-io/hwpx-owpml-model/blob/1453388472c703a4b299a0834f425cdac16644b9/OWPML/Class/Para/NoteType.h)의 `flag`·`instId`는 UINT32, `number`와 `userChar`·`prefixChar`·`suffixChar`는 UINT16 폭으로 검사합니다. 문자 필드는 UTF-16 **코드 단위 숫자**로 보존하며 서로게이트를 임의로 거부하거나 문자로 변환하지 않습니다. 관측된 `id` 속성은 모델의 여섯 필드와 구분해 불투명 원값으로 유지합니다. 부재와 빈 값은 구분하고 입력에 없던 모델 기본값을 채우지 않습니다. 직접 `subList`의 공통 11개 속성과 enum/숫자/Boolean 판정은 [ParaListType 단일 구현](hwpx-para-list.md)의 `para_list_attributes.zig`를 재사용합니다.

보고서는 주석 원문을 한 번만 복사하고, 그 안의 목록·직접 문단 XML은 복사본의 범위를 참조합니다. 따라서 원본 `Document`·ZIP 바이트·XML 트리를 해제한 뒤에도 보고서가 살아 있는 동안 유효하며 마지막에 `deinit()`해야 합니다. 주석·목록·직접 문단·직접 자식 개수와 속성·원문 소유 바이트에 독립 한도를 둡니다. 목록의 직접 문단 **경계**만 이 모듈이 소유합니다. 문단의 속성·run·텍스트 값은 기존 section 검사기가 담당하며, 각주/미주 표시 순서와 실제 번호 연결, 쪽 배치, 편집·저장·무손실 왕복은 아직 구현 범위 밖입니다.

본문 안 `autoNum`의 포함 관계와 `numType` 일치 진단은 별도 [각주·미주 안 번호 관계](hwpx-note-number-links.md)가 소유하며, 표시 번호의 계산은 여전히 하지 않습니다.

로컬 두 fixture 모음의 HWPX 484개 후보 중 ZIP 종료 레코드 거부 6개·암호화 2개를 제외한 476개 문서의 section XML을 독립 ZIP/XML로 조사했습니다. `footNote` 396건·`endNote` 823건, 직접 `subList` 1,219건, 그 안의 직접 `p` 8,268건을 관측했습니다. `flag`는 각주 5건·미주 27건에만 있었고 `number`·`instId`는 각각 1,215건, 관측 `id=""`는 각주·미주 각각 2건이었습니다. 이 분포는 해당 corpus의 원값이지 모든 HWPX 버전의 필수성 또는 전체 문서 지원률을 뜻하지 않습니다.

`tools/hwpx-note-bodies-diff.py`는 허용 파일 476개의 파일별 해시와 7개 개수, 거부/암호화 파일 집합을 독립 `zipfile`·`ElementTree` 결과와 대조해 모두 일치시켰습니다. Zig 조사기는 별도로 각 주석·목록·직접 문단의 반환 XML 바이트를 소유 section 트리의 해당 원문 범위와 476개 파일 전부에서 대조했습니다. 해시에는 각 주석의 종류·부모/요소 인덱스·알려진 속성 원값과 추가 속성 수, 직접 목록의 속성·진단·문단 인덱스 및 직접 자식 수가 포함됩니다. 문단 내부 XML 값·텍스트까지 **독립 XML 오라클**로 검증했다고 주장하지 않습니다. 독립 oracle의 변이 10개는 일반 Python과 `python3 -O`에서 모두 감지됐습니다. 기존 fixture `footnote-endnote.hwpx`와 추가 실파일의 단독 API/`inspectKnown` 보고서도 해시가 일치했습니다. fixture에는 각주·미주가 각각 **2건**으로 확인됐으며, 처음 1건으로 가정한 테스트 기대값을 실제 ZIP 기준으로 수정하고 테스트 실패 시 해제 경로를 보강한 뒤 재실행했습니다.

적대적 재검토는 (1) 정확한 namespace·부모·직접 자식과 중복/부재, (2) 공식 숫자 폭·XML 참조·빈/부재·미지 ParaListType 값, (3) UTF-16 양 바이트 순서·원본 해제 후 슬라이스 수명, (4) 각 개수/바이트 한도·OOM·오류 경로 해제량, (5) 파일별 독립 대조·known 연결의 다섯 경계로 수행합니다. 이 결과는 본문 경계 검사에 한정되며 실제 번호, 각주/미주 참조 짝, 표시 텍스트의 선택, 레이아웃을 검증하지 않습니다.

검증 명령 중 `zig test src/root.zig --test-filter 'HWPX note bodies'`의 Debug·ReleaseSafe·ReleaseFast는 각각 10/10 통과했고, `zig test src/hwpx_note_bodies_survey.zig -O ReleaseFast --test-filter 'HWPX note bodies real files known integration'`는 1/1 통과했습니다. 기존 `hwpx_known_survey.zig`의 ReleaseFast 8개 shard도 모두 통과했습니다. `zig build -Doptimize=ReleaseSafe`, 대상 Zig 파일의 `zig fmt --check`, `git diff --check`도 통과했습니다. 전체 `zig build test --summary all`은 종료 코드 0, `Build Summary: 5/5 steps succeeded; 2634/2634 tests passed`였습니다. 이 명령의 출력 중간에 있던 `failed command: .../test --cache-dir=... --listen=-` 줄은 후속 [Zig stderr 독립 재현](zig-test-stderr.md)으로 설명됐습니다. 이 문구만으로 실제 실패를 판정하지 않습니다.
