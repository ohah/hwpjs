# HWPX 번호 컨트롤 원값 검사

`Document.inspectNumberControls()`와 `XmlTrees.inspectNumberControls()`는 선택된 2011 section의 정확한 `hp:autoNum`·`hp:newNum`·`hp:pageNum`을 XML 순서대로 소유 보고서에 반환합니다. `Document.inspectKnown().number_controls`도 같은 검사기를 사용합니다. 부모의 이름과 namespace를 보존하지만, `hp:ctrl` 아래로만 임의 축소하지 않습니다. 외부 namespace의 동명 요소는 대상이 아닙니다.

`number_controls.zig`는 section 순회·부모·원문 XML·직접 자식과 한도를, `number_control_fields.zig`는 속성의 부재/빈 값 구별·정수/Boolean 어휘·enum 진단을 소유합니다. 직접 `hp:autoNumFormat`은 순서·중복·속성·원문을 보존합니다. 그 밖의 직접 자식 수와 format의 직접 자식 수를 진단합니다. `pageNum`의 format 자식은 예상 밖으로 표시하고, `autoNum`의 format 부재는 진단만 합니다. 보고서 문자열과 원문은 원본 문서 해제 후에도 유효하며 `deinit()`해야 합니다.

각주·미주 본문 안의 번호 컨트롤 포함 관계는 별도 [각주·미주 안 번호 관계](hwpx-note-number-links.md)가 이 보고서와 주석 보고서의 요소 인덱스를 연결해 관측합니다.

기준은 한컴의 [자동/새 번호 모델](https://github.com/hancom-io/hwpx-owpml-model/blob/1453388472c703a4b299a0834f425cdac16644b9/OWPML/Class/Para/AutoNumNewNumType.cpp), [번호 형식](https://github.com/hancom-io/hwpx-owpml-model/blob/1453388472c703a4b299a0834f425cdac16644b9/OWPML/Class/Para/AutoNumFormatType.cpp), [쪽 번호](https://github.com/hancom-io/hwpx-owpml-model/blob/1453388472c703a4b299a0834f425cdac16644b9/OWPML/Class/Para/pageNum.cpp), [열거형 목록](https://github.com/hancom-io/hwpx-owpml-model/blob/1453388472c703a4b299a0834f425cdac16644b9/OWPML/Class/enumdef.h)입니다. `autoNum`·`newNum`의 `num`은 signed `INT`로 검사합니다. 0과 음수도 어휘·범위상 허용하고, 실제 번호 배정은 계산하지 않습니다. `numType`, `pageNum/@pos`, `pageNum/@formatType`, `autoNumFormat/@type`은 알 수 없는 값을 거부하지 않고 원값과 진단으로 남깁니다. `autoNumFormat/@supscript`만 XML Boolean 어휘로 검사합니다. format의 번호 형식 enum은 [각주/미주 모양](hwpx-section-note-shapes.md)과 `numbering_values.zig` 한곳을 공유합니다. 이 검사는 표시 결과, 번호 증가·재시작, 조판, 편집·저장, 전체 XSD 적합성을 보증하지 않습니다.

합성 테스트는 3종 컨트롤, `num=0`·음수·범위 초과, 누락/빈 값, 알 수 없는 enum, 외부 namespace, 자식 중복·순서·예상 밖 자식, UTF-16 양쪽 엔디언, 한도, OOM, 오류 경로 누수, 문서 해제 후 소유권과 `inspectKnown` 연결을 검증합니다. 로컬 두 fixture 모음의 HWPX 484개 후보를 독립 ZIP/XML로 조사한 결과 6개는 ZIP 종료 레코드가 없고 2개는 암호화되어 476개를 검사할 수 있었습니다. 그 안에서 `autoNum` 1,282건, `newNum` 125건, `pageNum` 140건, `autoNum` 직접 `autoNumFormat` 1,280건을 관측했습니다. format 없는 `autoNum` 두 건은 `reference/rhwp/samples/issue3460/svg_picture_repro.hwpx`에 있습니다. `tools/hwpx-number-controls-diff.py`는 허용 파일 476개의 파일별 독립 해시·5개 개수를 Zig 결과와 모두 대조했으며 ZIP 거부 6개·암호화 2개의 파일 집합도 일치했습니다. oracle 변이 검사는 Python 일반·`-O` 모드에서 통과했고 실파일 두 개의 단독 API와 `inspectKnown` 해시도 일치했습니다. 이 분포는 관측치이지 모든 HWPX 버전의 완전성 증명은 아닙니다.

적대적 검증은 다섯 경계로 나눴습니다. (1) 선택 경계: 정확한 2011 namespace·직접 format만 인식하며 외부 동명 요소, 다른 부모와 자식 중복을 합성 검사하고 section 순서를 확인했습니다. (2) 값 경계: 부재·빈 문자열·미지 enum을 각각 보존하고 signed32·Boolean의 유효/오류 어휘, UTF-16 양쪽 엔디언을 확인했습니다. (3) 소유·한도 경계: 정확한 바이트 한도, 각 개수 한도, 모든 할당 실패 지점 및 정상 할당 뒤 어휘 오류의 해제량을 확인했습니다. (4) 독립 오라클 경계: Python ElementTree의 476개 파일별 결과와 변이 10개가 Zig 보고서와 분리되어 검증됐습니다. (5) 통합 경계: 단독 API와 `inspectKnown` 해시 및 기존 각주/미주 번호 enum 회귀를 확인했습니다. 어느 경계도 번호 표시 의미나 전체 문서 검증 완료를 뜻하지 않습니다.

전체 Debug `zig build test --summary all`은 종료 코드 0, 5/5 단계, 2,622/2,622 테스트 통과로 끝났습니다. 이 실행 후 **테스트만** 3개 더 추가했으므로 최종 테스트 소스의 해당 10개 필터 테스트는 Debug·ReleaseSafe·ReleaseFast 각각 별도로 통과시켰습니다. ReleaseSafe 제품 빌드와 기존 HWPX `inspectKnown` 실파일 8개 shard도 모두 통과했습니다. 전체 Debug 출력의 `failed command` 한 줄은 후속 [Zig stderr 독립 재현](zig-test-stderr.md)으로 설명됐습니다. 출력 문구 자체가 테스트 성공이나 전체 번호 기능의 정확성을 증명하지는 않습니다.

2026-09-27 재검증: 한컴 고정 버전 모델의 `num`·`numType`, `autoNumFormat`의 다섯 속성, `pageNum`의 세 속성과 현재 필드 파서를 대조했습니다. 전용 필터는 Debug·ReleaseSafe·ReleaseFast에서 각각 10/10, 실파일 단독/known 연결은 1/1, 독립 오라클의 일반·`-O` 자체검사는 각각 통과했습니다. 전체 파일별 대조는 허용 476개·ZIP 거부 6개·암호화 2개, `autoNum` 1,282개·`newNum` 125개·`pageNum` 140개·직접 format 1,280개·format 없는 `autoNum` 2개로 다시 일치했습니다. ReleaseSafe 제품 빌드도 통과했습니다. 앞서 같은 제품 코드에서 통과한 known-inspections 8개 shard는 이번 문서 전용 재검증에서 다시 실행하지 않았으며, 번호 표시 계산·편집·저장은 검증 범위 밖입니다.
