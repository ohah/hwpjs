# ICC 다국어 문자열 선택

## 명세와 정책 경계

[ICC.1:2022 §10.15](https://www.color.org/specifications/ICC.1-2022-05.pdf)는 원하는 지역이 없으면 같은 언어의 레코드, 원하는 언어도 없고 다른 사용자 선호도 없으면 첫 레코드를 사용하도록 설명합니다. [기술 노트 01-2002](https://www.color.org/unicode/)의 ISO 639-1·ISO 3166 코드와 동의 코드 설명은 별도 등록·동등성 검증 요구입니다. BCP 47 등록부의 폐기 코드·예약 범위 허용을 현행 ISO 등록 유효성과 동일시하지 않습니다.

`src/image/icc/mluc_selection.zig`는 파싱된 불변 mluc.View와 호출자가 우선순위대로 제공한 Preference 배열을 받습니다. 각 선호에 대해 전체 언어·국가 일치를 먼저 찾고, 없으면 해당 언어의 첫 레코드를 고릅니다. 그 언어가 없으면 다음 선호로 진행합니다. 모든 선호가 실패하거나 선호가 없으면 첫 레코드, 레코드가 없으면 null입니다.

다중 선호 배열 순서 우선과 동률에서 파일 순서 유지는 이 API의 명시적 정책이며 명세가 세부 순위 알고리즘까지 지정한다는 주장이 아닙니다. 앞선 선호의 같은 언어 후보가 뒤 선호의 정확 지역 후보보다 우선합니다. 지역을 생략한 선호는 해당 언어의 첫 레코드를 선택합니다. 지역 부재(null)는 원시 국가 코드 0000h와 다릅니다.

언어·지역은 원시 두 바이트끼리 비교하며 대소문자·동의 코드·과거 코드·비표준 코드 보정을 하지 않습니다. 선택 결과는 ISO 등록 유효성이나 Unicode 유효성을 보증하지 않으며 locale_deferred와 unicode_deferred를 true로 유지합니다. 잘못된 UTF-16 문자열도 레코드 선택 자체는 가능하고, 내용 검사에는 별도의 mluc_unicode.inspect를 사용합니다. 사용자에게 표시할 문자열의 검증·디코딩·렌더링 성공과 구분합니다.

## 책임·자원

문자열 저장 배치와 경계는 mluc.parse/at, 내용 검사는 mluc_unicode, 선택 정책은 mluc_selection이 소유합니다. 선택기는 문자열을 복사하거나 디코딩하지 않고 레코드 인덱스·선호 인덱스·선택 사유만 반환합니다. 호출자는 원본 View 수명을 유지하여 선택된 Record를 가져옵니다. 원본의 내용·순서·보류 플래그를 바꾸지 않습니다.

기본 한도는 레코드 100,000개·선호 32개이며 빈 문서의 조기 반환 전에도 검사합니다. 할당 없이 선호×레코드 수 이내로 순회하고 문자열 길이에는 비례하지 않습니다. 정상 파싱된 View와 불변 원본 계약은 원시 파서와 동일합니다. 선택기를 임의로 조작한 View의 재검증기로 쓰지 않습니다.

## 검증 기록

2026-09-08 최초 네이티브 테스트의 @memcpy 입력을 타입 없는 tuple로 작성해 컴파일 오류를 확인했습니다. 명시적 u8 배열로 수정한 뒤 Debug 네이티브 5/5 단계·458/458 테스트가 통과했습니다. 지역 일치가 뒤에 있는 경우, 중복 locale 동률, 지역 생략, 같은 언어 fallback, 다음 사용자 선호, 최종 첫 레코드, 빈 집합, 선호·레코드 한도를 검사합니다. 잘못된 UTF-16을 선택했다고 내용 유효성 플래그가 바뀌지 않음도 확인합니다.

테스트용 WASM mode167은 선호 목록과 mluc를 받아 선택 상태·인덱스·사유·보류 플래그만 반환합니다. 독립 JS는 후보 목록을 만들어 선호/일치 수준/원본 순위로 정렬하며 제품의 순차 탐색 구현을 재사용하지 않습니다. 4종 locale의 길이 0~4 목록 전체와 10종 선호 목록, 확장 stride·홀수 저장 시작·NUL 코드·대소문자·한도·잘림·손상 후 복구 입력을 정규 감사에 연결했습니다.

Debug WASM 직접 실행에서 정상 비교 3,425건·오류 거부 52건이 통과했습니다. macOS 기본 v4 프로파일 6개(ACESCG Linear, DCI(P3) RGB, Display P3, ITU-2020, ITU-709, ROMM RGB)의 desc/cprt 12개 태그를 읽기 전용으로 조사하고, 각각 선호 없음·enUS·enGB·koKR→enUS·미일치 선호의 5경우, 총 60건을 독립 선택 결과와 대조해 일치했습니다. 시스템 프로파일을 복제하지 않았고 이 표본에서 다중 locale 프로파일의 실제 표시를 검증했다는 뜻은 아닙니다. 실파일 수동 대조는 정규 감사 수에 합산하지 않습니다.

추가 적대적 직접 실행 67건도 통과했습니다. 레코드 100,000개·선호 32개에서 마지막 레코드/마지막 선호의 정확 일치, 마지막 선호의 같은 언어 fallback, 레코드 100,001개의 한도 거부를 확인했습니다. 64개 레코드 중 유일한 정확 일치 항목을 모든 위치로 옮겨도 해당 인덱스가 선택되었습니다. 선택 결과의 본문 복제는 없으며 이 수동 입력은 정규 감사 검사 수에 더하지 않습니다. 코드 검토에서는 빈 결과 전 한도 검사·앞선 언어 후보 때문에 뒤의 정확 지역 후보를 놓치지 않는 점·동률 첫 레코드 유지·문자열 디코더/등록부와의 책임 분리를 확인했습니다. 포맷·JS 구문·diff 공백 검사도 통과했습니다.

최초 Debug 전체 감사(`/tmp/hwpjs-icc-selection-Debug-first.log`)는 종료 코드 1, 17/20 단계로 끝났습니다. 실패 원인은 위에서 수정한 네이티브 fixture의 배열 타입 오류이며, 수정 전 컴파일이 실행된 결과였습니다. WASM 감사 자체는 정상 비교 3,425건·오류 거부 52건까지 통과했습니다. 수정 뒤 별도로 통과한 네이티브 검사와 합쳐 최초 전체 감사가 성공했다고 주장하지 않습니다.

수정본 세 모드 전체 감사를 Debug→ReleaseSafe→ReleaseFast 순차로 실행했습니다. 로그는 `/tmp/hwpjs-icc-selection-{Debug,ReleaseSafe,ReleaseFast}-final.log`입니다. 세 모드 모두 종료 코드 0, 각각 20/20 단계·네이티브 458/458·WASM 4,839,368개 검사로 통과했습니다. 신규 정상 비교 3,425건·오류 거부 52건도 세 모드에서 일치했습니다. 최종 적대적 코드 검토와 수동 경계 검사에서 이번 원시 코드 선택 정책의 추가 결함은 발견하지 못했습니다. 이는 ISO 등록/동의 코드 검증과 다국어 표시 기능의 완료를 뜻하지 않습니다.

## 후속 등록 검사의 조사 경계

[ISO 3166 공식 용어 설명](https://www.iso.org/glossary-for-iso-3166.html)은 공식 배정·예약·과거·사용자 할당 코드를 구분하며 UK를 예외 예약의 예로 듭니다. ICC §10.15의 공유 문자열 예시에도 en/UK가 있으므로 현행 공식 배정 목록에 없다는 이유만으로 모든 원시 mluc를 거부하는 정책을 만들지 않습니다. 등록 상태 진단, 판본/작성 시점 호환 정책, 동의 코드 비교를 구분해야 합니다. 현재의 원시 byte 비교는 이런 동등성을 구현한 것이 아닙니다.

2026-09-08 [Library of Congress 다운로드 안내](https://www.loc.gov/standards/iso639-2/ascii_8bits.html)와 해당 UTF-8 목록을 웹 조회했으나 403이 반환됐으며 Node의 일반 HTTP 요청도 403이었습니다. ISO OBP는 정적 조회에서 JavaScript 필요 안내만 반환했습니다. 이 조회로 새 등록 테이블을 얻었다고 간주하지 않았고 제품에 데이터나 의존성을 추가하지 않았습니다. 다른 공식 접근 경로 확인과 등록 상태·동의 코드 데이터 확보는 후속 작업입니다.
