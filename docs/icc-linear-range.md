# ICC 선형 분기의 정확한 출력 범위

## 계약과 책임

`linear_range.build(linear)`는 원본 입력 구간에서 `clip((slope*x+offset)/65536)`이 실제로 만드는 전체 출력 범위를 u256 유리수 구간으로 반환합니다. 입력은 기존 parametric_segments.Linear이며 입력 구간 검증은 공통 linear_clip.partition이 수행합니다. 기울기가 음수이면 출력 끝점 순서와 포함 여부가 반대로 바뀝니다.

입력 구간은 비어 있지 않고 함수는 연속이므로 출력 범위도 연결된 비어 있지 않은 구간입니다. 이 사실에 근거해 공통 클리핑 분할에서 얻은 조각들의 출력 경계를 합칩니다. 임의의 불연속 출력 구간을 hull로 합쳐 틈을 메우는 API는 아닙니다.

0/1 상수 조각과 기울기 0의 조각은 입력 끝점이 열려 있어도 실제로 상수값을 만드므로 닫힌 출력 단일점입니다. 비상수 affine 조각은 입력 끝점의 포함 여부를 유지하되 감소 방향이면 교환합니다. 같은 출력 경계의 포함 여부는 OR로 합칩니다. 클리핑 경계 계산·분할·조각 분류를 새로 복제하지 않고 linear_clip을 재사용하며 affine_value가 정확한 식 계산을 소유합니다. affine 조각의 끝값이 [0,1] 밖이면 내부 불변식 오류로 반환합니다.

코어에는 할당·파일 접근·부동소수점 계산이 없습니다. 출력 분모는 65536과 u64 입력 분모의 곱을 보존하므로 u64보다 클 수 있으며 u256 표현으로 전달합니다. 입력/출력 구간 타입·검증은 unit_interval, 최근접 값 선택은 rational_range_nearest가 소유합니다.

## 포함 여부의 반례

입력 (0,1), 함수 clip(2x−1/2)의 출력은 닫힌 [0,1]입니다. 실제 내부 구간에서 0과 1을 만들기 때문에 입력 flags를 그대로 출력에 복사하면 잘못됩니다. 반면 같은 입력에서 f(x)=x이면 출력 (0,1)은 열려 있습니다. 따라서 출력 끝점을 무조건 닫아도 안 됩니다.

입력 [0,1), 함수 3/4−x/2의 출력은 (1/4,3/4]입니다. 입력의 시작 포함 여부가 출력의 상한에 대응합니다. 상수 함수는 입력이 열려 있더라도 값 하나를 실제로 만들므로 출력은 닫힌 단일점입니다.

## 검증 진행

구현 중 감소 방향의 끝점 교환을 구조체 자기 재대입으로 작성했을 때 신규 테스트 2개가 EmptyIccInterval로 실패했습니다. 끝점 값과 포함 플래그를 명시적인 swap으로 교환하도록 수정한 뒤 같은 테스트 4개가 모두 통과했습니다. 이력은 신규 구현에서 잡은 결함이며 기존 레거시 버그를 발견했다는 뜻이 아닙니다.

전체 네이티브 570/570가 통과했습니다. 신규 테스트는 열린 입력의 클리핑 포화, 정확히 0/1에 닿는 열린 끝점, 감소 방향 포함 정보, 상수 이미지, u64를 넘는 출력 분모, 단일점·잘못된 입력, 최근접 출력 연결을 포함합니다.

테스트 mode204는 start/end n/d u64 BE, flags u32 BE, slope/offset i32 BE의 44바이트를 받습니다. 출력은 기존 공통 136바이트 WideInterval wire를 재사용하며 성공 시 항상 구간이 있습니다. 길이·flags·자원 한도를 검사하고 결과를 계산한 후 버퍼를 할당·전체 초기화합니다. 제품 JS API는 변경하지 않았습니다.

독립 JS 기준은 원래 식의 양 끝값을 BigInt로 계산하고 순서를 정한 뒤 클리핑합니다. 출력 상수 여부와 엄격한 포화 부등식으로 포함 여부를 판단하므로 제품의 분할/조각 합치기 알고리즘을 기대값 생성에 사용하지 않습니다. 기울기/offset 각 7종 × 입력 구간 6종 × flags 4종, 최대 u64 분모, 잘못된 구간·잘림·과잉·flags·한도·오류 후 복구를 검사합니다. 각 정상 출력 범위를 mode203에 넘겨 목표 0,1,1/2,3/5의 최근접 결과도 독립 출력 범위 기준과 비교합니다.

직접 Debug WASM 결과는 ranges=895/nearestChecks=3580/rejected=345로 통과했습니다. 세 수치는 별도 호출이므로 신규 호출 합계는 4,820입니다. 출력 flags를 모두 닫기, 비상수 출력에 입력 flags를 그대로 복사하기, 성공 범위를 빈 wire로 바꾸는 세 변형을 각각 ERR_ASSERTION으로 검출했습니다. 입력 flags 복사는 최초에 열린 단일점이라는 잘못된 출력 형식으로도 걸렸지만, 최종 변형에서는 상수 출력을 제외해 유효한 비상수 구간에서 의미 오류를 검출했습니다. 제품 파일에는 변형을 남기지 않았습니다. 전체 세 모드 감사는 진행 중입니다.

## 실제 ICC 하위 분기 대조

시스템 Display P3·ITU-2020·ITU-709·ROMM RGB의 RGB TRC type3 태그 12개를 읽기 전용으로 검사했습니다. 양의 c, 0<d<65536, 0<c*d<65536²를 확인한 뒤 하위 입력 [0,d/65536)의 독립 기대 출력 [0,c*d/65536²)와 mode204 결과를 정확한 BigInt 분수로 비교했습니다. 12개 범위가 일치했고 각 하위 범위만 mode203에 넘긴 목표 1의 최근접 판정 12건은 모두 unattained였습니다. 상위 분기를 포함한 전체 곡선의 최근접 결과라는 뜻은 아니며 이 수동 24호출은 정규 audit에 합산하지 않습니다.

## 최종 감사와 적대적 재검토

Debug·ReleaseSafe·ReleaseFast 전체 audit가 각각 종료 코드 0, 20/20 단계, 네이티브 570/570, WASM checks=6,566,130으로 통과했습니다. 신규 4,820건이 이전 6,561,310건에 추가됐습니다. 각 모드 신규 결과는 ranges=895/nearestChecks=3580/rejected=345입니다. 로그는 `/tmp/hwpjs-icc-linear-range-{Debug,ReleaseSafe,ReleaseFast}.log`입니다. 앞의 진행 중 문장은 이력이며 최종 결과는 이 절을 기준으로 합니다.

ReleaseSafe·ReleaseFast 산출물 직접 실행도 같은 신규 수치로 통과했고 출력 끝점을 강제로 닫는 변형을 각각 검출했습니다. 변경 Zig 포맷·JS 문법·diff 공백·문서 로컬 링크 1개를 확인했습니다.

최종 재검토에서 공유 clipping partition 재사용, 비어 있지 않은 연속 이미지에 한정한 경계 합치기, 상수 조각의 닫힌 출력, 감소 방향의 값·포함 플래그 교환, 같은 경계의 OR 병합, 넓은 분모 보존, 입력 선행 검증과 결과 초기화를 확인했습니다. 초기 끝점 교환 결함 수정 후 이 범위에서 추가 결함은 발견하지 않았습니다.

## 남은 범위

이 모듈은 선형 분기만 다룹니다. 파라메트릭 거듭제곱 분기의 기호적 출력 범위, 전체 곡선의 범위 조립, 기호적 거리 비교와 F.1(b)→F.1(a) 연결은 미완료입니다. 실제 HWP 문서 렌더링이나 전체 ICC 역변환 완료로 해석하지 않습니다.
