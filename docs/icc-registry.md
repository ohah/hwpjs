# ICC 등록부 대조 작업

공식 CSV 구조 검사·식별자 추출·제한된 다운로드와 오프라인 스냅샷을 구현했습니다. 후속 [Zig 조회·헤더 대조](icc-registry-lookup.md)를 별도 API로 추가했으며 기존 `registry_fields_deferred`는 그대로 유지됩니다. 아래 단계별 기록은 당시 결과로 읽습니다.

## 출처와 분리

[ICC 등록부 안내](https://registry.color.org/)는 CMM·제조사·장치·태그·타입 등록부를 구분합니다. 헤더의 제조사/장치 대조에는 장치 ID뿐 아니라 연결된 제조사도 필요합니다. 이 작업은 일반 프로파일 다운로드 목록과 별개입니다.

- `tools/icc-registry/csv.mjs`: BOM·인용·이스케이프·줄바꿈과 크기/행/열/필드 한도를 검사합니다. 기본 최대 입력 4 Mi UTF-16 코드 유닛, 행 100,000, 열 32, 필드 1 Mi 코드 유닛입니다. UTF-8 디코딩과 다운로드 바이트 한도는 호출자의 책임입니다.
- `inspect.mjs`: 종류별 정확한 열 스키마, 행 너비, 식별자의 hex/ASCII 일치, 중복을 확인합니다. 출력은 숫자 식별자 또는 제조사–장치 숫자 쌍, 원본 논리 행 번호·오류 이유·해당 ID 열의 원문입니다. 이름·연락처·주소·설명 열은 출력/저장하지 않습니다. 예상한 식별자 오류만 격리하며 다른 예외는 전체 실패로 전파합니다.
- 짧은 ASCII는 명세의 공백 패딩과 대조하지만 대소문자를 바꾸거나 hex와 ASCII 불일치를 자동 보정하지 않습니다. 헤더/행 너비가 틀리면 전체 실패, ID 오류는 해당 행을 격리합니다. `complete`는 이 추출에서 격리된 행이 없다는 뜻이며 역사적 등록부 완전성 인증이 아닙니다.
- 중복 장치 여부는 제조사와 장치의 쌍으로 검사합니다. 같은 장치 ID가 서로 다른 제조사에 속할 수 있으므로 장치 ID만으로 중복 제거하지 않습니다.

## 2026-09-07 실측

공식 CSV를 UTF-8 fatal 디코딩하여 메모리에서만 검사했습니다. CSV 원문은 저장소에 추가하지 않았습니다.

| CSV | 바이트 | 데이터 행 | 추출 항목 | 격리 행 |
|---|---:|---:|---:|---:|
| [CMM](https://registry.color.org/cmm-signatures/cmm-signatures.csv) | 1797 | 31 | 31 | 0 |
| [제조사](https://registry.color.org/manufacturer-signatures/manufacturer-signatures.csv) | 36569 | 281 | 278 | 3 |
| [장치](https://registry.color.org/device-signatures/device-signatures.csv) | 341891 | 3071 | 3027 | 44 |

제조사의 논리 행 208/241/278은 각각 `LNV-4C4E5600`, `FP-46502A2A`, `DNP-444E502E`로 공백 패딩 ASCII와 hex가 일치하지 않았습니다. 장치 격리 행에는 `6C9C-3643393` 같은 짧은 hex, `735F-32434331` 같은 불일치, 그리고 제조사 ID 불일치가 포함됩니다. 추출에 성공한 장치 쌍의 제조사는 모두 추출 제조사 집합에서 발견했습니다. 이 결과만으로 격리 행을 오타라고 확정하거나 삭제하지 않습니다.

원문 SHA-256:

```text
cmm          6684cc01ec77039349bcb714b5936879b86ae77ccd7b3f63aa11788bcc1833ff
manufacturer 21e2fa1aa586631ab111cc7972772fee18537005c52afd1805b1243fe7c4282f
device       8da5be386f4a514c0604e463a9c7adb8b67d1b34f898ae064b798dcaefa0b86f
```

따라서 런타임에서는 미지정·등록 확인·불확실/미대조·스냅샷 내 미발견을 구분해야 합니다. 이 불완전한 추출 목록에서 찾지 못했다는 이유만으로 영구적인 미등록이나 잘못된 헤더로 확정하지 않습니다. 불확실한 행의 원본 식별 근거와 갱신 정책을 스냅샷 계약에 포함하는 작업이 남아 있습니다.

## 적대적 검증

초기 `node --test tools/icc-registry/csv.test.mjs`는 6/6 통과했습니다. 빈 입력/필드·BOM·CRLF·인용부호·인용 내부 개행·독립 serializer 256회 왕복, 잘못된 인용/종결/NUL, 정확한 한도, 스키마/행 너비, 연락처 배제, 중복과 제조사–장치 쌍, 실제 불일치 형태를 확인했습니다. 재검토에서 입력 타입과 스키마 객체의 상속 프로퍼티 경계를 보강했습니다. 이 시점에는 정규 audit 연결 전이었으며 이후 결과는 조회 계약의 검증 기록을 참조합니다.

## 식별자 전용 스냅샷

후속 최종 검증과 런타임 조회 범위는 [조회 계약](icc-registry-lookup.md)에 기록합니다. 아래 6/11개 테스트 및 미연결 언급은 해당 단계 당시의 기록입니다.

`src/image/icc/registry/source.json`은 CSV 원문 대신 식별자·문제 행의 ID 열·출처 URL·원문 바이트 길이/해시·추출 개수를 담습니다. 2026-09-07 새 다운로드에서 위 세 해시와 개수가 동일함을 확인해 생성했습니다. 연락처 열은 편입하지 않았습니다. `schemaVersion`은 현재 1이며 등록부 시점은 원문 해시로 식별합니다. 현재 시점의 영구적인 등록 여부를 인증하는 자료는 아닙니다.

`download.fetchSnapshot`은 고정된 공식 URL 3개를 읽고 redirect를 거부합니다. 요청별 timeout 기본 20초, 수신 중 누적 바이트 기본 4 MiB 한도를 적용합니다. 초과·HTTP 실패·잘못된 UTF-8·CSV 실패에는 부분 결과를 반환하지 않으며 다운로드를 취소/정리합니다. 함수는 파일을 쓰지 않습니다. 이번 스냅샷도 결과 검토 후 별도 파일 변경으로 반영했습니다.

`snapshot.validateSnapshot`은 허용 필드·URL·해시 표기·개수·정렬/고유성·ID 범위·문제 행 번호와 이유·제조사 참조 누락 목록을 오프라인 검사합니다. CSV 원문을 저장하지 않으므로 이 검사만으로 원문 해시나 추출의 재현성을 증명하지는 않습니다. 실제 다운로드 대조와 구분합니다. 허용하지 않은 연락처 필드가 추가되면 거부하지만, 손상된 원본 ID 열의 내용까지 임의로 보정/삭제하지는 않습니다.

`node --test tools/icc-registry/csv.test.mjs tools/icc-registry/download.test.mjs tools/icc-registry/snapshot.test.mjs`는 보강 후 11/11 통과했습니다. 수신 도중 한도 초과 시 취소와 lock 해제, 빈 응답/HTTP/UTF-8 실패, 중간 소스 실패, 스냅샷 변형도 검사했습니다. 초기 제조사 관계 테스트는 마지막 항목이 참조된다고 잘못 가정하여 실패했고, 실제 장치가 참조하는 부모를 제거하도록 수정했습니다. 이후 정규 audit 연결·파생 Zig 테이블·조회 API는 조회 계약에 기록했습니다.

## 다운로드 조각 메모리 보강

2026-09-07 최종 재검토에서 100,000바이트를 1바이트씩 받는 스트림을 재현했습니다. 기존 조각 배열은 데이터 크기 외에 조각별 Buffer/배열 항목을 계속 보관했습니다. `node --expose-gc`에서 시작 직전 GC 후 4,096조각마다 heapUsed를 표본 측정했을 때 관측 증가가 30,087,160바이트였습니다.

조각 배열 대신 입력 한도 안에서 배수 성장하는 연속 버퍼로 바꾸고 빈 조각을 보관하지 않도록 수정했습니다. 같은 조건의 수정 후 관측 증가는 4,622,632바이트였습니다. 이는 GC/Response 실행 비용을 포함한 한 번의 표본 관측이며 고정 메모리 보증이나 지속 성능 기준이 아닙니다. 버퍼의 쓰이지 않은 부분은 0으로 초기화하고 반환 뷰는 수신 길이까지만 노출합니다. 100,000개의 조각과 중간 빈 조각, 실제 바이트 전체 비교를 회귀 테스트에 추가했습니다. 정규 `icc-registry-audit`는 14/14 테스트를 통과했습니다.
