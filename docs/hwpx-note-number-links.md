# HWPX 각주·미주 안의 번호 컨트롤 관계

`Document.inspectNoteNumberLinks()`와 `XmlTrees.inspectNoteNumberLinks()`는 [각주·미주 본문](hwpx-note-bodies.md)과 [번호 컨트롤](hwpx-number-controls.md)의 기존 보고서를 **같은 선택 section 트리의 요소 인덱스**로 연결합니다. `Document.inspectKnown().note_number_links`도 같은 관계 검사기를 재사용합니다. 이 검사기는 `hp:autoNum`의 가장 가까운 상위 `hp:footNote` 또는 `hp:endNote`를 찾고, 주석의 직접 `hp:subList` 안에 있는지와 `numType`의 `FOOTNOTE`/`ENDNOTE` 일치 여부, 기존 파서가 읽은 `num` 정수 원값을 보고합니다. 외부 namespace의 동명 주석을 소유자로 삼지 않고, 중첩 주석은 가까운 주석에 귀속합니다.

`note_number_links.zig`는 부모 관계와 링크 수·한도를 소유합니다. 주석/번호 속성 어휘나 XML 파싱은 재구현하지 않습니다. 입력 보고서는 같은 트리에서 만들어야 하며, section 개수·요소 종류/위치가 모순되면 오류를 반환합니다. 보고서에는 정수·인덱스·Boolean만 복사하므로 원본 트리와 두 입력 보고서를 해제한 뒤에도 유효하고, 마지막에 `deinit()`합니다. `numType` 부재는 불일치와 구분합니다. 번호 컨트롤이 없는 주석이나 주석 밖의 `autoNum`도 개수로 남깁니다. 이 관계는 **포함 관계**일 뿐, 그 컨트롤을 화면에 표시되는 유일한 주석 번호로 확정하지 않습니다. 다중 컨트롤·누락·서식·번호 증가/재시작·실제 쪽 배치·편집·저장·무손실 왕복은 해석하지 않습니다.

공식 한컴 [NoteType](https://github.com/hancom-io/hwpx-owpml-model/blob/1453388472c703a4b299a0834f425cdac16644b9/OWPML/Class/Para/NoteType.cpp)은 직접 `subList`를, [AutoNumNewNumType](https://github.com/hancom-io/hwpx-owpml-model/blob/1453388472c703a4b299a0834f425cdac16644b9/OWPML/Class/Para/AutoNumNewNumType.cpp)은 `num`과 `numType`을 모델링합니다. 그러나 두 모델의 존재만으로 화면 표시 번호 계산 규칙이 정해지지는 않습니다. 따라서 원값과 구조만 진단합니다.

독립 `tools/hwpx-note-number-links-diff.py`는 ZIP/OPF/ElementTree로 section의 주석·컨트롤과 부모 관계를 다시 읽고, `src/hwpx_note_number_links_survey.zig`가 반환한 파일별 링크 인덱스·종류·숫자·진단 해시와 대조합니다. 로컬 484개 후보 중 ZIP 종료 레코드 거부 6개·암호화 2개를 제외한 476개 파일이 파일별로 일치했습니다. 주석 안 `autoNum` 연결 1,216건, 종류 불일치 0건, 직접 목록 밖 연결 0건, 컨트롤이 없는 주석 8건을 관측했습니다. 같은 corpus의 주석 본문 총수는 1,219건이므로 일부 주석에 둘 이상의 `autoNum`이 있다는 의미이지, 각주/미주 번호가 유일하다는 근거가 아닙니다. 이 수치는 fixture 분포이며 다른 버전의 필수 규칙이 아닙니다.

합성 적대적 검증은 (1) 외부 namespace·주석 밖 컨트롤·중첩 주석의 가장 가까운 소유자와 section별 동일 요소 인덱스, (2) 직접 목록 안팎·누락/빈/다른 `numType`의 구분, (3) 음수 `num`의 보존과 표시 번호 비추론, (4) 정확한 링크 개수 한도·모든 할당 실패 및 모순된 입력 보고서의 오류, (5) 독립 오라클의 변이 검출·파일별 corpus·실파일 단독/known 경로로 나눕니다. Oracle의 열 가지 결정적 변이를 일반 Python 및 `-O`에서 감지했습니다. 전체 문서 의미 모델이나 화면 결과를 검증했다는 주장이 아닙니다.

`zig test src/root.zig --test-filter 'HWPX note number links'`의 최종 테스트 소스는 Debug·ReleaseSafe·ReleaseFast에서 각각 7/7 통과했습니다. 두 실파일의 단독 API와 `inspectKnown()` 결과는 일치했고, 기존 HWPX known 실파일 8개 ReleaseFast shard도 모두 통과했습니다. `python3 tools/hwpx-note-number-links-diff.py`의 허용 파일 476개 파일별 해시·거부/암호화 파일 집합은 독립 XML 결과와 일치했습니다. `zig build -Doptimize=ReleaseSafe`, 대상 Zig 파일의 `zig fmt --check`, `git diff --check`도 통과했습니다. 전체 Debug `zig build test --summary all`은 종료 코드 0, 5/5 단계, 2,639/2,639 테스트 통과였습니다. 이 전체 실행이 시작된 뒤 **테스트만** 다중 section 인덱스 격리 사례 하나를 추가했으므로, 그 추가분을 포함한 전용 테스트 7/7을 세 모드에서 별도 재실행했습니다. 전체 빌드 출력의 `failed command: .../test --cache-dir=... --listen=-`는 후속 [Zig stderr 독립 재현](zig-test-stderr.md)으로 설명됐습니다. 이 문구는 최종 성공 상태나 문서 의미 정확성을 대체하지 않습니다.

2026-09-27 재검증: 공식 한컴 AutoNumNewNumType의 `num`·`numType` 필드와 기존 `note_number_links.zig`의 포함 관계만 확인했습니다. `HWPX note` 필터는 Debug·ReleaseSafe·ReleaseFast에서 각각 27/27, 단독/known 연결은 1/1 통과했습니다. 독립 번호 관계 오라클은 일반·`-O`의 변이 10개를 검출했고, 전체 실행에서 허용 476개·ZIP 거부 6개·암호화 2개, 연결 1,216개·종류 불일치 0개·직접 목록 밖 0개·컨트롤 없는 주석 8개가 파일별로 일치했습니다. 같은 코드·corpus의 known-inspections ReleaseFast 8개 shard도 각각 통과했습니다. 표시 번호 계산이나 유일성은 검증하지 않습니다.
