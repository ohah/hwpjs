# 글자 모양·문단 모양 대화상자

현재 공용 글자 모양 창은 크기·굵게·기울임, 문단 모양 창은 여섯 정렬 값을 지원합니다. 단위 검사와 Noori HWP5/HWPX 대표 운영 경로의 적용·undo·저장·재열기 검증 범위를 구분합니다. 기존 API 지원, 이 부분 대화상자 구현, 전체 글자·문단 모양 완성은 서로 다른 상태입니다.

이 문서는 대화상자의 표시·초안·적용 경계를 설명합니다. 공개 API 목록은 [Headless API 범위](headless-api-coverage.md), 형식별 원본 보호와 전체 완료 기준은 [편집기 완료 조건](fixture-editor-completion.md)을 따릅니다.

## 현재 제공되는 기능

다음은 기존 API와 현재 창의 범위를 구분한 목록입니다. 크기·굵게·기울임과 정렬만 현재 창에서 적용하며, 나머지 API의 존재가 창 연결을 뜻하지는 않습니다. 원본 선택, capability, 문서 형식에 따라 거부될 수 있습니다.

| 항목 | 기존 API와 도구 | 대화상자와 구분할 점 |
| --- | --- | --- |
| 글자 크기·굵게·기울임 | `SET_CHARACTER_PROPERTIES_COMMAND` | 같은 선택의 세 속성을 한 명령으로 적용할 수 있습니다. 크기는 1/100pt 단위입니다. |
| 밑줄 | `SET_CHARACTER_UNDERLINE_COMMAND` | 별도 명령입니다. Boolean 조회값만으로 정확한 위치나 선 모양을 추정하지 않습니다. |
| 취소선 사용 | `SET_CHARACTER_STRIKE_COMMAND` | Boolean on/off입니다. 선 모양과 색 전체를 편집하는 명령은 아닙니다. |
| 문단 정렬 | `SET_PARAGRAPH_ALIGNMENT_COMMAND` | 기존 typed 정렬 명령입니다. 전체 문단 속성을 한 번에 바꾸는 API는 아닙니다. |
| 글자색 | `SET_CHARACTER_TEXT_COLOR_COMMAND` | 독립 글자색 창이 typed 조회·명령에 연결되어 있습니다. 공용 글자 모양 창의 크기·굵게·기울임 통합 적용과는 별개입니다. `#RRGGBB`와 원본 바인딩·권한 검증 및 Native 색 정책을 따릅니다. |
| 문단 여백·줄 간격 | 개별 Native/facade 기반 | 원본 단위와 대상 제약이 있습니다. 대화상자의 통합 적용 완료를 뜻하지 않습니다. |

문자 서식은 검증된 비어 있지 않은 원본 선택을 대상으로 합니다. 캐럿에서 다음 입력의 서식을 바꾸는 기능으로 해석하지 않습니다. 문단 정렬의 캐럿 대상은 기존 문단 선택 검사를 따릅니다. readonly, 오래된 선택, 불명확한 원본 소속을 UI에서 우회하지 않습니다.

저장소 소스, 격리 후보와 실제 게시 상태를 구분합니다. 독립 글자색 창은 조회·적용·취소·이력을 지원하지만 공용 글자 모양 창의 전체 원자 적용은 미완료입니다. [원본 색상 정책](source-color-policy.md)을 함께 확인합니다.

독립 글자색 창의 기존 strikethrough 양형식 증거와 신규 Noori HWP5/HWPX 운영 증거는 별개입니다. 공개 fd5·비공개 44709 시도는 API 진입점 회귀로 복구했으며, 수정 후보는 공개 076da·비공개 5bade입니다. 비공개 운영에서는 Noori 두 문서의 API 12단계, 색 적용·undo·redo·저장·재열기, 8자 입력 뒤 trusted CDP 반복 undo/redo와 독립 CFB/XML 검사를 확인했습니다. 공개 게시 검증은 별도이며 물리 OS 키 반복·IME·외부 한컴 신규 저장·전체 문서와 조판의 완료를 뜻하지 않습니다.

## 현재 첫 대화상자

첫 글자 모양 창은 크기·굵게·기울임의 변경분만 기존 명령 한 번으로 적용하는 범위입니다. 첫 문단 모양 창은 정렬을 기존 명령 한 번으로 적용하는 범위입니다. 기본·확장 탭과 나머지 항목의 지원 이유를 표시하더라도, 미연결 항목을 적용됐다고 안내하지 않습니다.

글꼴·음영·일부 효과의 개별 Native/facade 경로는 현재 공용 창과 별개입니다. 이 첫 범위로 전체 글자·문단 모양의 목표를 대체하지 않습니다. 글꼴, 언어별 설정, 정확한 밑줄 위치·모양·색, 음영·효과, 여백·간격, 테두리·배경 등은 각각 조회·쓰기·원자 적용 계약이 필요합니다.

창을 열 때 선택과 상태를 함께 캡처합니다. 초안을 자동으로 다른 선택에 옮기지 않습니다. 기본 정책은 확인 시 고정한 대상에 적용하는 captured-target입니다. 새 복합 적용안의 `selectionVersion`은 선택 사항입니다. 값을 제공한 경우에만 해당 capability를 확인하고 실행 직전 선택 검사를 요구하는 방향입니다. 값을 생략한 기존 경로까지 strict 검사로 바꾸거나, 모든 대기열 경합이 차단됐다고 설명하지 않습니다.

## 값, 혼합값, 초안

공식 [CharShape](https://developer.hancom.com/en-us/webhwp/devguide/hwpctrl/properties/charshape)와 [ParaShape](https://developer.hancom.com/webhwp/devguide/hwpctrl/properties/parashape)는 선택 범위의 속성을 조회하며, 부분적으로만 다른 속성은 반환 항목에서 제외하고 설정 대상에 있는 항목만 반영하는 방식을 설명합니다. [GetDefault](https://developer.hancom.com/webhwp/devguide/action/methods/getdefault)는 현재 상태에 맞는 액션 인수를 얻는 API입니다.

우리 UI는 알려진 값, 혼합값, 알 수 없는 값, 사용할 수 없는 값을 구분해야 합니다. 사용자가 바꾸지 않은 초안은 별도 상태입니다. 빈칸이나 unknown을 false·0·기본 글꼴로 바꾸어 보내지 않습니다. 미수정 속성은 요청에서 제외하고, 명시적 해제나 0은 해당 필드의 검증을 거쳐 실제 변경으로 처리합니다.

빈 참고 문서에서 관측한 글자 크기나 줄 간격은 모든 문서의 기본값이 아닙니다. 읽을 수 없는 원본 필드에 임의 기본값을 채워 쓰지 않습니다. 단위 변환도 글자 크기와 문단 여백을 같은 규칙으로 묶지 않고 기존 Native 계약을 확인합니다.

## 남은 계약

| 구분 | 필요한 작업 | 완료로 보면 안 되는 근거 |
| --- | --- | --- |
| 원자 적용 | 여러 글자·문단 속성의 검증과 변경을 한 Native 계획, 한 commit, 한 undo로 연결 | 여러 setter의 순차 호출, `editor.update()` 수집, 실패 후 자동 undo |
| 조회 | 필드별 값·혼합·unknown·지원 이유, 단위·enum, 원본 존재와 writable을 같은 대상에서 관측 | Boolean에서 밑줄 위치 추정, UI 초안이나 캐시를 문서의 정답으로 사용 |
| 선택 검사 | `selectionVersion`을 제공한 요청에서 capability에 따라 문서·선택·소속을 실행 직전에 확인하는 fence | 기본 captured-target이나 기존 명령도 strict 검사한다고 주장 |
| 쓰기 | 언어별 metrics, 모든 선 모양, 글자·문단 테두리/배경, 줄 격자 등의 대상별 writer와 보존 검증 | parser, 기존 shape ID, Canvas 보기 옵션, 일부 outline/shade setter의 존재 |

복합 적용을 지원하지 않는 엔진에서는 이를 명시적으로 거부해야 합니다. 기존 단일 명령으로 몰래 분해해 전체 성공처럼 보이면 안 됩니다. 포맷 적용 capability와 이력 정책 버전은 서로 독립입니다.

`editor.update()`는 명령을 모아 순서대로 실행합니다. 뒤 명령이 실패해도 앞에서 반영된 변경은 남을 수 있습니다. 같은 옛 target은 첫 변경 뒤 오래된 대상이 될 수도 있습니다. 따라서 전체 대화상자의 원자 적용을 대신하지 않습니다.

## 공통 창의 box-sizing과 찾기 입력 경계

2026-10-26, 소스 수정 `f711ad56`의 독립 검증입니다. 찾기 창이 `.hwp-demo` 밖의 sibling으로 생성되면 shell의 후손 전용 `border-box` 규칙이 적용되지 않았습니다. 실제 Chromium에서 input의 computed `box-sizing: content-box`와 `width:100%` 바깥으로 더해진 패딩·테두리를 확인했고, 520px 폭에서는 다음 찾기 버튼을 2px 침범했습니다. 공통 `.hwp-dialog-layer` 자체·후손·후손 가상 요소에만 `border-box`를 적용하며 전역 reset은 추가하지 않습니다.

찾기 input의 border와 `outline-offset:2px`는 떨어진 윤곽으로 보였습니다. CSS 선언이 outline 두 개를 그린다는 뜻은 아닙니다. 입력 포커스의 테두리를 표시하고 `:focus-visible`의 2px outline을 offset0으로 유지합니다. 실제 Chromium에서 마우스로 누른 text input도 `:focus-visible`이므로 이를 일괄 숨기지 않습니다. 버튼·다른 서식 컨트롤의 기존 키보드 포커스 표시는 유지합니다.

## 취소, 오류, 포커스

접수 전 취소·닫기·Escape는 서식 명령을 보내지 않는 계약입니다. 확인을 접수한 뒤 창을 닫는 것은 Native 변경 취소가 아닙니다. pending 중 중복 적용을 막고 결과를 받을 수명은 유지해야 합니다.

실패하면 원래 오류와 초안을 보존합니다. 이미 반영됐지만 재관측이 필요한 결과는 편집을 다시 보내지 않습니다. 닫은 뒤에는 같은 문서의 최신 유효한 선택일 때만 호스트 포커스를 돌려줍니다. 이전 선택을 강제로 복원하거나 새 문서의 포커스를 빼앗지 않습니다.

Tab, 조합 입력, Enter/Escape, 창 크기 변경, readonly·혼합 선택, 적용 후 undo/redo, 독립 CFB/XML 저장과 재열기는 각각 확인할 게이트입니다. 기존 dialog 관측이나 다른 기능의 테스트 통과를 새 대화상자의 완료 근거로 합산하지 않습니다.

## 언어별 글꼴 이름 창 후보

공용 글자 모양 창과 별도로 일곱 언어 중 하나와 이름 하나를 선택하여 `SET_CHARACTER_FONT_NAME_COMMAND` 한 번으로 적용하는 후보입니다. 문서의 언어별 이름 목록과 single·mixed·unknown·원본 이름 미확인을 구분합니다. 이름을 trim하거나 Unicode 정규화하지 않으며, 정확히 같은 single 값과 미수정 초안만 no-op입니다. readonly·빈 캐럿·오래된 선택은 기존 공개 API의 거부 이유를 표시합니다. 여러 언어 또는 모든 글자 속성의 원자 통합 적용과 다음 입력 서식 지정은 완료 범위가 아닙니다.

격리된 새 글꼴 SDK와 cb48 Native를 사용해 Noori HWP5/HWPX의 Vanilla·React·Svelte 6경로에서 적용·undo 원본 바이트 일치·redo·저장·재열기와 독립 CFB/XML 기대값 및 잘못된 기대값 거부를 확인했습니다. 이는 저장된 이름 검증이며 실제 OS 글꼴 face 사용, 외부 한컴 렌더링 동치, 기본 타이핑 지연 해결이나 운영 배포 완료의 근거가 아닙니다. committed-refresh-required는 error가 있어도 적용 완료로 취급하여 같은 초안을 재접수하지 않습니다. 단위 검증은 [개발·검증 명령](development-commands.md#font-name-ui-tests)을 따릅니다.

## 문단 원자 서식 창 후보

새 문단 모양 창은 열 때만 공개 capability와 명시 field query를 각각 한 번 호출하고, 같은 문서·선택 상태에서 변경분을 `APPLY_FORMATTING_PATCH_COMMAND` 한 번으로 전달합니다. 보통 입력과 presentation 갱신에는 이 조회를 추가하지 않습니다. 공식 문단 선택 생성 경로를 사용하며 선택이 바뀌거나 문서가 교체되면 이전 초안을 적용하지 않습니다. 취소·변경 없음은 명령을 보내지 않고, 적용 뒤 관측 복구가 필요하면 재접수를 막습니다.

조회 범위는 정렬, 다섯 여백, 줄 간격 종류·값, 줄 격자, 테두리 연결, 테두리, 배경의 12개 필드입니다. 편집 가능 여부는 필드별 capability와 관측 단위에 따릅니다. HWP5 원본 단위를 임의로 pt로 바꾸지 않으며, 알 수 없는 값·혼합값·미지원값에 기본값을 채우지 않습니다. 초기 구현에서 줄 간격 종류 전환과 테두리·배경 상세 편집을 후속 범위로 남겼습니다. 종류 전환 후속의 실제 확인 범위와 HWP5 단위 제한은 아래 기록을 따릅니다. 전체 문단 모양 완성을 뜻하지 않습니다.

현재 SDK export가 없으면 기존 정렬 창을 유지합니다. 원자 서식 ABI가 없는 cb48에서도 기존 창으로 돌아가며 새 query·patch 성공으로 세지 않습니다. 읽기 전용은 조회와 쓰기 권한을 구분해 표시합니다. 모의 검사 35개는 선택 변경·늦은 응답·dispose·IME·단일 명령·commit 후 관측 오류를 검사하며 실제 Native 이력·저장 증거를 대신하지 않습니다. 정규 명령은 [개발·검증 명령](development-commands.md#문단-원자-서식-창-단위-검증)을 따릅니다. 현재 후보 검증과 운영 배포는 별개입니다.

### 줄 간격 종류 변경과 형식별 원본 단위

2026-10-28 격리 r2는 HWPX의 글자에 따라·고정 값·여백만 지정·최소 종류를 명시 값과 한 원자 patch로 연결한다. 같은 관측의 종류·단위 및 두 필드 쓰기 권한을 검사하고, 종류를 바꾸면 이전 숫자를 지워 새 값을 직접 입력하게 한다. 다른 종류에서 원시 정수가 원본과 같더라도 명시 값을 보존한다. 알 수 없는 단위·혼합 종류·지원 밖 enum·읽기 전용·낡은 선택을 쓰기 가능으로 추정하지 않는다.

HWP5는 비례 간격 이외 Native 질의가 `hwp5-source-unit`을 반환한다. `HWPUNIT`으로 기대한 최초 실제검사의 세 실패를 보존한다. 짝수 원값은 거리의 두 배이며 홀수에는 상대 기준이 필요하므로, 원값을 HWPUNIT 또는 pt로 단순 환산하지 않는다. 이 후보에서는 HWP5 종류 전환을 이유와 함께 비활성화하고 기존 백분율 값 편집만 유지한다. 안전한 내부 변환기는 별도 후속이며 이 결과에 합치지 않는다.

신규 모형16+기존 문단26=42검사와 타입·선택4파일 lint/format이 통과했다. 실제 동일 공식 SDK/Worker a273d450…·정규 d849a4b2…에서는 HWPX 네 종류의 Reader 검사4건, 별도 새 브라우저 프로필의 UI 네 종류와 HWP5 제한·백분율 한 건을 확인했다. 실제 찾기 선택→초안 취소/재열기/Tab→명시 쌍 한 원자 명령→undo 원본 바이트 일치/redo 편집 바이트 일치→저장·새 문서 재열기·새 찾기 선택→질의값 및 읽기 전용 모달/API 거부가 통과했다. 소유 브라우저·서버는 종료했고 입력 핀 변동은 없었다.

이는 격리 후보의 형식별 범위이며 운영 배포·HWP5 전체 종류·독립 CFB/XML 저장 오라클·전체 조판·성능·OS IME 동치 완료가 아니다. 종류 선택은 실제 DOM select의 값/변경 이벤트, 숫자·확인·취소는 브라우저 입력으로 실행했다. 최초 모형41 통과를 실제 Native 성공으로 승계하지 않았으며 새 Native·SDK 생산이나 실제 제품 변경은 하지 않았다.


### c4b78 문단 재연결 후보의 엔진 경계

공개 API 함수 존재는 Native 원자 쓰기 지원을 의미하지 않는다. 창을 열 때 실제 capability를 조회하며, 현재 cb48이 atomic=false이면 기존 정렬6 창으로 돌아간다. 여백·줄 간격·격자·테두리 연결을 cb48에서 지원한다고 표시하지 않는다. 기존6860에서 확인한 확장 문단창은 별도 진단 근거이며 현재 엔진 승격이나 모든 필드 write 성공으로 상속하지 않는다.

문단 전용 tool은 다른 모달이 열려 있으면 cap/query를 시작하지 않고, 취소 뒤에도 다른 모달이 있으면 본문 focus를 복원하지 않는다. 공통 글자창과의 접속은 별도 최소 hunk로 합성한다. 본 후보는 HEAD 기반이며 원 작업트리 WIP와 인덱스를 읽거나 수정하지 않았다.


### 현행 cb48 정렬 창 연결 검증

현행 엔진에서는 원자 문단 서식 ABI가 없어 정렬 전용 창으로 전환합니다. 이 경로에는 미지원 여백·간격·격자·테두리·배경 입력을 활성화하지 않습니다. 정렬창은 공통 controller/view와 기존 단일 정렬 명령을 그대로 쓰며, 전용 표현 보강만 담당합니다.

격리 공유 후보의 문단 42개와 글자·공유 93개는 별도 명시 entry 검사입니다. 실제 Chrome에서는 동일 공식 g5 SDK/Worker를 유지하고 실행 모듈만 cb48로 명시하여 Noori H5/HX 각각 정렬 fallback, 375×320 본문 스크롤과 하단 버튼 접근, 모달 상호배타·Tab 내부 포커스·Escape 본문 복원, 정렬 적용·undo 원본 바이트 복원·redo·저장 재열기를 확인했습니다. 기본 load/save에는 formatting 요청0, 창을 열 때 capability 조회만 있으며 미지원 query/atomic patch는0입니다. 정렬값 입력은 표준 select setter와 change 이벤트, 열기·확인은 실제 CDP 포인터로 검증했습니다. 물리 키보드의 native select 선택·OS IME·전체 Canvas 동치·성능 개선 증명은 아닙니다.

SDK에 포함된 진단6860과 실제 사용 cb48은 다른 입력입니다. 새 Native 배포·전체 문단 필드 쓰기 지원·실제 제품 반영을 이 결과로 주장하지 않습니다. 두 세션은 editor.dispose 뒤 Worker 잔류0이며 브라우저 close 명령의 exit1은 별도로 보존했습니다. 시작 identity가 같은 소유 프로세스 정리 후 inactive/pid null·잔류0을 확인했고 운영 서버에는 신호를 보내지 않았습니다.
