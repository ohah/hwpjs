# ICC 파라메트릭 분기 구간 모델

## 계약

`parametric_segments.assemble`은 기존 전체 정의역 검사를 통과한 곡선을 최대 두 개의 원본 분기로 조립합니다. 분기점과 활성 거듭제곱 계수는 parametric_domain.powerDomain을 재사용합니다. 구간 경계는 정규화 u64 분수이며 포함 여부를 명시합니다. 분기점을 f64로 반올림하거나 열린 끝점을 인접 부동소수점 값으로 대체하지 않습니다.

상위 분기가 start에서 활성화되면 하위 구간은 [0,start), 상위는 [start,1]입니다. start=0이면 하위 분기가 없고 start=1이면 상위는 닫힌 한 점 구간입니다. 상위 분기가 전혀 없으면 하위 구간이 [0,1] 전체를 포함합니다. 두 구간은 겹치거나 틈을 만들지 않습니다.

Linear는 원본 signed 16.16 slope/offset, Power는 a/b/g/offset을 보관합니다. type1의 하위는 0, type2의 하위는 c이며 상위 오프셋도 c입니다. type3은 c*x와 (a*x+b)^g, type4는 c*x+f와 (a*x+b)^g+e를 구분합니다. type0의 암묵적 a/b는 기존 powerDomain이 소유합니다. 전체 정의역 오류는 그대로 전달합니다. 값과 구간은 소유된 값 타입이며 할당이나 입력 변경은 없습니다.

unit_interval.Interval은 비어 있지 않은 정규화 구간의 검증과 정확한 포함 검사를 소유합니다. 양 끝의 분수 유효성·순서·한 점 구간의 양 끝 포함을 확인합니다. 비교에 u64 두 값의 u128 곱만 사용하여 최대 분모에서도 오버플로와 반올림을 피합니다. 역전 구간은 InvalidIccIntervalOrder, 열린 한 점 구간은 EmptyIccInterval입니다. 잘못된 분수는 공통 Fraction 오류를 유지합니다.

이 모델은 Table 68의 원본 분기를 표현할 뿐입니다. [반례 조사](icc-parametric-inverse-topology.md)에서 확인한 클리핑 경계/밑의 영점에 따른 추가 분할, 단조성·상수성·점프 비교, 달성 가능한 역상과 실제 역함수 계산은 아직 남아 있습니다. 기존 점 평가기는 변경하지 않았으며 이번 조립 성공을 역변환 가능성으로 해석하지 않습니다.

## 검증

후속 [임계점 분할](icc-curve-partition.md)은 선형 클리핑과 거듭제곱 밑 영점을 다룹니다. 원본 두 분기 조립과 전체 단조성 판정은 구분합니다.

초기 네이티브 실행은 종료 코드 0, 5/5 단계·488/488 테스트로 통과했습니다. 최대 u64 분모, 약분 형태가 다른 한 점 구간, 열린 끝점, 잘못된 구간/좌표, 분기점 소유권과 전체 구간 덮기, e/f 구분, x=1 한 점 분기와 비활성 분기를 확인했습니다.

WASM mode180은 para payload를 받아 고정 112바이트를 반환합니다. 앞 56바이트는 하위, 뒤 56바이트는 상위 분기입니다. 각 슬롯은 존재 플래그 u32, start/end의 u64 분자·분모 네 개, 포함 비트 u32, 원본 i32 계수 네 개를 LE로 담습니다. 하위 계수는 slope/offset/0/0이고 상위는 a/b/g/offset입니다. 없는 슬롯은 모두 0입니다. 제품 파서·정의역 검사·분기 조립 후에만 출력 메모리를 할당합니다.

독립 JS 기준은 기존 전체 정의역의 임계점 열거 기준을 export해서 재사용하고 제품의 분기 함수를 호출하지 않습니다. 다섯 함수의 지수·양/음/0 계수·정의역 안팎 경계와 서로 다른 오프셋을 조합하여 반환 분수와 포함 비트·계수·빈 슬롯을 비교합니다. 잘림·한도·실패 후 정상 호출도 확인합니다. 전체 감사 결과는 실행 종료 후 기록합니다.

Debug WASM 직접 실행은 비교 3,016건·예상 오류 거부 1,377건으로 통과했습니다. 별도 수동 검사에서는 지수 i32 최솟값/최댓값, 계수 최솟값·오프셋 최댓값을 d=0/1/1초과 구간에 적용한 6건의 원형 보존을 확인했습니다. 이 수동 검사 수는 정규 감사 수에 합산하지 않습니다.

테스트 민감도 확인에서는 두 분기가 모두 존재하는 반환값의 하위 끝점 포함 비트를 의도적으로 켰습니다. 새 비교가 ERR_ASSERTION으로 잘못 닫힌 하위 구간을 검출했습니다. 제품이나 저장소 파일은 변형하지 않았습니다. 정확한 포함 함수 자체는 네이티브 테스트에서 검사하고, mode180은 구간 조립·wire 표현을 검사한다는 범위를 구분합니다.

시스템 ICC 파일의 para TRC 태그 15개(type0/type3)를 읽기 전용으로 확인했습니다. type0의 하위 슬롯 부재와 암묵적 a/b, type3의 열린 하위 끝점·닫힌 상위 시작점과 정확한 d 분수, g/a/b/c 원값이 모두 일치했습니다. 공유 payload의 고유 개수나 type1/2/4 실파일 검증을 뜻하지 않습니다. 파일을 복사·수정하지 않았고 수동 검사는 정규 감사 수에 합산하지 않습니다.

Debug 전체 감사 `/tmp/hwpjs-icc-segments-Debug.log`는 종료 코드 0, 20/20 단계·488/488·WASM 5,697,877건으로 통과했습니다. 신규 비교 3,016건·거부 1,377건도 확인했습니다. 나머지 모드는 종료 후 기록합니다.

ReleaseSafe·ReleaseFast 전체 감사도 `/tmp/hwpjs-icc-segments-ReleaseSafe.log`, `/tmp/hwpjs-icc-segments-ReleaseFast.log`에서 각각 종료 코드 0, 20/20 단계·488/488·WASM 5,697,877건으로 통과했습니다. 신규 비교/거부 수도 일치했습니다.

최종 검토에서 Interval의 시작/끝 포함 여부 네 조합에 대해 0·1/2·1 포함 판정을 명시적으로 추가했습니다. 기존 네이티브 테스트 안에 단언을 추가한 것이며 제품 코드·WASM bridge·JS 감사는 변경하지 않았습니다. 앞선 전체 감사 결과를 이 추가 단언의 근거로 대신하지 않고 네이티브 세 모드를 별도 재실행합니다.

추가 단언을 포함한 네이티브 Debug·ReleaseSafe·ReleaseFast 재실행이 모두 종료 코드 0, 5/5 단계·488/488로 통과했습니다. 로그는 `/tmp/hwpjs-icc-segments-native-{Debug,ReleaseSafe,ReleaseFast}.log`입니다. 위 완료 전 표현은 각 실행 당시 기록입니다.

최종 적대적 검토에서 빈 분기와 한 점 구간의 구분, 분기점의 단일 소유권, u64 분수의 u128 곱 범위, 서로 다른 e/f 보존, 정의역 오류 전파, 비할당 모델과 probe의 출력 메모리 경계를 확인했습니다. 추가 결함은 발견하지 못했습니다. 구간 포함 규칙은 unit_interval, 분기점은 parametric_domain, 원본 분기 조립은 parametric_segments로 책임을 분리했습니다. 포맷·변경 JS 문법·diff 공백·문서 로컬 링크 2개 검사도 통과했습니다. 전체 문서 검증 및 단조성·역함수 완성을 뜻하지 않습니다.
