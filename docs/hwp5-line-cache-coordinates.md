# ViewText 줄 캐시의 원문 좌표 가설 검증

[병합·본문 바이트 대조](hwp5-merged-line-cache.md) · [명시적 문단 좌표 API](hwp5-revision-coordinates.md) · [ViewText 기본 검사](hwp5-track-change-viewtext.md)

## 대조 대상 부재와 값 불일치의 구분

기존 조사는 issue5169 ViewText의 다섯 문제 문단에 대해 BodyText에서 같은 줄 캐시 바이트를 찾지 못했다고 기록했습니다. 추가 조사 결과, **BodyText 루트 99문단에는 줄 레코드 자체가 없습니다.** 이 결과는 대응하는 줄 위치의 값이 서로 다르다는 증거가 아니라 대조 대상의 부재입니다. 실제 PARA_LINE_SEG가 없을 때와 레코드는 있지만 행이 0개일 때를 구분해서 집계합니다.

| 파일·스트림 | 전체 문단 | 줄 레코드 | 빈 줄 레코드 | 전체 줄 행 | 루트 줄 행 |
|---|---:|---:|---:|---:|---:|
| issue5169 BodyText | 228 | 2 | 0 | 2 | 0 |
| issue5169 ViewText | 590 | 524 | 0 | 723 | 133 |
| task2070 BodyText | 53,448 | 0 | 0 | 0 | 0 |
| task2070 ViewText | 53,448 | 53,447 | 0 | 54,552 | 2,354 |

표본은 `reference/rhwp/samples/issue5169_viewtext_changetracking.hwp`와 같은 samples 디렉터리의 `task2070/1130000-201900011_D0150004-1-002_2017년기준 시장구조조사.hwp`의 Section0입니다. BodyText의 개별 길이 초과 0건만으로 전체 줄 캐시 검증이 강하게 입증되었다고 해석하면 안 됩니다. 특히 두 번째 파일의 BodyText에는 검사할 줄 행이 전혀 없습니다.

## 명시적 가설의 결과

표 58의 병합 표식, 표 60의 WCHAR 배열, 표 62의 줄 시작 위치와 캐시 설명만으로 병합 좌표 축을 확정할 수 없습니다. 조사에서는 **CR·제어문자 payload를 포함한 문단별 선언 UTF-16 길이를 그대로 연결한 축**을 가정합니다. 텍스트 부재는 앞서 검증한 정확히 1유닛인 경우에만 명시적 CR 후보로 처리합니다. 그 축에서 줄 시작을 원본 문단/유닛으로 찾고, 앞에 있는 `0x11` 범위의 합집합을 제외한 결과 위치를 계산합니다.

| ViewText 선두 | 원본 줄 시작 | 가설상 변환 후 줄 시작 | 해당 원본 유닛 제외 여부 |
|---|---|---|---|
| 35 | 0, 97, 119 | 0, 26, 48 | true, false, false |
| 116 | 0, 183, 226 | 0, 50, 93 | 모두 false |
| 133 | 0, 52, 92 | 0, 51, 91 | 모두 false |
| 147 | 0, 49, 92 | 0, 47, 90 | 모두 false |
| 167 | 0, 46, 84 | 0, 46, 83 | 모두 false |

issue5169의 루트 99묶음·줄 시작 133개 모두 같은 가설로 조사하며 문제의 다섯 묶음만 선택해서 범위 성공을 확인하지 않습니다. 원본 위치·가설상 결과 위치·원본 문단 번호·문단 내부 위치·제외 여부·해당 코드 유닛을 출력합니다. 문단 끝 경계는 오른쪽 문자가 없으므로 원본 문단/유닛 및 코드 유닛을 null로 기록합니다. 문단 경계는 다음 비어 있지 않은 문단의 오른쪽 유닛을 선택합니다. 이 선택은 조사 도구의 명시적 규칙이며 한글 프로그램의 커서 affinity 규칙을 확정한 것이 아닙니다.

루트에 편향되지 않도록 기존 독립 `revisionGroupEvidence`의 흐름별 소유권으로 중첩 문단까지 확대했습니다. issue5169 ViewText 524묶음·723줄, task2070 ViewText 53,448묶음·54,552줄 전체가 가정한 원문 축 안에 들어옵니다. 병합 후속 문단에 별도 줄 캐시가 없고, 모든 줄 행이 누락 없이 조사되는지도 검사합니다. BodyText의 두 줄도 포함하면 네 스트림에서 총 55,277개 줄 시작입니다. 문단 끝 경계를 가리키는 사례는 0건입니다.

선두 35의 첫 줄을 포함해 issue5169 ViewText에서는 **45개 줄 시작**이 가설상 제외되는 원본 유닛을 가리킵니다. 나머지 세 스트림에서는 0건입니다. 따라서 줄 시작마다 살아 있는 문자가 있어야 한다는 검사를 새로 넣으면 이 표본을 거부하게 됩니다. 제거된 위치를 결과 경계로 모을 수 있다는 산술적 사실만으로 그 줄의 시각적 배치가 맞다고 판단하지 않습니다.

## 책임과 검증

`tests/hwp5/line-cache-coordinate-evidence.mjs`가 부재/빈 레코드 집계와 좌표 가설을 소유합니다. survey는 기존 `paragraphEvidence`·`rootMergeGroups`·`revisionGroupEvidence`·`rangeFilteredCandidate`를 사용하며 CFB·레코드·병합 규칙을 다시 구현하지 않습니다. 제품 Zig의 정렬/이진 검색 구현을 기대값으로 호출하지 않고 유닛별 마스크를 사용합니다. 원본 버퍼·태그·스냅샷을 변경하지 않습니다.

`line-cache-coordinate-evidence.test.mjs`는 7개 테스트로 다음을 검사합니다: CR 포함 축과 비연속 문단 번호, 두 구간 조합 784개 및 역순/중복 질의, 부재 CR, 서로게이트·8유닛 인라인 제어문자 보존, 빈 멤버/전체 삭제/끝 경계, 범위 밖·비정수 질의와 길이 오류, 줄 레코드의 부재/빈 값 구분. 기존 15개 조사 도구 테스트와 함께 `line-cache-audit` 및 전체 `audit`에서 실행합니다. 실제 두 파일의 위 집계와 다섯 문제 묶음의 변환 위치·제외 여부는 assertion으로 고정합니다.

이 조사로 원본 길이 기반 가설의 구체적인 결과와 독립 대조의 한계를 확인했습니다. **BodyText에 대응 줄 캐시가 없으므로 정확한 줄 좌표 축은 아직 확정하지 않았습니다.** 기본 ViewText의 `InvalidLinePosition` 제한은 그대로이며, 명시적 문단 좌표 API에 캐시를 자동 전달하지 않습니다. 다음 근거는 같은 문서의 신뢰 가능한 원본 프로그램 레이아웃 결과 또는 병합 전후 캐시가 함께 있는 별도 표본이어야 합니다. 폰트·폭을 추정한 줄바꿈 결과만으로 확정하지 않습니다.

## 실행 결과

Debug → ReleaseSafe → ReleaseFast 전체 audit가 성공했습니다. 각 모드 네이티브 276/276, 기존 Node 47/47 및 조사 도구 Node 22/22, 빌드 단계 16/16이며 HWP5 WASM 검사 호출은 각 1,384,982회입니다. 제품 코어와 ABI는 변경하지 않았습니다. 전체 실행 중 조사 범위를 모든 흐름으로 확장했으므로 완료 후 최종 `line-cache-audit`를 같은 세 모드에서 다시 실행하여 각각 Node 22/22·빌드 단계 7/7과 전체 55,277개 줄 시작의 조사 결과를 확인했습니다.

재검토에서는 부재와 빈 레코드의 혼동, 루트/문제 문단에 대한 표본 편향, 삭제 경계의 생존 문자 가정, CR·제어문자 축 혼용, 기존 문서의 오래된 미구현 설명을 확인하고 수정했습니다. 최종 포맷·JS 구문·문서 상대 링크·diff 검사도 통과했습니다. 전체 로그는 `/tmp/hwpjs-line-cache-coordinate-{debug,safe,fast}.log`, 최종 조사 재검증은 `/tmp/hwpjs-line-cache-coordinate-final-{debug,safe,fast}.log`입니다. 이 통과는 가설의 계산과 검증 범위의 정확성에 대한 것으로 전체 문서 의미 검증 완료가 아닙니다.
