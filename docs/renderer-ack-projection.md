# 입력 응답의 표시 투영 계산

입력 명령과 Native 응답은 각각 처리합니다. 같은 문서에서 splice를 기다리는 동안 중간 화면 투영의 레이아웃 계산을 미루고, 남은 입력 초안을 적용할 때 계산합니다. 권위 콘텐츠 자체는 즉시 갱신합니다. geometry 읽기·paint·응답 처리 finally는 최신 레이아웃을 확정하는 경계입니다. pendingKind는 특정 snapshot이 해당 요청의 응답이라는 증명이 아닙니다.

문서 교체·폭·DPR·글꼴·입력 취소·undo와 오래된 응답을 구분하며 실제로 그려진 프레임의 포인터 가드를 유지합니다. 문단 조회 인덱스는 현재 불변 snapshot 하나와 최대 4096행만 보관합니다. 검증할 수 없거나 변경 가능한 행은 기존 선형 조회로 돌아갑니다.

정규 회귀는 소형 합성 입력으로 투영·초안·geometry·paint·오류·문서 전환·인덱스 경계를 검사합니다. 별도의 동일 3fc Noori 실브라우저 100자 비교 3쌍에서는 ACK 완료가 약 4.14~4.19초에서 3.28~3.30초로 줄었고 reflow가 300회에서 200회로 줄었습니다. 외부 프로젝트 CPU 부하가 있었으며 단독 유휴 측정은 아닙니다. 100명령·100응답·최종 텍스트·caret·최종 Canvas 픽셀을 대조했습니다. Native 16회 이력 한도는 바꾸지 않았습니다.

한 번의 전체 레이아웃은 문서 크기 D에 비례하는 작업이 남습니다. K회 편집의 전체 O(K·D), 문서가 늘어나는 경우 O(K·D0+K²) 경계를 제거한 변경은 아닙니다. 평균적인 Map 조회 이득을 최악 상수 시간 보장이나 전체 O(n) 증명으로 확대하지 않습니다.

실행 명령은 [개발·검증 명령](development-commands.md)의 입력 응답 표시 투영 회귀를 따릅니다.

합성 회귀는 실제 Native 저장 검사가 아닙니다. 실제 3fc A/B 결과와 Native 저장·이력 회귀는 별도의 검증 범위입니다.

## HWPX 표시용 header 조회의 국소 재사용

기존 display resource cache는 검증된 일반 텍스트 splice에서 `tableCreationResources`의 ID 목록도 소유 복사로 재사용합니다. 해당 조회는 원본 header와 소유 paragraph/character 리소스 ID에 의존합니다. 서식·구조·문서 전환·실패·undo/redo는 기존 전체 무효화 정책을 유지합니다. 위치·dirty·표 owner/site 및 `characterRanges`는 이 항목에 포함하지 않습니다. 정규 회귀 명령은 [개발·검증 명령](development-commands.md#hwpx-표시-자원-캐시-회귀)을 따릅니다.

동일 aebc/cb48 Noori HWPX의 격리 계측 8키 비교에서 해당 Native 조회는 8회에서 1회로 줄고, warm Worker 평균은 84.3ms에서 79.1ms로 줄었습니다. 단일 순차 표본이며 조용한 성능 A/B가 아닙니다. 8명령·8응답·Native 이력 통계·undo8 후 저장 원본 바이트를 대조했고, 별도 Native getter 검사에서 redo8 저장도 비교했습니다. 실제 제품 배포 결과로 확대하지 않습니다.

실제 입력 문자열의 Canvas `fillText` 호출은 첫 beforeinput 후 약75.9ms로 첫 ACK 약321.1ms보다 먼저였습니다. 이는 픽셀 합성 완료 시각이 아니며 처리 backlog 전체를 최초 글자 표시 지연으로 동일시하지 않습니다. 전체 표시 재조회·원문 복사와 O(K·D) 경계는 남고, 이번 국소 개선이 사용자 전체 O(n) 요구나 입력 지연 해결을 완료한 것은 아닙니다.

## 그림 자원 세대와 문단 재사용의 실제 관측

2026-10-30의 격리 후보에서 Noori HWP5를 열고 첫 표시와 두 번째 표시를 비교했습니다. 필수 관측 자료와 같은 flow의 paint 대응 검사는 통과했고 각 단계에서 기존 렌더러와 후보의 전체 layout JSON이 같았습니다. 그러나 최초 재사용 적중을 기대한 검사는 적중 증가 0으로 실패했으며, 이 원 결과를 성공으로 바꾸지 않았습니다. Native 편집·undo·저장 명령은 실행하지 않은 표시 전용 진단입니다.

후보의 마지막 첫 표시 계산과 두 번째 계산 사이에 실제 `decodedResourceEpoch`가 1에서 2로 바뀌었고 그림 자원 콜백이 그 변화를 기록했습니다. 폭·배율·DPR·글꼴 세대·측정 정책·분절 identity는 같았으며 그리기 전 기준선 복원도 확인했습니다. 따라서 두 계산의 의존성이 모두 같았다는 전제는 성립하지 않습니다. 다만 당시 기록에 bitmap의 identity·치수·오류·분기 원값은 없어 실제 치수 변화인지 최초 관측 또는 보수적 무효화인지는 확정하지 않습니다. `picturePending=false`는 자원 세대 불변의 증명이 아닙니다.

이는 변경 의존성의 무효화 계약과 양립하는 관측이며, 속도 개선이나 전체 문서 재사용 성공의 증거는 아닙니다. 이 원 진단에서는 변경 의존성의 재계산과 동일 의존성의 적중을 분리하는 세 단계 후속 검사를 아직 실행하지 않았습니다. 원 실패·합성 무효화 회귀·이 후속 계획을 서로 합산하지 않습니다.

원 관측 메타데이터의 SHA256은 `42a132b2403972dc4d96fe9c753ddffdc1ff5cd4436836f680dbfb5ee5a39711`이며, 네 layout JSON의 SHA256은 모두 `2cc181816546bcd1c41ca9b068f32fa2604a9b1ef07d749df26e968d93a175e4`입니다.

별도의 실제 Noori HWP5 세 단계 진단에서는 처음 표시 → 관측된 자원 세대 변경 후 표시 → 의존성이 같은 재표시를 정확히 한 번씩 실행했습니다. 제품 소스 `77fed0c3…`와 캐시키는 바꾸지 않았습니다. 자원 분기는 `first-observation`이었고 epoch가 1→2로 증가했습니다. 관측된 bitmap은 1200×153, 오류는 null, refreshing은 false였으나 이전 값은 null이므로 실제 치수가 바뀌었다고 증명하지 않습니다.

의존성이 바뀐 단계의 후보는 miss 57회·적중 증가 0·캐시 세대 증가 1을 기록했습니다. 다음 재표시는 관측된 전체 flow 의존성과 준비된 scope·캐시 세대가 같았으며 적중 57회·추가 miss 0이었습니다. 단계별 기존 렌더러와 후보, 변경 단계와 마지막 재표시의 전체 layout JSON 여섯 개가 모두 위의 동일 SHA256과 일치했습니다. 양쪽 진단 실패 계수와 정책·경계 관측 누락은 0이었고 마지막 flow가 완료 paint에 대응했습니다.

이 결과는 원 두 단계의 적중 증가 0 실패를 덮지 않습니다. 원문서 토큰은 같았고 소유 브라우저와 서버 정리가 끝났지만, 이번 검사는 입력·undo·저장·HWPX·Canvas 픽셀·속도·전체 조판 정합성의 증거가 아닙니다. 새 관측 메타데이터 SHA256은 `919fa887717389370d19737d7299f4eeba98b99cf33c8424a12912e92b5cfe74`입니다.
