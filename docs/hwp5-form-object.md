# HWP5 양식 개체의 관측 접두부

[본문 계약](hwp5-body-contracts.md)

## 명세와 실제 근거

공개 명세 표 57은 `HWPTAG_FORM_OBJECT = HWPTAG_BEGIN+75`(태그 91)를 정의하고 표 5는 가변 길이·예시 레벨 2로 나열합니다. 양식 속성 문자열의 상세 내부 배치는 이 표에 정의되어 있지 않습니다. 절대 레벨 2를 모든 중첩 양식에 적용하는 검사는 추가하지 않았습니다.

분할 요약본 `legacy/rust/.claude/skills/hwp-spec/3-2-3-본문.md`의 양식 행은 레벨 1로 적혀 있어 공식 PDF 표 5의 2와 다릅니다. 이번 확인에서는 공식 PDF(`/tmp/hwp5-spec.uK0MG9/spec.pdf`, SHA-256 `1d1da9e6fe22563ae2c5285bbbfc6762974fb7f002278084cbc11e5266bdc782`)를 직접 대조했고, 요약본의 1을 검증 규칙으로 채택하지 않았습니다. 보관된 레거시·레퍼런스 원문은 수정하지 않았습니다.

`reference/rhwp/samples/form-01.hwp`와 `form-02.hwp`는 모두 HWP 5.0.3.0이며 BodyText/Section0에 양식 레코드가 각각 5개 있습니다. 아래 배치가 열 개 모두에 맞고 추가 꼬리는 없습니다.

| 오프셋 | 폭 | 관측 필드 |
|---:|---:|---|
| 0 | 4 | 첫 타입 ID 원시 바이트 |
| 4 | 4 | 둘째 타입 ID 원시 바이트 |
| 8 | 4 | 의미를 확정하지 않은 DWORD (`raw_length`) |
| 12 | 2 | 뒤따르는 UTF-16 코드 유닛 수 |
| 14 | 2 × 유닛 수 | 속성 문자열 원시 UTF-16LE 바이트 |
| 이후 | 가변 | 미해석 꼬리 (`extra`) |

다섯 첫 타입 ID는 순서대로 `tbp+`(버튼), `tbc+`(체크박스), `boc+`(콤보박스), `tbr+`(라디오 버튼), `tde+`(편집 상자)입니다. 실제 열 개에서 두 ID가 같고 DWORD는 u16 문자열 유닛 수와 같습니다. 레코드 전체 바이트 수와 같은 값은 아닙니다. 첫 파일의 유닛 수는 371·412·422·443·505, 둘째는 371·412·418·443·505입니다. 두 ID의 동일성과 DWORD의 의미를 모든 버전의 필수 조건으로 일반화하지 않습니다.

rhwp 로컬 `e8800c8de`의 `src/parser/control.rs::parse_form_control`도 첫 ID와 오프셋 12의 문자열 길이를 사용합니다. 해당 주석은 오프셋 8을 전체 길이라고 부르지만 현재 표본에서 관측한 관계는 위와 같습니다. 반면 `src/serializer/control.rs::serialize_form_control`은 UTF-16 유닛 수를 u32와 u16 두 필드에 기록합니다. 이 작성기의 동작만으로 모든 버전의 길이 불일치 정책이나 65,535유닛 초과 표현을 확정하지 않습니다. rhwp는 알 수 없는 첫 ID를 PushButton으로 처리하고 둘째 ID·DWORD를 모델 필드로 해석하지 않습니다. 우리 파서는 미지 타입을 버튼으로 바꾸지 않고 두 ID와 DWORD를 보존합니다. rhwp의 UTF-16 손실 디코딩이나 속성 문자열 파서 코드를 이식한 것은 아닙니다.

추가 후보 `issue6266/seizure_list_form_button.hwp`는 파일 서명이 `HWP Document File V3.00`인 HWP3입니다. CFB/HWP5 표본으로 사용하지 않았으며 해당 파일을 못 여는 것을 새 양식 접두부 파서의 실패로 집계하지 않습니다.

## API·SSOT·수명

`hwp5.form_object.View.parseObserved(payload)`는 위 관측 배치를 명시적으로 선택하는 함수입니다. `type_id`, `secondary_type_id`, `raw_length`는 값으로 보존하고 `properties`, `extra`는 입력을 빌립니다. 호출자가 두 슬라이스를 사용하는 동안 입력을 유지해야 하며 할당·문자열 디코딩·스크립트 실행·원문 수정은 하지 않습니다.

태그와 첫 ID의 관측 분류는 `body/form_object.zig`, 길이 접두사가 있는 UTF-16 읽기와 잘림 검사는 기존 `utf16_string.read`가 소유합니다. u16 길이 뒤 최소 바이트가 부족하면 `UnexpectedEnd`입니다. 원시 NUL·고립 서로게이트·CR을 보존하며 UTF-16 코드 유닛을 Unicode 문자 수로 다시 계산하지 않습니다. 길이 접두사로 읽는 부분은 최대 65,535유닛이고, 그 이후 바이트는 꼬리로 남깁니다. DWORD 값으로 메모리를 할당하거나 u16 길이를 대체하지 않습니다.

`View.kind()`는 첫 ID가 정확히 일치할 때만 다섯 관측 종류를 반환합니다. 미지 ID는 `.unknown`이며 원래 ID가 남습니다. 둘째 ID와 다르거나 DWORD가 다른 경우도 원형을 보존합니다. 이는 그 값의 의미·형식까지 유효하다는 판정이 아닙니다.

기본 본문 Iterator와 문서/컨테이너 검사는 이 관측 함수를 자동 호출하지 않습니다. 태그 91은 여전히 `Value.unknown`으로 원시 framing을 보유하고 미해석 개수에서도 제외하지 않습니다. 속성 문자열의 명시적 UTF-16 유닛 문법과 전체 중첩 검사는 [속성 토큰·트리](hwp5-form-properties.md), 직접 부모·공통 속성·전역 예산을 연결하는 명시적 경로는 [양식 조립](hwp5-form-controls.md)이 소유합니다. 속성별 타입·참조·기본값, 레이아웃·편집·저장 및 다른 버전의 배치는 후속 범위입니다. 제품 JS 공개 API를 확장한 것도 아닙니다.

## 실측과 적대적 검증

테스트 전용 mode 104는 두 ID·DWORD, 속성 바이트 수·꼬리 바이트 수·관측 종류의 24바이트 보고서 뒤에 속성 원문과 꼬리를 반환합니다. `form-object.mjs`는 독립 Node 바이트 읽기로 기대값을 만들어 전체 결과를 비교합니다.

합성 정상 258건·거부 369건으로 다섯 ID 및 미지/역순/대문자 ID, 첫 ID의 모든 단일 비트 변형, 서로 다른 둘째 ID, DWORD 0·1·최상위 비트·UINT32_MAX, 빈 문자열·NUL·서로게이트·홀수 꼬리, 필요한 문자열이 끝나기 전의 모든 잘린 prefix, 65,535유닛과 한 바이트 부족 및 오류 뒤 재처리를 검사합니다. 네이티브 테스트는 빌린 슬라이스의 원본 연결과 ID 분류, 잘림 경계를 확인합니다. 접두부 파서는 할당하지 않습니다.

실파일 10개 payload의 전체 반환 바이트를 대조하고, 각각의 모든 잘린 prefix와 문자열 길이 65,535로의 변조를 거부한 뒤 원본으로 재처리합니다. 실제 거부 검사는 form-01 4,381건·form-02 4,373건입니다. 디스크 파일·스냅샷은 변경하지 않습니다. 이 결과는 확인한 접두부 배치의 검증이며 양식 전체 지원 완료를 뜻하지 않습니다.

## 실행 결과와 재검토

Debug → ReleaseSafe → ReleaseFast 전체 audit가 성공했습니다. 각 모드 네이티브 278/278, 기존 Node 47/47 및 조사 도구 Node 22/22, 빌드 단계 16/16이며 HWP5 WASM 검사 호출은 각 1,394,393회입니다. 완료 후 세 모드 산출물에서 양식 전용 합성·실파일 적대적 검사를 다시 실행하여 위 건수와 모든 반환 바이트를 재확인했습니다. 전체 로그는 `/tmp/hwpjs-form-object-{debug,safe,fast}.log`입니다.

재검토에서는 미지 타입의 기본값 치환, 두 길이·ID의 의미 혼동, UTF-16 원문 손실과 빌린 입력 수명, 최대 길이·잘림·오류 후 복구, 공식 PDF와 분할 요약본의 레벨 불일치를 확인했습니다. 공통 길이 리더와 별도 양식 책임을 유지하며, 기본 파서의 미해석 진단을 성공으로 바꾸지 않았습니다. 포맷·JS 구문·문서 링크·diff 검사도 통과했습니다. 전체 양식 문법·문서 의미 검증이 완료되었다는 의미는 아닙니다.
