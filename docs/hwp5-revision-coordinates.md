# 관측 변경 추적 UTF-16 좌표 변환

[문단 바이트 변환](hwp5-revision-projection.md) · [묶음 텍스트 조립](hwp5-revision-text.md) · [관측 근거와 줄 캐시 제한](hwp5-merged-line-cache.md)

## 범위와 단일 책임

`body/revision_coordinates.zig`의 `Map.buildObserved(allocator, units, ranges, max_ranges)`가 종류 `0x11`의 비어 있지 않은 범위를 복사·정렬·합집합으로 합치고 누적 제거 길이를 계산합니다. 바이트 생성과 좌표 조회가 이 같은 맵을 사용하므로 삭제 구간 계산을 각각 구현하지 않습니다. 범위 wire와 `start<=end<=units` 검사는 기존 `range_tags.Ranges.parse`와 `Range.validateBounds`가 소유합니다. 선택하지 않은 종류도 길이·위치·전체 범위 개수 한도를 검사합니다.

공개 명세 표 63은 영역의 중첩 가능성과 종류/데이터 배치를 정의하지만, `0x11`을 모든 버전의 삭제 규칙으로 정의하지 않습니다. 이 모듈은 실파일 대조에 근거한 명시적 관측 API입니다. 원본 태그·하위 24비트·텍스트를 변경하지 않으며 기본 문서/컨테이너 경로와 제품 JS API에는 자동 적용하지 않습니다.

## 좌표 계약

`Map.mapBoundary(source_unit)`는 문단 내부 원시 UTF-16 코드 유닛 경계 `[0,source_units]`를 받아 `{offset:u32, removed_unit:bool}`을 반환합니다. 문자가 아닌 코드 유닛이 기준이므로 서로게이트와 확장 제어문자도 원시 너비로 셉니다.

- `offset`: 그 경계 앞에 남아 있는 코드 유닛 수. 삭제 구간 내부의 여러 경계는 같은 결과 경계로 모입니다.
- `removed_unit`: 해당 경계의 **오른쪽 원본 유닛**이 제외되는지 여부. 반열린 삭제 범위의 시작은 true이고 끝은 false입니다. 인접한 삭제 범위는 먼저 합치므로 중간 접점은 true입니다. 문단 끝 경계는 항상 false입니다.
- 범위를 초과한 입력은 `RevisionCoordinateOutOfBounds`입니다. 삭제된 위치를 살아 있는 문자 위치로 조용히 바꾸지 않습니다.

예를 들어 6유닛에서 `[1,4)`를 제외하면 원본 경계 1·2·3·4는 모두 결과 경계 1이지만, `removed_unit`은 각각 true·true·true·false입니다.

`revision_text.Report.mapBoundary(paragraph_node, source_unit)`는 문단 노드를 이진 검색하고 해당 맵을 조회한 뒤 문단의 `projected_start`를 더합니다. 반환값은 `{group_index:usize, projected_unit:u64, removed_unit:bool}`이며 결과 묶음 안의 위치입니다. 문단이 아닌 노드·존재하지 않는 노드는 `InvalidRevisionMember`입니다. 덧셈 오버플로는 `RevisionCoordinateOverflow`입니다. 보고서 배열·맵을 호출자가 임의로 재정렬하거나 수정하지 않는 전제입니다.

원본 노드 번호는 출처 식별자입니다. 묶음 누적 선언 좌표만으로 문단을 역검색하는 API, 결과에서 원본으로의 역방향 매핑, 줄 캐시 좌표 해석은 제공하지 않습니다. 특히 issue5169의 문단 자체 길이를 넘는 ViewText 줄 시작 위치를 이 API에 그대로 넣을 수 없습니다. 공개 명세 표 62의 줄 캐시 축을 밝혔거나 기존 `InvalidLinePosition` 검사를 완화한 것이 아닙니다. 전체 변경 추적 수락·거절, 레이아웃·스타일·참조 재계산 및 저장 가능한 문서 변환도 별도 범위입니다.

## 소유권·한도·복잡도

Map은 선택 범위 배열을 소유하고 원본 텍스트나 범위의 포인터를 보관하지 않습니다. `storage`는 원래 할당 전체, `count`는 합집합 구간 수이며 `spans()`는 사용 중인 앞부분만 노출합니다. `deinit`은 축약된 앞부분이 아니라 전체 할당을 해제합니다. 생성은 O(R log R), 조회는 O(log R)이며 메모리는 선택한 실제 범위 수에 비례합니다. 선언 길이가 UINT32_MAX여도 그 길이만큼 할당하지 않습니다.

`revision_projection.projectObservedMapped`는 이 맵과 맵으로 생성한 바이트를 함께 소유하는 `Projected`를 반환합니다. `Projected.deinit`으로 둘 다 해제합니다. 기존 바이트 전용 `projectObserved`는 같은 함수를 호출한 후 맵만 해제하고 바이트를 반환하므로 API의 기존 출력은 유지됩니다.

묶음 조립기는 각 맵을 Member로 이동하여 Report가 소유하게 합니다. 입력 버퍼·Tree·Index를 해제한 뒤에도 결과 텍스트와 좌표를 조회할 수 있습니다. Report.deinit 및 실패 정리는 이미 생성한 모든 맵을 해제합니다. 전체 범위 예산은 문단 사이에 공유되며, 텍스트 payload 한도 외에 범위 배열·문단/묶음 메타데이터 메모리가 별도로 필요합니다. 단독 맵의 범위 한도는 인자로 주고, 문단 변환의 기본 범위 한도는 100,000개입니다.

## 실파일 대조와 적대적 검증

테스트 mode 103은 mode 102의 버전·전체 예산·CR 정책 뒤에 질의 수(u32), 질의 배열(문단 노드 u32 + 원본 유닛 u32), decoded Section을 받습니다. 결과는 질의마다 묶음 인덱스 u32·결과 유닛 u64·제외 여부 u32의 16바이트입니다. 질의 수 한도와 잘림을 먼저 검사하며 늦은 질의 실패에도 부분 결과를 반환하지 않습니다. 기존 mode 102 보고서 wire는 변경하지 않았습니다. 모두 테스트 전용이며 제품 ABI가 아닙니다.

네이티브 검사는 6유닛에서 가능한 두 구간 조합 784개에 대해 모든 경계를 독립 마스크와 비교합니다. 중복·역순·인접·중첩·빈 구간·전체 삭제, UINT32_MAX와 끝 경계, 다른 종류의 경계 검사, 원본 범위 덮어쓰기 이후 수명 및 모든 할당 실패를 포함합니다. 묶음 조립의 기존 할당 실패 검사도 맵 소유권 이동·늦은 실패 해제까지 실행합니다.

`revision-coordinates.mjs`는 미지 레코드로 문단 위치를 이동시킨 합성 입력에서 정상 9건·오류 거부 7건을 확인합니다. 선행 질의 성공 후 비문단/없는 노드·초과 위치 오류, 질의 한도·잘림, 오류 후 재처리와 빈 입력을 포함합니다. 실제 두 파일의 BodyText/ViewText 네 스트림에서는 **모든 문단의 모든 코드 유닛 경계 932,289개**를 독립 JS 유닛 마스크와 비교합니다.

| 문서·스트림 | 문단 | 검사 경계 | 제외 유닛 |
|---|---:|---:|---:|
| issue5169 BodyText | 228 | 3,828 | 0 |
| issue5169 ViewText | 590 | 10,907 | 2,060 |
| task2070 BodyText | 53,448 | 458,769 | 0 |
| task2070 ViewText | 53,448 | 458,785 | 0 |

이는 선택한 관측 변환의 위치 계산에 대한 검증입니다. 원본 한글 프로그램의 모든 좌표 처리와 일치한다는 증명은 아닙니다. 바이트 변환의 별도 검사에서는 issue5169 루트 99묶음을 실제 BodyText 원문과 계속 대조합니다. 디스크 표본·스냅샷은 변경하지 않습니다.

## 실행 결과와 재검토

Debug → ReleaseSafe → ReleaseFast 전체 audit가 성공했습니다. 각 모드 네이티브 276/276, 기존 Node 47/47 및 조사 도구 Node 15/15, 빌드 단계 16/16이며 HWP5 WASM 검사 호출은 각 1,384,982회입니다. 완료 후 같은 세 모드 산출물에서 좌표 전용 합성·실파일 검사를 다시 실행하여 위 결과를 재확인했습니다. 전체 로그는 `/tmp/hwpjs-revision-coordinates-{debug,safe,fast}.log`입니다.

적대적 재검토는 합집합 산술·끝 경계, 입력 수명과 실패 정리, 비연속 문단/노드 조회, 실제 원본 및 독립 oracle 대조, SSOT·문서 지원 범위의 다섯 관점으로 수행했습니다. 정렬·합집합 책임이 이전 변환기에 있다고 적힌 문서와 내부 좌표 미지원 문구를 현재 코드에 맞춰 수정했습니다. 포맷·JS 구문·상대 링크·diff 검사도 통과했습니다. 이 단계의 검증 성공을 전체 명세 구현 완료로 보지 않습니다.
