# ICC 거듭제곱 클리핑 경계의 기호적 실근

## 명세와 범위

[ICC.1:2022 Table 68](https://www.color.org/specifications/ICC.1-2022-05.pdf)의 거듭제곱 분기는 `(a*x+b)^g+offset`이고 출력 범위 밖은 0/1로 클리핑합니다. 이 문서의 g·offset·target 입력은 모두 원본 signed 16.16 정수입니다. target=0 또는 65536으로 각각의 클리핑 경계 방정식을 구성할 수 있습니다. 모듈은 다른 i32 target도 허용합니다.

`power_level.solve(g, offset, target)`은 **밑 변수 z**에 대한 `z^(g/65536)=(target-offset)/65536`의 실수 해 집합을 반환합니다. 근을 f64로 계산하지 않고 정확한 기호식으로 보존합니다. 이 모듈의 경계는 x 좌표가 아닙니다. `z=(a*x+b)/65536`을 역으로 풀어 활성 구간과 비교하는 단계, a=0인 상수 밑 처리, 실제 클리핑 구간 조립, 분기 간 점프·전체 단조성·역변환은 후속 작업입니다. 실근 표현의 구현을 그 단계들의 완료로 간주하지 않습니다.

## 결과 계약

후속 [정확한 좌표와의 비교](icc-power-root-compare.md)는 등식 증명·정수 상/하한을 사용합니다. 활성 구간 포함·클리핑 분할은 별도 단계입니다.

- `Solutions.all_nonzero`: g=0이고 target-offset=65536인 경우입니다. 모든 **0이 아닌 실수 밑**이 해이며 기존 정책에 따라 0^0은 제외합니다. 모든 x가 해라는 뜻은 아닙니다.
- `Solutions.finite`: 최대 두 근의 값 배열과 count를 반환합니다. count=0은 해가 없는 경우입니다. count 밖은 초기화하지 않으므로 읽지 않습니다.
- `Root.zero`: g>0이고 target-offset=0인 경우의 유일한 근입니다. g<0에서는 0이 해가 아니며 유한한 다른 밑도 0으로 거듭제곱되지 않습니다.
- `Root.nonzero`: 부호와 양수 크기를 분리합니다. 크기는 `(numerator/65536)^(exponent_numerator/exponent_denominator)`입니다. 분자는 `abs(target-offset)`, 역지수 분자는 ±65536, 양수 분모는 abs(g)입니다. 약분이나 무리수 근사 없이 원래 수식을 보존합니다. 두 근이면 양수·음수 순서이며 좌표순 정렬 결과가 아닙니다.

양수 우변에는 항상 양수 근이 있습니다. 음수 밑은 정수 지수에서만 허용하며, 짝수 지수는 양수 우변에 음수 근을 하나 더 만들고 홀수 지수는 음수 우변에 음수 근을 만듭니다. signed 16.16의 비정수 지수를 기약분수로 쓰면 분모가 짝수이므로 음수 밑의 실근은 없습니다. 이는 기존 정의역 정책과 일치합니다.

`fixed16_exponent.classify`가 원본 지수의 비정수/짝수 정수/홀수 정수 분류를 소유합니다. 전체 정의역 검증, 클리핑 전 방향 판정, 이번 실근 구성이 재사용합니다. f64 점 계산은 다른 입력 표현을 다루며 이 정수 분류에 강제 변환하지 않습니다.

target-offset의 범위는 −4294967295..4294967295로 i64 안에 들어갑니다. g의 최솟값을 먼저 i64로 확장한 뒤 부호를 바꾸므로 abs(g)=2147483648도 u32 분모에 보존됩니다. 계산량과 메모리는 지수 크기와 무관하게 상수이며 실제 거듭제곱·할당·입력 변경은 없습니다. 유효 곡선인지, 근이 실제 활성 구간에 있는지는 이 방정식만으로 판정하지 않습니다.

## 검증

네이티브 테스트는 √2의 두 부호, 음의 역지수, 음수 우변과 비정수 지수의 무해, 0^0과 상수 해 집합, 영점과 음의 지수, 전체 i32 차이·최소 지수 보존을 확인합니다.

테스트 WASM mode182는 g/offset/target i32 BE 12바이트를 입력받습니다. 결과는 kind u32 LE(0=finite, 1=all_nonzero), count u32 LE와 근당 20바이트입니다. 각 근의 sign i32 LE(−1/0/+1), numerator u64 LE, 역지수 분자 i32 LE, 분모 u32 LE를 순서대로 반환합니다. 영점 슬롯은 전부 0이고 최대 출력은 48바이트입니다. 제품 JS API에 노출하지 않습니다.

독립 JS 검사는 원래 지수를 BigInt 기약분수로 줄인 뒤 후보 밑 부호 −1/0/+1의 정의역·출력 부호로 해 집합을 대조합니다. 제품의 근 생성 함수를 호출하거나 기대 슬롯을 제품으로 생성하지 않습니다. 역지수는 `p*g=65536*q`를 정확한 정수로 검사합니다. 모든 표현 가능한 정수 지수 65,536개와 네 가지 우변, 정수부 −32768/0/32767 각각의 모든 16비트 소수부와 양·음 우변, 비정수 이웃·i32 극값 조합, 잘림·과잉 입력·자원 제한·오류 후 정상 재사용을 포함합니다.

전체 감사와 적대적 검증의 최종 결과는 실행 완료 후 이 절에 기록합니다.

### 실행 기록

초기 네이티브 검사는 494/494로 통과했습니다. 초기 전체 Debug 로그 `/tmp/hwpjs-icc-power-level-Debug.log`도 20/20 단계·494/494·WASM 검사 5,981,034건으로 통과했습니다. 이 실행은 지수 분류 공통화와 모든 소수부 패턴 추가 이전 상태이므로 최종 상태의 근거로 대체하지 않습니다.

공통화 이후 Debug 산출물에서 신규 해 집합 비교 656,341건·예상 오류 거부 14건을 직접 실행해 통과했습니다. 같은 산출물에서 기존 구간 분할 비교/거부 13,101/6,917건, 전체 정의역 비교/거부 5,262/4,381건도 통과했습니다. 임시 반환값 래퍼로 역지수 부호를 뒤집으면 독립 검사가 ERR_ASSERTION으로 검출했습니다. 제품에는 이 변형을 남기지 않았습니다.

`/System/Library/ColorSync/Profiles`의 para TRC 태그 15개(type0/type3)에서 원본 지수로 0/1 경계 방정식 30개를 읽기 전용 검사했습니다. 밑 변수의 영점과 양수 단위 근 표현을 확인했습니다. 해당 프로파일에서 실제 활성 x 구간에 포함되는지, 두 분기 사이의 연속성이나 시각적 결과가 같은지는 이 조사로 주장하지 않습니다. 파일 복사·수정은 없으며 수동 건수는 정규 감사에 합산하지 않습니다.

최종 세 모드 감사는 `/tmp/hwpjs-icc-power-level-Debug-final.log`, `/tmp/hwpjs-icc-power-level-ReleaseSafe-final.log`, `/tmp/hwpjs-icc-power-level-ReleaseFast-final.log`에 순차 실행 중입니다. 완료된 모드의 결과를 확인하기 전에는 전체 최종 감사를 통과로 표시하지 않습니다.

Debug·ReleaseSafe 최종 로그는 각각 20/20 단계·494/494 네이티브 테스트·WASM 검사 6,374,250건으로 통과했습니다. 신규 비교/거부는 각 656,341/14건입니다. ReleaseSafe 산출물 직접 실행도 같은 신규 건수로 통과했으며, 두 근 중 음수 근을 삭제하거나 all_nonzero 해 집합을 빈 집합으로 바꾸는 임시 반환값 변형을 각각 ERR_ASSERTION으로 검출했습니다. 이러한 변형은 제품 파일에 적용하지 않았습니다.

### 활성 구간 비교 전의 정밀도 반례

후속 경계 포함 판정의 적대적 조사에서 type4 `[131072,65536,0,0,0,32768,0]`, 즉 `clip(x²+1/2)`의 상한 클리핑 근 √(1/2)를 사용했습니다. 아래 두 정규화 u64 분수는 정확히 경계의 양쪽에 있습니다.

| 좌표 n/d | 정확한 2n²−d² | Number(n)/Number(d) | 해당 f64를 mode160에 전달한 결과 |
|---|---:|---:|---:|
| 4866752642924153522 / 6882627592338442563 | −1 | 0.7071067811865476 | 1 |
| 11749380235262596085 / 16616132878186749607 | +1 | 0.7071067811865475 | 0.9999999999999999 |

첫 분수는 근보다 작고 두 번째는 크지만, 분자·분모를 각각 f64로 바꾸고 나누면 좌표 순서가 반대가 됩니다. 이는 mode160이 원래 분수를 입력받아 잘못 비교한 결과가 아닙니다. 이 API는 이미 반올림된 f64를 입력받는 근사 점 계산이며, 정보 손실은 앞선 변환에서 발생했습니다. 최초 조사 가정인 '두 변환값이 같을 것'은 실측에서 기각됐고 더 강한 순서 역전이 확인됐습니다. 근사 평가의 기존 계약을 정확한 경계 판정으로 승격하지 않습니다.

재현의 정확한 부호 증거는 JavaScript BigInt의 `2n*n*n-d*d`로 확인할 수 있습니다. 두 좌표는 Pell 수열 `(p,q)=(1,1)`에서 `(p,q)←(p+2q,p+q)`를 반복하여 p≤2⁶⁴−1인 마지막 두 q/p를 취한 것입니다. 이 수동 증거는 정규 감사 건수에 합산하지 않았습니다. 후속 활성 구간 비교는 이러한 좌표를 f64로 변환하지 않은 상태에서 구분해야 합니다.

### 최종 확인

세 모드 순차 실행은 종료 코드 0으로 완료했습니다. 위 `-final.log` 세 파일 모두 20/20 단계·494/494 네이티브 테스트·WASM 검사 6,374,250건을 기록합니다. 각 신규 비교/거부는 656,341/14건입니다. ReleaseFast 산출물 직접 실행에서도 신규 검사와 기존 구간 분할 13,101/6,917건·정의역 5,262/4,381건의 비교/거부가 통과했습니다. 앞의 실행 중 문장은 진행 이력이며 최종 상태는 이 절이 소유합니다.

최종 적대적 코드 검토에서 g=0의 별도 정의역, 0의 음의 거듭제곱 제외, 음수 밑의 홀짝, 원본 i32 차이와 최소 지수의 확장, 최대 두 근의 초기화 범위, probe 최대 48바이트와 실패 경로, 공통 지수 분류 재사용을 확인했습니다. 해당 범위에서 추가 결함은 발견하지 않았습니다. Zig 포맷·변경 JS 문법·로컬 문서 링크·diff 공백 검사도 통과했습니다. 전체 ICC 색상 변환 또는 HWP/HWPX 문서 기능 완료를 주장하지 않습니다.
