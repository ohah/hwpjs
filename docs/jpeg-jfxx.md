# JPEG JFXX 확장 작업

JFIF 확장의 payload 해석과 JPEG 썸네일 내부 복호화를 구현했습니다. 외부 APP0 배치 검증과 RGB 색 변환은 포함하지 않습니다.

## 근거와 책임

[T.871](https://www.itu.int/rec/T-REC-T.871-201105-I/en) 6.4 및 10.2~10.5를 로컬 공식 PDF로 확인했습니다. JFXX는 `JFXX\0` 식별자와 한 바이트 extension code를 사용합니다. 미지원 확장은 건너뛰고 주 이미지를 계속 처리해야 하므로, 미지 코드 자체를 전체 JPEG 오류로 바꾸지 않습니다.

- `thumbnail.zig`: u8 치수 읽기와 packed RGB8/팔레트 RGB8 뷰, 경계 검사된 픽셀 조회를 소유합니다. 기존 JFIF 헤더와 JFXX RGB 경로가 같은 RGB 읽기를 재사용합니다. JFIF는 치수 0을 허용하지만 JFXX 비압축 썸네일은 두 치수가 모두 nonzero여야 합니다.
- `jfxx.zig`: APP0의 마커/길이를 제외한 payload를 해석합니다. 65,533바이트 상한과 정확한 식별자를 확인합니다. 코드 0x11은 치수·768바이트 팔레트·정확한 width×height 인덱스, 0x13은 치수·정확한 3×width×height RGB를 읽습니다. 알려진 비압축 형식의 잘림·여분 바이트는 거부합니다.
- 0x10은 `jpeg_unchecked`로 원문을 반환합니다. 빈 데이터나 손상 데이터도 이 상태에서 유효한 JPEG로 인증하지 않습니다. 별도 `jfxx_jpeg.decode`로 baseline JPEG, JFIF/JFXX 마커 부재, 성분 제약 및 성분 평면 복호화를 확인합니다.
- 미지 코드는 `unknown { code, bytes }`로 원문을 보존합니다. payload 해석기가 임의로 JPEG/RGB로 추측하지 않습니다.

payload 파서의 모든 뷰는 입력을 빌리며 할당하지 않습니다. 입력은 사용 중 불변·유효해야 합니다. 픽셀 조회는 범위 밖과 usize 최댓값에 null을 반환하며, 팔레트의 R/G/B 순서를 바꾸지 않습니다. 외부 APP0 위치·중복·연속성과 JPEG 썸네일 복호화는 별도 책임입니다.

## 비압축 단계 검증 이력

Debug JPEG 네이티브 92/92개가 통과했습니다. 코드 바이트 전체의 알려진/미지 분기, 비균일 팔레트 256색과 역순 인덱스 256개, RGB 픽셀 위치, 최대 인덱스, 잘림·여분 바이트·0 치수·식별자·세그먼트 상한을 검사했습니다. 두 비압축 형식의 모든 nonzero u8 치수 조합도 검사하여 인덱스/팔레트/RGB 크기와 세그먼트 한도를 구분했습니다.

전체 네이티브 재실행도 808/808개 통과했습니다.

## WASM 독립 대조

테스트 전용 mode 263은 JFXX payload를 받고 u32 6개(code/width/height/원문 길이/조회 RGB 길이/보류 종류), 원래 extension_data, 픽셀 조회로 얻은 RGB를 반환합니다. 보류 종류는 비압축 0, JPEG 미검증 1, 미지 코드 2입니다. 비압축 뷰의 범위 밖 및 usize 최댓값 픽셀 조회도 확인합니다. 제품 API는 변경하지 않습니다.

`tests/hwp5/jpeg-jfxx.mjs`는 고정 바이트 위치와 JS 팔레트 조회로 기대 결과를 계산합니다. Debug WASM 비교 3,736건·거부 1,207건이 통과했습니다. 전체 코드 바이트, 빈 미지/압축 payload, 여러 치수/세그먼트 상한, 잘림/식별자/0 치수/여분 바이트/출력 한도, 역순 팔레트 인덱스를 검사했습니다. 정규 audit에 연결했습니다.

RGB 읽기 공통화 이후 기존 JFIF 비교 67,414건·거부 66,003건, 실제 HWP JPEG 참조 8건과 `s1.jpg`의 헤더/프레임 제약도 Debug에서 다시 통과했습니다. JPEG 미검증·팔레트·RGB·미지 코드 네 가지 결과의 모든 출력 바이트를 각각 XOR 1 하여 총 1,026곳의 변조를 검출했습니다.

실파일 APP 조사에서는 JFXX를 아직 관측하지 않았으므로 합성 입력 검증을 실제 JFXX 파일 검증으로 보고하지 않습니다. 외부 APP0 배치·중복 검사도 후속 단계입니다. 이후 검증 결과는 아래에 기록합니다.

## JPEG 압축 썸네일 내부 검증

`jfxx_jpeg.decode(allocator, extension_data, options)`는 0x10의 압축 데이터를 명시적으로 복호화합니다. 65,527바이트 상한은 APP payload에서 JFXX 식별자·코드 6바이트를 제외한 크기입니다. Baseline SOF0만 허용하고 JFIF의 기존 8비트·성분 수·ID 검사기를 재사용합니다. 부모 이미지와 썸네일의 성분 수가 같아야 한다는 조건은 추가하지 않습니다.

`structure.inspectWithMarkerCheck`로 기존 전체 마커/엔트로피 순회에 순수 검사 함수를 적용합니다. SOI/EOI와 스캔 뒤를 포함해 모든 마커를 확인하며, APP0의 정확한 `JFIF\0` 또는 `JFXX\0` 식별자는 거부합니다. 별도 마커 순회를 복제하거나 APP 데이터 속 JPEG에 재귀하지 않습니다. 다른 APP 마커의 의미를 인증하지는 않습니다.

검사 후 기존 `sample_planes.decode`를 호출하므로 추가 bounded 구조 순회가 한 번 있습니다. 기존 테이블·스캔 커버리지·엔트로피·IDCT·평면 소유권을 재사용합니다. 썸네일 뒤 여분 바이트는 호출자가 일반 JPEG trailing 허용 옵션을 켜도 거부합니다. 성공 결과는 소유권 있는 성분 평면이며 업샘플링·색 변환은 하지 않습니다.

Debug JPEG 네이티브 95/95개 통과. 정상 baseline, 모든 할당 실패 지점, 샘플 한도, 마지막 패딩 오류, 엔트로피 전/후의 금지 APP0, 다른 APP0의 허용, 비-baseline 코드, 잘못된 ID, 모든 입력 잘림, 여분 바이트와 크기 상한을 검사했습니다. 후속 대조 결과는 아래에 기록합니다.

전체 네이티브 811/811개가 통과했습니다. 압축 썸네일용 mode 264는 기존 평면 probe의 입력·출력을 재사용하고 복호화 진입점만 JFXX 전용으로 선택합니다. 기존 mode 260의 평면 형식은 바꾸지 않았습니다.

`tests/hwp5/jpeg-jfxx-jpeg.mjs`의 독립 마커 검사와 평면 oracle로 Debug 비교 271건·거부 159건이 통과했습니다. 단색/3성분, 치수 경계, 서로 다른 샘플링, 재정렬된 스캔, restart/DNL/Q 재정의, 금지 마커의 엔트로피 전후 배치, 비-baseline/ID/패딩/잘림/한도 오류를 포함합니다. 비압축 확장과 기존 JFIF 독립 검사도 다시 통과했습니다. 정규 audit에 연결했습니다.

압축 썸네일의 Debug 평면 출력 978바이트도 각각 XOR 1하여 모두 검출했습니다. `/tmp/hwpjs-jfxx-mutants.PiyrRb/`의 별도 소스 복사본에서는 RGB 순서 반전·팔레트 오프셋 3배 누락·중첩 금지 검사 제거·baseline 제한 제거를 세 모드 모두 컴파일 후 테스트 실패로 검출했습니다. 각 변형은 JPEG 95개 중 1개가 실패했습니다. 뒤의 두 변형은 기대 오류 대신 소유권 있는 이미지를 반환하므로 기대 오류 검사에서 실패하며 Debug/ReleaseSafe에서 추가 누수 진단이 발생했습니다. 이는 의도적 결함 검출이며 정규 소스의 할당 정리 검사와 구분합니다.

## 릴리즈 독립 재검증

ReleaseSafe와 ReleaseFast의 별도 WASM에서도 각각 비압축/미지 확장 비교 3,736건·거부 1,207건, 압축 썸네일 비교 271건·거부 159건, 기존 JFIF 비교 67,414건·거부 66,003건이 통과했습니다. 비압축/미검증 출력 1,026바이트와 압축 평면 출력 978바이트의 개별 변조도 두 모드 모두 검출했습니다.

실제 HWP의 JPEG 참조 8건과 `reference/rhwp/samples/s1.jpg`의 JFIF 헤더·프레임 제약도 두 릴리즈 모드에서 다시 일치했습니다. 참조 수는 고유 이미지 수가 아니며, 이 회귀 검사는 실제 JFXX 복호화나 progressive 픽셀 복호화를 입증하지 않습니다. 제품 JS API는 여전히 CFB만 제공하며 HWP BinData의 JPEG 연결·업샘플링·색 변환은 후속 범위입니다.

## 전체 회귀 검증

Debug → ReleaseSafe → ReleaseFast 순서로 `zig build audit --summary all`에 각 최적화 옵션을 적용했습니다. 세 모드 모두 20/20 단계, 네이티브 811/811개, 독립 audit의 checks 7,655,824건이 통과했습니다. 로그는 `/tmp/hwpjs-jfxx-{Debug,ReleaseSafe,ReleaseFast}-audit.log`에 남겼습니다. 이 검사 수는 포맷 지원률이나 모든 입력에 대한 무결함 보증이 아닙니다.

SSOT 검토에서는 JFIF/JFXX의 RGB 바이트 읽기와 픽셀 조회를 `thumbnail.zig`로 공유하고, 압축 썸네일의 구조·프레임·테이블·엔트로피·평면 복호화는 기존 JPEG 계층을 재사용하는 것을 확인했습니다. 확장 payload 해석, 압축 내부 제약, 테스트용 직렬화는 별도 책임으로 유지합니다.
