# ICC 유리수 거듭제곱 값 비교

## 필요성과 범위

이 수치 비교를 사용하는 [분기 경계 점프 판정](icc-parametric-jump.md)은 원본 계수·오프셋·좌극한·클리핑 연결을 소유합니다.

[ICC.1:2022 §10.18 Table 68](https://www.color.org/specifications/ICC.1-2022-05.pdf)의 type3/type4 분기 연결에서는 하위 선형 식의 좌극한과 상위 거듭제곱 식의 실제 값을 비교해야 합니다. 원시 c=d=1이면 하위 값 c*d는 1/4294967296입니다. 이를 다시 signed 16.16으로 반올림하면 정확한 경계 판정을 할 수 없습니다. 공식 표의 x<d / x>=d 및 출력 [0,1] 제한을 재확인했습니다.

`rational_power_order.compare(precision, base_n, base_d, g, target_n, target_d)`는 `(base_n/base_d)^(g/65536)`과 `target_n/target_d`의 순서를 반환합니다. 분자는 i128, 양의 분모는 u128, g는 원시 i32입니다. 결과는 lt/eq/gt 또는 현재 정밀도에서 미확정인 null입니다. precision은 128/256/512/1024입니다.

이 단계는 **오프셋 없는 수치 비교 원시 기능**입니다. 원본 분기의 조립·오프셋 차감·클리핑·좌극한과 실제 값의 선택·전체 단조성·역변환은 호출 계층의 후속 작업입니다. 일반 유리수 좌표를 받는다는 사실을 전체 곡선 연결 완료로 해석하지 않습니다. 제품 JS API도 추가하지 않습니다.

## 정확성과 SSOT

- 분모 0은 InvalidIccPowerCoordinate입니다. 밑 0의 비양수 지수, 음수 밑의 비정수 지수는 UndefinedIccCurvePower입니다. 목표값의 부호가 달라도 실수 정의역 오류를 먼저 검사합니다.
- 밑 0, 지수 0과 서로 다른 부호는 정수 비교로 처리합니다. i128 최솟값은 signed 부호 반전 없이 u128 절댓값으로 처리합니다. g의 최솟값도 u32 절댓값을 사용합니다.
- 음의 지수는 양수 밑 크기의 분자/분모를 교환합니다. 음수 밑의 홀수 정수 지수는 최종 크기 순서를 반전합니다. 지수 분류는 기존 fixed16_exponent를 재사용합니다.
- 새 rational_power_equality가 양의 유리수 거듭제곱의 동등성 판정을 소유합니다. 기존 radical_equality도 이 기능을 호출합니다. 기약 A/B와 서로소 p/q에서 결과가 유리수이려면 A와 B 각각이 완전 q제곱이어야 한다는 조건으로 검사하고, bounded 정수 거듭제곱으로 목표 분자/분모와 대조합니다. 이 내부 함수의 전제는 양의 모든 유리수 성분과 양의 p/q이며 외부 비교기가 보장합니다.
- integer_power.root의 입력/출력을 u128로 확장했습니다. degree=1은 즉시 반환하고 degree>=128에서는 value=1 외의 완전 거듭제곱이 없으므로 이분 탐색 없이 거부합니다. 곱셈은 기존 오버플로 감지 bounded를 공유합니다.
- 동등하지 않으면 기존 positive_bounds의 방향성 있는 정수 경계를 사용해 `(A/B)^abs(g)`와 `(N/D)^65536`을 비교합니다. 두 경계가 겹치면 동등하다고 간주하지 않고 null을 반환합니다. 최대 정밀도에서 모든 입력이 판정된다는 보장은 없습니다.

## 검증 구성

네이티브 검사는 u128 최대값·큰 완전 제곱·127/128차 경계, 3/7과 7/3의 정확한 결과, 음수 밑/지수/목표값, i128/i32 극값, 분모 0과 정의역 실패를 포함합니다. 작은 유리수 격자에서는 별도 u256 정수 거듭제곱과 교차 곱을 직접 계산해 순서를 대조합니다.

테스트 WASM mode190은 72바이트 BE 입력(precision u32, g i32, base_n i128, base_d u128, target_n i128, target_d u128)을 받습니다. 출력은 i32 LE −1/0/+1/2(미확정)입니다. JS 기준은 기존 BigInt 유리수 도우미로 정수 거듭제곱을 직접 전개하며 제품의 기호근·방향성 경계 알고리즘을 복제하지 않습니다. 네 정밀도, u128 Pell 경계의 미확정/정밀도 상승, 모든 입력 잘림·과잉 바이트·크기 제한·부적합 정밀도와 실패 후 복구를 검사합니다.

## 실행 기록

첫 네이티브 빌드는 기존 root 테스트 네 곳의 기대 타입이 ?u64로 남아 있어 컴파일 오류가 발생했습니다. 반환형 확장에 맞춰 ?u128로 고쳤으며 기존 기대값은 변경하지 않았습니다.

Debug 테스트 WASM의 신규 검사 직접 실행은 comparisons=2894, rejected=779, undecided=1로 통과했습니다. 별도 읽기 전용 수동 검증에서는 고정 seed 123456789, 128비트 LCG로 만든 큰 유리수 1,000개를 BigInt 교차 거듭제곱과 대조했고 일치했습니다. 미확정 반환 2를 동등 반환 0으로 바꾸는 임시 호출 래퍼는 기존 검사에서 ERR_ASSERTION으로 검출됐습니다. 제품에는 변형을 남기지 않았으며 수동 검사 건수는 정규 감사에 합산하지 않습니다.

실제 `/System/Library/ColorSync/Profiles`의 Display P3, ITU-2020, ITU-709, ROMM RGB에서 type3 r/g/bTRC 12개를 다시 읽었습니다. 원시 계수로 밑 `(a*d+b*65536)/4294967296`, 하위 좌극한 `c*d/4294967296`을 직접 만들고 256비트 비교기에 전달했습니다. 두 출력이 엄격히 (0,1)에 있다는 판정도 확인해 이 지점에서는 클리핑이 순서에 영향을 주지 않음을 확인했습니다. 상위 값과 하위 좌극한의 순서는 앞의 두 프로파일에서 gt, 뒤의 두 프로파일에서 lt였으며 [기존 고정밀 조사](icc-parametric-inverse-topology.md)의 점프 부호와 일치했습니다. 이는 실제 태그에서의 수치 비교 실측이지 일반 곡선 연결 API·프로파일 전체 유효성·OS 색상 엔진 결과 검증은 아닙니다.

### 최종 확인

`/tmp/hwpjs-icc-rational-power-Debug.log`, `/tmp/hwpjs-icc-rational-power-ReleaseSafe.log`, `/tmp/hwpjs-icc-rational-power-ReleaseFast.log`의 순차 전체 감사가 모두 종료 코드 0으로 완료됐습니다. 각 로그는 20/20 단계·514/514 네이티브 테스트·WASM 검사 6,433,176건을 기록합니다. 신규 검사 수는 세 모드 모두 comparisons=2894, rejected=779, undecided=1입니다. 기존 기호근 비교·클리핑 회귀 검사도 포함합니다.

ReleaseFast 산출물 직접 대조도 같은 신규 검사 수로 통과했고, 미확정을 동등으로 변조한 반환값을 ERR_ASSERTION으로 검출했습니다. 적대적 재검토에서는 기약 지수의 완전근 조건, u128 이분 탐색과 곱셈 오버플로 경계, 최소 signed 값의 절댓값, 부호 단축보다 앞선 정의역 검사, 방향성 경계 겹침의 미확정 유지, 검사 오류 뒤 정상 호출 복구를 확인했습니다. 해당 범위에서 추가 결함은 발견하지 않았습니다. 변경 Zig 포맷·JS 문법·로컬 문서 링크 6개·diff 공백 검사도 통과했습니다.
