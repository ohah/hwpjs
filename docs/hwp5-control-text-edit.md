# HWP5 제어 포함 텍스트 편집 확장 작업

현재 공개 splice API는 탭과 알려진 표·도형 등의 anchor, 같은 문단 안의 하이퍼링크 표식을 보존하는 텍스트 편집을 연결했습니다. 다른 필드와 문단 간 필드는 계속 거부합니다. 이 문서는 확장 중인 경계 검증과 실제 조사 근거를 기록하며 전체 지원 완료 계약이 아닙니다.

후속 관측 SUM/AVG 계산식 구역의 일반 문단/숫자 셀 편집·원자적 재계산은 [계산식 계약](hwp5-formula-command.md)이 소유합니다. 아래 chart 175개 일괄 거부는 이 연결 전 기록이며, 현재 수식 표식 대상 문단 직접 편집과 일반 다른 필드/문단 간 필드 제한은 유지합니다.

## 2026-10-01 실제 거부 조사

후속 전수 검사에서 SectionControl 거부 175개는 모두 chart.hwp 한 구역입니다. 원문 CTRL_HEADER의 `%fmu` 계산식 13개가 source_policy의 비하이퍼링크 필드 거부에 걸려 모든 문단을 막습니다. 이 값은 미지 ID가 아니라 기존 control_rules의 알려진 code 3이며 SUM 10개·AVG 3개입니다. 원문 문단 인덱스는 23·29·35·64·70·76·129·130·131·132·156·162·168입니다. 공통 필드 속성은 0, 기타 속성은 8, command 길이는 21~26 UTF-16 단위, instance ID 뒤 extra는 각각 4바이트입니다.

예를 들어 command는 `=SUM(B?:E?)??%g,;;67.5`, `=SUM(?2:?4)??%g,;;245`, `=AVG(B?:E?)??%.2f,;;266.00`입니다. 조사에서는 command 길이 밖의 instance ID를 문자열로 출력하지 않도록 바로잡았습니다. 외부 명령 실행은 하지 않습니다. 이 거부를 풀어 원문만 보존해도 참조 셀 편집 뒤 계산 결과가 최신이라는 보장은 없습니다. 계산식 지원에는 주소/범위 해석·의존 셀 추적·계산 및 표시/command 결과 갱신 또는 명시적 미해결 모델이 필요하며 현재 구현했다고 주장하지 않습니다. 일반 필드의 소유 범위와 문단 간 시작/끝 연결도 별도 검증 대상입니다.

`software.hwp`의 전체 101문단에 시작 삽입을 시도했습니다. 남은 8개의 거부는 원본 레코드와 공개 미리보기 토큰을 대조해 분류했습니다. 인덱스는 0부터 시작합니다.

| 문단 | 관측한 제어 |
|---|---|
| 0 | 구역·단·머리말·도형·표 |
| 33 | 8 UTF-16 유닛 탭 뒤 `- ` |
| 42, 80 | 표 anchor |
| 44 | 도형 anchor 뒤 `주요 기능 흐름` |
| 88 | 단 정의와 하이퍼링크 `mozuERD` |
| 93 | 하이퍼링크 `mozuAPI` |
| 98 | 하이퍼링크 `mozuGitHhub` |

최초 API 이름을 잘못 사용한 조사 명령은 import 단계에서 실패했습니다. 현재 실제 export `createExperimentalHwp5Editor`로 다시 실행한 결과만 위 분류에 사용했습니다. 기존 제어 마스크 정책에서 먼저 거부되므로 이를 파일 손상이나 뒤의 소유권 검증 성공으로 해석하지 않습니다.

## 경계 검증의 책임

`hyperlink_source.zig`는 같은 문단의 `%hlk` 시작과 끝을 확인합니다. 실제 software 끝 표식은 `%` 대신 NUL을 기록하므로 이 관측 변형과 완전한 ID만 허용합니다. 최대 중첩은 32이며 잘못된 끝·시작 없는 끝·끝 없는 시작은 거부합니다. 필드의 공통 command envelope는 기존 `field_start.Properties.parse`를 재사용합니다. 명령/URL은 실행하지 않습니다. 문단을 넘는 필드와 다른 필드 종류를 완성했다고 보지 않습니다.

실제 software 하이퍼링크 문단 88·93·98의 내부 삽입, 문단 93의 label 전체 교체·삭제에서 시작/끝 표식과 command의 원문 보존, 독립 전체 Section 및 저장 재열기를 확인했습니다. 끝 ID 불일치·끝 부재 반례는 원자적으로 거부하고 전체 원본 저장을 확인했습니다. native 집중 검사는 중첩·잘못된 짝·깊이 33 거부를 포함합니다. 현재 전수 검사는 1,481문단 중 1,301개 성공, software 101/101개 실제 삽입 성공입니다. 이 검사는 전체 편집 UI·페이지/서식 재조판·모든 필드 의미 완료의 증명이 아닙니다.

software의 원본 하이퍼링크 속성은 세 곳 모두 0x2800입니다. label 수정 시 bit 15 갱신과 편집 가능한 모델의 책임은 [필드 속성 계약](hwp5-field-attribute-edit.md)이 소유합니다. 일반 안전 저장을 주장하지 않고 계속 `allow_stale_layout` 실험 정책을 사용합니다. 한컴 동작 대조는 후속 작업입니다.

아래 초기 탭 단계의 1,103개·94/101개 및 2,692개 검증 수치는 당시 기록입니다. 하이퍼링크 연결 단계의 전수 1,301개·편집 집중 49개와도 구분합니다. 캡션·바탕쪽 연결 후 전수 성공은 1,304개이며, 계산식 준비까지 포함한 최신 ReleaseSafe 편집 집중 63개·전체 Zig 2,703개가 통과했습니다. Canvas 연결의 현재 범위와 브라우저 증거는 [제어 표시 계약](canvas-control-offsets.md)이 소유합니다.

편집 뒤에도 raw로 남기는 직접 제어 헤더 수는 `plain_text_source.Validation.preserved_direct_records`가 반환하고 모델의 `deferred_direct_records`에 유지합니다. 제어를 보존했다는 이유로 의미 모델까지 투영됐다고 보고하지 않습니다. 실제 anchor 연결의 할당 실패 검사는 open·연결 검증·apply·저장 실패 시 원본 값/byte-exact 저장 유지와 성공 출력 재열기를 검사합니다.

추가 anchor 연결에서는 `control_source.zig`가 기존 `control_links`와 `control_type_validation`을 재사용합니다. wire ID·제어 헤더의 순서/종류·누락을 검사하며 새 ID 대응표를 만들지 않습니다. 직접 CTRL_HEADER와 그 하위 레코드를 원문 보존하며 다른 직접 미지원 레코드는 계속 거부합니다. control mask만 믿지 않고 실제 토큰과 직접 제어 헤더에서도 연결 검증을 호출합니다.

저장기는 불변 Tree의 직접 부모와 source binding으로 문단을 찾습니다. 종전의 단일 `current` 문단 상태는 중첩 문단 뒤 부모 메타데이터를 복원하지 못하므로, 제어 포함 부모 편집에 앞서 제거했습니다. 기존 공개 API가 이 문단을 거부했던 단계의 실제 파일 손실이라고 주장하지 않습니다. 합성 writer 검사는 중첩 제어/문단 뒤의 부모 글자 모양을 수정하고 다른 레코드 원문 보존을 확인합니다.

실제 software 문단 0·42·44·80의 삽입은 독립 전체 Section oracle, 비대상 스트림과 저장 재열기를 통과했습니다. oracle도 부모의 직접 레벨 메타데이터만 바꾸고 중첩 자식 레코드는 원문으로 기대하도록 확장했습니다. wire ID 불일치·제어 토큰 누락은 원자적으로 거부하고 원본 byte-exact 저장을 확인했습니다. 전수 검사는 1,481문단 중 1,293개 성공, software 98/101개 성공이며 남은 3개는 하이퍼링크입니다. 전체 Zig 회귀는 별도 진행 중입니다. Canvas는 이 anchor들의 직접 입력을 아직 열지 않습니다.

공식 본문 제어 표의 1/8유닛 구분은 기존 `body/control.zig`와 `body/text.zig`가 소유합니다. 새 `edit/control_boundaries.zig`는 기존 토큰 파서를 호출하며 별도 제어 폭 대응표를 만들지 않습니다. 끝 PARA_BREAK는 편집 대상에서 제외하고, 제어 내부의 시작/끝 위치 및 제어 토큰을 삭제하는 범위를 거부합니다. 양옆 경계에서의 삽입과 제어 사이의 텍스트 교체는 경계 차원에서 허용합니다.

경계 검사만으로 제어 ID·필드 짝·자식 레코드 의미·범위 이동·저장 보존을 증명하지 않습니다. 현재 native splice는 탭/끝 표식과 위 연결 검증을 거친 알려진 anchor를 보존하며 기존 소유권·메타데이터 검사를 유지합니다. 제어 내부 위치와 제어 전체 삭제는 거부합니다. 새 제어 생성은 아직 허용하지 않습니다. Canvas의 탭 연결은 [제어 표시 계약](canvas-control-offsets.md)이 소유합니다.

실제 software 문단 33에서 탭 앞/뒤 삽입과 뒤의 텍스트 교체·삭제를 실행했습니다. 탭 원문 16바이트, 독립 oracle의 전체 Section 및 다른 스트림, 저장 후 재열기를 대조했습니다. 탭 내부 7위치와 전체 토큰 삭제는 명령 전후 값 및 원본 byte-exact 저장으로 거부 원자성을 확인했습니다. 첫 테스트의 Buffer/Uint8Array 타입 비교 실패는 바이트로 정규화해 해결했습니다.

Worker는 제어 포함 응답을 일반 Unicode로 디코딩하거나 텍스트 토큰으로 위장하지 않습니다. 임시로 native 저장/미리보기 projection을 재사용하며 별도 JS 제어 파서를 만들지 않습니다. 탭의 직접 입력 UI와 실제 브라우저 검증은 위 별도 계약을 따릅니다. 큰 문서 재투영 성능은 아직 별도 미검증입니다.

ReleaseSafe 전체 Zig 2,692개가 통과했습니다. 추적 전수 검사에서 1,481문단 중 1,103개가 성공했으며 software는 94/101문단 성공·제어 포함 7문단 거부입니다. 집중 테스트를 전체 편집 완료로 대신하지 않습니다.

Debug·ReleaseSafe·ReleaseFast 제품 편집 집중 검사는 Worker 회귀를 포함해 각각 46개가 통과했습니다.

실제 Worker 모듈의 Node 회귀는 제품 WASM으로 탭 뒤 텍스트 교체, 기존 다른 문단 편집 보존, 제어 내부 삽입 거부의 `applied=false`, 반복 삽입과 제어 표식/직접 입력 불가 상태 유지를 확인했습니다. Node 환경이 Worker 경계를 모사하며 실제 브라우저 증명이 아닙니다.

집중 검사는 탭의 모든 내부 경계, 양쪽 삽입 위치, 제어 전체 삭제, 필드 시작/끝 사이 Unicode scalar 경계, 잘못된 종료 코드와 문단 끝을 검사합니다. 기본 root 테스트에 연결했습니다. ReleaseSafe·ReleaseFast 각각 root 포함 4개 검사가 통과했습니다. 후속 연결 시 실제 파일의 전체 Section·비대상 스트림 대조와 손상/할당 실패 반례가 필요합니다.
